# 결정 기록 — 선택적 자체 토큰 계층과 확장형 권리·재고·검표 계층의 개발 범위 편입 (2026-09-29)

상태: **범위 편입 제안 — 설계·계획 문서화에 한정. 구현·배포·발행 미승인.**
효력: 사용자가 이 문서를 포함한 PR을 병합하는 때 생긴다. 작성 에이전트에게는 병합·승인 권한이 없으므로, 작성만으로는 효력이 생기지 않는다([프로그램 결정](PROGRAM_DECISIONS_20260928.md) §0과 같은 방식).
사용자는 언제든 이 결정을 바꾸거나 되돌릴 수 있고, 그 경우 새 결정 문서가 이 문서를 대체한다.
이 결정은 `AGENTS.md`의 사람 전용 병합, 비작성자 exact-HEAD 검토, 단일 작성자, UNKNOWN fencing, 자동 재시도·polling 금지, 잠금 blob 규칙을 바꾸지 않는다.

## 0. 이 문서가 하는 것과 하지 않는 것

1. 사용자 요청에 따라 두 항목을 개발 범위에 편입한다.
2. 이번 실행 권한은 설계·계획 문서화에 한정된다.
3. 토큰의 구체 정책과 구현 착수, 운영 발행은 별도 단계다.
4. 현행 새 coin/TIX 구현 제한을 전면 해제한 것이 아니다.
5. 과거 Task 005와 9월 28일 결정은 역사적 기록으로 보존한다. (보존은 수정하지 않는다는 뜻이다. 9월 28일 결정과 Task 005의 결정 5는 현행 잠금의 근거로 계속 유효하다. §4)
6. 기존 제한과 새 범위가 어떻게 공존하는지 후속 우선순위를 명시한다. (공존은 §4, 우선순위는 §5)

### 4.1 Task 005 재확인 항목 — Astra 판정 수신

Task 005는 두 가지를 남겼다. 하나는 "새 coin/TIX 모듈(B)을 다시 제안하는 사람이 있으면 ADR 트리거를 재확인한다"는 열린 질문이고(`docs/tasks/TASK_005_MEGA_COMMERCE_PROGRAM.md:174`), 다른 하나는 Astra 판정 항목을 Astra가 뒤집기 전에는 JunTae에게 다시 묻지 않는다는 규칙이다(`:62-63`). 이 PR의 토큰 청사진은 **구현이 아니라 설계 문서**이고 사용자의 지시에 따라 작성했다. 그러나 "자체 토큰 패키지의 청사진"이 위의 "다시 제안"에 해당해 ADR 트리거를 당기는지는 이 PR이 정할 수 없어 Astra 아키텍처 검토의 질문으로 올렸다(§6.3의 6).

**Astra 판정** — PR #79 댓글 [`5901429335`](https://github.com/BeautifulMind-JT/kix-protocol/pull/79#issuecomment-5901429335)(`cursor[bot]` 계정으로 2026-09-30 게시): **"해당한다."** 트리거는 "proposes"(제안)이지 "implements"가 아니고, 자체 토큰 계층을 범위에 넣고 코인 형태(F1~F4)를 비교·권고하는 것은 구현이 아니어도 "다시 제안"에 해당한다는 이유다. 그래서 **범위·한계를 기록하는 ADR(TL-A)을 TL-0 착수 전에 둔다.** 그 ADR은 TL-2의 ADR + Astra 재결정(잠금 해제)을 대체하지 않는다. Astra는 이 판정이 **이 docs PR의 병합을 막지 않는다**고 적었다. 이 PR은 사용자가 병합하기 전에는 효력이 없고, 이 판정을 받아들일지는 사용자가 정한다(D-B).

## 5. 후속 우선순위와 의존성

### 5.1 원칙

- 진행 중이거나 예정된 Track K·Track P 작업(첫 묶음 잔여 검토, 4단계 비교 준비, hosted CI 확인, Wave 6 골격, P-SDK-0 등. 프로그램 결정 §6은 이를 후속 과제 후보로 적는다)은 이 문서 때문에 **중단하거나 순서를 바꾸지 않는다.** 이번 편입은 그 작업의 범위·게이트를 바꾸지 않는다.
- TL·RS 작업은 각각 새 작업문서, 새 branch, 새 세션, 새 PR로 진행한다. 작업문서는 승인된 orchestrator가 작성자 세션 밖에서 확정한다. 이번 세션에서는 어느 것도 dispatch하지 않았다.

## 6. 권고안과 사용자 결정

### 6.1 권고안 (근거는 각 청사진)

- **토큰 역할.** 설계 대상 메커니즘은 U2 책임 담보(조건부: 담보 자산은 비교 후 결정, 토큰 단독 담보 금지)와 U3 참여 보상(조건부: 비양도 회계 먼저) 두 가지다. **이것은 자체 토큰의 채택 권고가 아니다.** U2에서 토큰은 보조 담보 후보이고, U3에서 토큰 전환은 TL-3 이후의 선택 기능이다. U1 수수료는 지급 수단 강제 불채택·할인 크레딧 보류, U4 거버넌스는 보류, U5 팬 혜택은 권한 객체로 구현하고 토큰 연계는 보류, "보유=혜택"은 불채택이다. 토큰의 존재 자체도 선택 사항이다.
- **토큰 표현.** 미결. F1 오픈 루프 코인, F2 폐쇄 루프 토큰, F3 권한·영수 객체, F4 오프체인 포인트를 TL-0가 비교한다. 규제형 여부는 초기화 때만 정할 수 있고 되돌릴 수 없으며, 공급 모드는 유연(Unknown)이 기본이지만 고정·소각 전용으로 바꾸면 되돌릴 수 없으므로 첫 배포 전에 정한다.
- **권리 확장.** 16슬롯은 회귀 기준으로 보존하고, 새 프로파일은 읽기 전용 `ShowControl` + 독립 공유 객체 페이지 + GA 슬롯 범위 샤드 + 해시 라우팅 nullifier 샤드로 설계한다. 위임의 최소 단위는 페이지다. 큰 단일 `Show` 유지안은 산술로 막히고(직접 발급만이면 N ≤ 28,444, 유료 발급이 있으면 N ≤ 6,095, 비공개 경로까지 쓰면 N ≤ 1,855), Show 내부 분할안은 고정 소스의 공식 문서가 피하라는 유형이다.
- **주요 위험.** ZK 폐기 루트가 발급마다 바뀌어 "현재 루트만 수용" 규칙이 규모에서 증명을 계속 무효화한다는 점(RS-2의 핵심 설계 질문이자 구조 권고의 선행 결정), 발행자 서명 함수가 쓰는 소유 객체 `IssuerCap`의 직렬화(참조로만 쓸 때의 잠금 여부는 미확인), 잠금 v4 커널의 `MAX_SEATS = 4,096`, 새 회로·ceremony·verifier 이전, 페이지 크기·경합의 측정 부재.
