## 3. LC-FACT — 늦은 사실 보존

제공자 수신 원문, provider/account/환경/endpoint/API-version/contract-version/
상품/결제수단/operation-kind/event-item/operation과 적용 프로파일 버전,
검증 결과와 원문 참조를 수신 ACK 전에 내구성 있게 확보해야 한다. 현재는
inbox 구현이 없으며 이 문장은 ACK할 수 있다는 허가가 아니다. 보존 실패 시
제공자 ACK를 하지 않고 해당 범위의 신규 의도를 제한한다.

같은 event-item의 다른 내용은 원본을 덮어쓰지 않는다. event identity와
경제 operation identity는 서로 다른 중복 경계다. batch delivery id를 서로
다른 capture의 단일 event id로 사용하지 않는다. 현 단계 토스 일반 카드에는 KCP·
이지페이 특유의 다거래 배치/ID재사용 처리를 구현하지 않는다. 토스의 transmission ID,
결제 ID와 canonical fact ID의 매핑·재전달 안정성은 여전히 확인·설계 대상이다.
원문 출처 미검증 webhook은 검증된 자금 사실로 쓰지 않고, 원문을 신호로 보존한 뒤
인증된 단건 조회로 결합을 확인하는 방향만 정한다. 미구현 inbox/조회 성공을 가정하지 않는다.

회수·만료 뒤 실제 capture 또는 체인 성공이 도착해도 원래 operation/grant/주문에
결합한 사실을 보존한다. 현재의 권위가 대사하되 옛 lease를 되살리거나 현재 다른
구매자의 재고를 해제하지 않는다. 미바인딩 사실은 UNMATCHED로 보존하고 임의 주문을
생성하지 않는다. 이 용어는 계약상 처리 상태이지 이번에 추가한 kernel enum이 아니다.

v4의 상충 Err(Capacity)는 bound 격리와 논리시간 변경이 이미 적용된 결과다.
상위 저장/처리 계층은 이를 전부 rollback/no-op으로 취급하지 않는다. 저장하지 못한
새 원문은 별도 custody 책임을 가진다. 토스의 자동 재전송은 마지막 간격이
4,096분(68시간 16분), 명시된 간격 합계가 5,461분(91시간 1분)이다. 이 계산과
관리 재전송 가능성을 근거로 수일 뒤 도착하는 사실의 보존을 운영 요구로 둔다.
공식 근거·2026-09-17 확인일은 [제공자 프로파일 §2–3](PG_TOSS_CARD_PROFILE.md)에
있다. 68시간·91시간·15일 어느 것도 KIX의 증거 삭제/UNKNOWN 해제 시한으로 정하지 않는다.
종결 뒤 모순 사실도 과거 결과를 지우지 않고
추가 대사·의무 판단 대상으로 남긴다. 반환 필요 표식은 실제 환불 완료가 아니다.

## 4. LC-CUT — 회수 후 재생 경계

`lease_generation`, `ExecutionFence.generation`, business epoch, wire/semantics
version은 서로 바꾸어 쓸 수 없다. grant g의 신규 약정 중단 위치 C_g와 체인
회수 확정 증거 H_g를 연결하되 서로 다른 권위의 커밋 위치로 유지한다.
두 숫자를 하나의 전역 sequence처럼 비교하지 않는다. 관계 증명이 필요하다.

역사 재생은 당시의 승인 입력·정책·그때 유효했던 lease 근거로 기존 약정을 복원한다.
회수 후 옛 generation의 새로운 예약/발행 허가는 적용하지 않는다. 그러나 C_g 뒤의
늦은 실제 자금/체인 사실과 반환 의무는 버리지 않는다. 로그를 cut에서 절단해
후속 사실을 없애지 않는다. historical replay에서 외부 호출을 실행하지 않는다.
새 외부 실행은 복원 이후 현재 권위와 실제 전송 허용 조건을 다시 만족해야 한다.

source cut·이전 writer 차단·미발행 약정을 검증하지 못하면 해당 범위의 신규
소비/재위임을 보류한다. 침묵·복구 timeout·체인 미발행만으로 미사용 잔량을 만들지
않는다. chain freshness 시간원·기한, 독립 증거 가용성·비협조 cut 증명은 미정이다.
따라서 이 초안만으로 운영 회수나 오프라인 판매를 승인하지 않는다.

PG의 API 키 차단·조회·웹훅 재전달 규칙은 이미 전송된 자금 요청 또는 체인 lease의
회수를 증명하지 않는다. 토스 15일 멱등키 만료는 C_g/H_g와 무관하며, 그 뒤 UNKNOWN을
새 키나 다른 PG로 재송신할 허가가 아니다. 독립 회수 cut은 계속 미정이다.

동일 물리 로그에 두 사실 종류를 보존할 수는 있으나 chain effects/확정 증거와
오프체인 커밋의 필드는 분리한다. 로컬 fsync가 chain finality를 대신하지 않는다.
#11의 현재 v1 로그에 이를 구현한 것으로 표시하지 않는다. v1을 v4로 조용히
재라벨링하거나 기존 golden을 덮어쓰지 않는다.

## 5. LC-TERM — 조건 평가·지정 주체 승인·내구 기록에 따른 운영 종결

### 5.0 기존 정의의 한계와 변경의 의미

이전 §5는 PG가 최종 실패/void 또는 영구 비실행을 보장하는 operation 단위 인증
증거를 종결의 필요조건으로 삼았다. 2026-09-16 PG 비교 보고서
`PG_COMPARISON_RESEARCH_7e580b26c04e.md`(blob
`7e580b26c04edb226a729c79a2ec6731c1f858b2`)에서는 토스·NICEPAY·KCP·이니시스·
이지페이 모두 **LC-TERM 전체 충족을 공개 자료로 확인하지 못했다**.
이는 다섯 제공자가 기능이 없다고 입증했거나 서면으로 보장을 거절했다는 뜻이 아니다.
질문지 회신도 아직 없다. 없는 보장을 있는 것으로 추정하지 않는다.

카드 승인은 PG가 VAN을 통해 카드사에 요청하는 구조이고 승인·매입·취소·실제 반환은
같은 사실이 아니다[S4]. PG도 원천기관 처리와 응답에 의존하므로 자사 조회와 통보
규격만으로 미래 모든 예외의 부재를 보장한다고 해석할 수 없다. PG가 이런 보장을
제공하지 않으면 옛 정의는 UNKNOWN과 예약을 종료할 수 없는 필요조건에 매달린다.
**이번 변경은 더 강한 외부 사실을 얻는 것이 아니라, 남는 불확실성 아래 허용되는
운영 판단과 책임을 명시하는 보장 수준의 변경**이다. 인증된 관측과 원문 보존은 유지한다.

업계 비교의 범위: '일반 티켓팅은 타임아웃·대사 배치·운영 예외로 흡수한다'는 사용자
비교 관점이다. 모든 티켓팅 사업자의 내부 절차가 동일하거나 승인 기록이 없다는
전수 근거는 없다. 공식 결제 문서는 불명확한 결과의 대사와 사후 웹훅을 설명하고[S5],
공개 티켓팅 시스템에도 수동 환불 관리 경로가 있다[S6]. KIX는 이런 판단의 조건,
증거 범위, 승인자, 위임 한도, 잔여 위험을 명시적 계약·기록으로 남긴다.
이점은 재현 가능한 판단·권한 통제·사후 책임 추적, 비용은 증거 수집·저장·운영 승인·
대사 지연·예외 대응이다. 담보/여신에서는 'PG가 확인한 사실'과 '운영자가 위험을
감수하고 닫은 건'을 구분해야 미확정 결제를 확정 수익 또는 무부담 담보로 오인하지
않는다. **기록은 위험 공개에 필요하지만 독립 담보 실재·우선순위·법적 효력을 대신하지 않는다.**

### 5.1 정의와 적용 범위

LC-TERM = **객관적 조건 전부 충족 + 유효한 지정 승인 주체 + 승인의 내구성 있는 기록**.
여기서 종결은 '원 operation의 추가 송신과 일상적인 미결 처리 흐름을 닫는 운영 결정'이다.
'원천 결제가 영구히 없었다/실패했다', '환불 이행', '법률상 채무 소멸', '체인 권리
회수 완료'의 선언이 아니다. provider 사실과 사건 처리 상태를 별도로 유지한다.

- 외부 사실: 미확인/확인된 승인/취소·반환 등 실제 증거의 상태를 보존한다.
- 운영 판단: 조건·증거 범위를 특정해 승인된 종결을 별도로 기록한다.
- 허용 후속 조치: 무엇을 중단/해제/계속 보존할지 승인에 명시한다. 종결 승인 자체는
  슬롯·재고·담보·review·증거의 포괄 해제 권한이 아니다.

아래 C1~C5는 **토스 국내 KRW 일반 카드의 '승인 사실 미확인' 운영 종결 경로**다.
확정 capture가 존재하거나 조회에서 승인 이력이 확인되면 이 부재 경로로 닫지 않는다.
취소/부분취소에 승인 이력이 있다면 그 capture를 보존한 별도 반환·대사 경로다.
제공자가 더 강한 종결 증거를 주면 첨부하지만 그 보증을 반드시 얻어야만 진행되는
구조로 되돌리지 않는다. 실제 MID/환경/API·계약 버전/상품/수단/operation 종류,
원요청·키 사용 이력·금액/자산이 특정돼 있어야 C1~C5 평가를 시작할 수 있다.

### 5.2 객관적 조건 — 하나라도 미충족/미확인이면 승인 없음

| 조건 | 토스 카드에서 확인할 내용 | 필요한 이유 / 빠질 때 깨지는 것 |
|---|---|---|
| C1 인증된 조회에서 승인 사실 미확인 | 해당 계정의 HTTPS+Basic GET `/v1/payments/{paymentKey}` 또는 `/v1/payments/orders/{orderId}`를 사용[S1/S3]. 키 둘 다 알면 둘 다 대조. 정상적으로 완료된 조회의 응답·시각·범위·음성 결과를 보존 | 잘못된 MID/환경/ID 또는 통신 오류를 '결제 없음'으로 오인해 실제 결제의 근거를 지움 |
| C2 재전송 검토기간 충족 | 알려진 이벤트의 자동 재전송 최대7회·간격 1/4/16/64/256/1024/4096분과 관리 재시도 상태를 확인[S2]. 아래 §5.3의 관찰 기준점과 5,461분 경과를 기록 | 통상 재전달 중인 사건을 지나치게 일찍 닫음. 단, 통과해도 미래 전달/성공 부재는 증명하지 않음 |
| C3 미종결 전송 시도 없음 | 모든 원요청·attempt·worker·outbox·retry/운영 수동 송신 경로를 열거하고, 능동 전송/대기 job/재개 권한 없음과 원operation 재전송 fence를 입증. 원격 처리중 증거가 있으면 미충족 | 숨은 작업자·재시작·새 키가 같은 결제를 실행하거나 '없는 이력=미전송'으로 오인 |
| C4 대사 완료 | 전체 로컬 원요청·응답·inbox/미처리 큐와 계정에서 접근 가능한 PG 조회·거래/정산 자료를 operation별 대조. 기간·페이지·watermark·누락·불일치와 결론을 기록[S3]. 필수 자료의 구멍 또는 미처리 관련 신호가 있으면 완료 아님 | 일시적인 단건 조회 또는 미처리 통보만 보고 실제 자금·상충 증거를 놓침 |
| C5 가능한 제공자 증거 첨부 | 조회 원문, 받은 서면 회신·거래기록·망취소/취소 응답 등을 출처·범위와 함께 첨부. 미제공/보장하지 않음/회신 대기를 구분하고 요청·회신 이력도 기록 | 승인자가 일부 증거를 골라 쓰거나 미수신 보증을 받은 것처럼 주장 |

C1에서 timeout, 401/403, 429, 5xx, 잘못된 ID, 파싱 오류는 부재 증거가 아니다.
정상 제공자 오류 응답의 not-found도 **그 조회에서 미확인**이라는 의미일 뿐이다.
한 번만 조회하고 시간만 기다리는 것으로 끝내지 않는다. 기간과 대사가 끝난 뒤
승인 직전에 다시 조회하고, 증거 snapshot/명령 상태 버전에 결합해 평가한다.
known capture, 관련 미처리 신호 또는 증거 변경이 있으면 이전 평가를 무효화한다.
이는 수집 후 승인까지의 외부 원천 변화까지 원자적으로 봉쇄한다는 보장은 아니다.

C3의 '시도'와 '경제 결과'를 분리한다. 소켓 timeout 후 로컬 송신 작업이 종료돼도
원격 경제 결과는 미확인일 수 있다. 모든 로컬 시도가 빠짐없이 식별돼 종료/재송신
차단됐고 그 UNKNOWN이 대사에 포함됐다는 의미이지, PG의 미실행을 증명하는 것이 아니다.
`IDEMPOTENT_REQUEST_PROCESSING` 등 현재 원격 처리중을 보여주는 근거, 살아 있는
sender 또는 출처를 설명할 수 없는 시도가 있으면 C3는 거짓이다. 단순히 attempt를
'완료'로 덮어쓰거나 승인으로 누락을 메우지 않는다. 이 범위를 넘어 남는 원격 위험은
승인 기록에 그대로 남긴다. 이 구분으로 옛 제공자 보증 필요조건을 이름만 바꿔 유지하지 않는다.

C4에는 원천별 접근 가능 여부를 기재한다. 카드사 내부 전체 자료·절대 최종성 확인서는
필수로 추가하지 않는다. 제공 가능한 PG 자료를 생략하지 않으며, 제공되지 않는 자료는
없음을 기록한다. 로컬 원요청·모든 송신 시도·관련 수신 큐의 완전성은 필수다.
C5의 '있는 만큼'은 C1/C3/C4의 필수 자료까지 생략해도 된다는 예외가 아니다.

### 5.3 시간 조건과 15일의 관계 — 시간만으로 종결하지 않음

확인일 2026-09-17. 공식 자동 재전송의 마지막 **간격**은 4,096분=68시간16분이고,
간격 합은 5,461분=91시간1분이다[S2]. 토스 설명의 '3일19시간'과 표의 합계 계산을
구분한다. 관리 재시도·새 이벤트·처리 지연은 이후에도 있을 수 있다. 재전송이 끝나는
것은 전달 절차의 종료이지 승인/실패의 최종성이 아니다.

**계약상 관찰 기준점 제안(토스의 추가 보증 아님):** 신규 송신 차단이 내구성 있게
기록된 시각, 마지막 로컬 송신 종료시각, 마지막 새로운 중요 인증 사실의 수집시각, 확인 가능한
각 이벤트의 최초 전송시각 중 가장 늦은 것을 T_anchor로 삼고 `T_eval >= T_anchor +
5,461분`을 요구한다. 알려진 관리 재시도가 미처리이면 C4도 미충족이다. 모든 관련
원문 시각·offset·시간원과 판단 근거를 보존하고, 인증되지 않은 임의 timestamp를
anchor로 채택하지 않는다. 새 관련 사실이 확인되면 이전 조건 평가를 다시 한다.
같은 음성 조회의 반복 확인·동일 snapshot·정확한 중복 전달은 새 중요 사실로 세지 않아
T_anchor를 계속 뒤로 밀지 않는다. 승인 직전 재조회는 C1의 신선도 확인이며, 내용이
달라질 때만 이전 평가를 무효화하고 새 기준점 여부를 판단한다.

최초 웹훅 전송시각을 알 수 없으면 **'PG의 실제 재전송 창이 끝났다'고 표시하지 않는다**.
`origin_unknown`을 남기고, 위 로컬 관찰기간을 충족했다는 제한된 사실만 사용한다.
이 경우는 1단 자동승인 제외이며, 나머지 조건 충족 뒤 2단에서 원격 잔여 위험을
명시적으로 판단한다. 조회 부재인데 존재 여부조차 모르는 이벤트의 시작시각을 만들어
계약을 닫지 않는다. 시간원/로컬 시도 종료를 확인할 수 없으면 C2 자체가 미충족이다.
따라서 C2는 '알려진 전달창 검토+정의된 관찰기간'이지 미래 이벤트 소진의 증명은 아니다.

멱등키는 최초 요청에 사용한 날부터 **15일**, 같은 키/API키/주소/메서드 조합의 첫
응답을 재사용한다[S1]. 91시간 조건과 기산점·목적이 다르다. 조건들이 15일 안에
충족될 수 있지만, 승인 후에는 남은 유효기간과 무관하게 원operation의 POST 재송신을
차단한다. 15일 경과가 승인을 촉발하지 않으며, 더 기다렸다는 이유로 안전 등급도
올리지 않는다. 경과/키교체 후에는 새 키로 같은 UNKNOWN 작업을 보내지 않고 GET·대사만
계속한다. 정확한 제공자 만료 경계/계정 예외를 모르면 1단 제외·2단 검토 사유다.
기산점을 알 수 없는 상태를 '15일 경과'로 간주하지 않는다. GET의 음성 결과와 재송신
차단은 첫 응답 캐시와 별도의 근거다. 수신·명령 이력의 보존기간을 15일로 정하지 않는다.

논리식은 `C1 AND C2 AND C3 AND C4 AND C5 AND 유효한 승인 AND 내구기록`이다.
시간만 참이면 결론이 나오지 않는다. 조건 미충족을 사람 승인으로 예외 통과시키는
경로도 없다. 이것이 '시간 경과만으로 UNKNOWN을 실패 처리하지 않는다'는 원칙과의
관계다. 외부 결과는 여전히 미확인일 수 있으며 오직 운영 결정의 상태만 달라진다.

### 5.4 승인 주체와 기록 — 인간/자동 모두 동일한 추적 요건

사용자가 지정한 사업상 권한 주체가 직접 승인하거나 명시적 규칙으로 위임한다.
실명·서비스 principal·대체 담당자는 아직 미지정이다. 담당자가 없거나 위임이 만료·
회수됐으면 승인하지 않는다. 휴가/장애 시 시간 경과로 승인권을 넘기지 않는다.
대체자는 같은 또는 더 좁은 scope의 사전 기록된 권한을 가져야 한다.

승인 기록의 필수 내용(문서상 필드이며 schema/코드 아님):

| 묶음 | 반드시 남길 내용 |
|---|---|
| 정체성과 범위 | decision ID, case/원command/provider-account-operation, 환경·API/계약·상품/수단, 원요청·금액/자산, 현재 scope/실행 세대 |
| 조건과 증거 | C1~C5 각 평가·근거 원문 위치/무결성·출처·수집시각, T_anchor/시각 신뢰·origin_unknown, 모든 시도 목록·송신 fence·대사 범위/cut |
| 승인 권한 | **자동/사람 구분**, 실제 principal, 권한 issuer, **위임/직접승인 규칙 ID와 버전·해시**, 유효기간·회수상태, 대체승인 여부 |
| 결정과 위험 | 승인/거절·이유·남은 provider uncertainty, 상충/분쟁 여부, 금액·누적 한도 판정, 허용 후속조치의 정확한 목록, 늦은 사실 수신·보상 책임 |
| 동시성·재생 | 평가한 상태/증거 revision, 적용 전 재확인, 승인시각·내구 commit 위치, 이전 결정/정정 링크, 실행했거나 아직 하지 않은 후속조치 |

사람의 직접 승인에도 규칙 ID를 비우지 않고, 사용자에게서 부여받은 직접승인 정책을
참조한다. 자동 승인은 서비스의 고유 identity와 위임 규칙을 함께 기록한다. 자연어
'승인함'·LLM 출력 또는 단순 hash 하나는 권한·내구성·원문 가용성의 증명이 아니다.
비밀키/카드정보를 승인문에 적지 않는다. 원문 접근권한·증거 범위를 가진 검토자는
조건과 권한을 재검증할 수 있어야 한다.

상태/증거/권한이 바뀌면 이전 평가로 commit하지 않는다. 유효 권한과 조건 재검사를
통과한 승인·원operation 송신차단·사건 상태 변경은 같은 권위 경계에 내구성 있게
기록되거나, 이미 내구적으로 성립한 차단을 확인한 뒤 기록돼야 한다. 그 다음에만
해당 승인에 허용된 조치를 실행한다. 응답만 유실돼도 같은 결정은 재사용하고 중복
해제하지 않는다. crash·증거 저장 실패 시 승인 성공을 응답하지 않는다. 저장소 선택,
서명 포맷, 실행 구현은 이번 범위 밖이며 현재 이 경계는 구현되지 않았다.

### 5.5 자동화의 두 종류와 3단 승인

증거 수집·조건 평가·승인 요청서 작성의 자동화는 **승인권의 위임과 별개**다.
AI는 자료 정리와 설명안을 만들 수 있지만, 사실 출처나 평가기 판정을 대신하거나
조건을 선택적으로 생략하지 못한다. 승인 자동화는 아래 규칙을 기계적으로 검증하고
지정 권한으로 기록하는 행위이며, 자유로운 LLM 판단을 권위로 채택하지 않는다.

| 단 | 경계 | 처리 |
|---|---|---|
| 1 자동 승인 | C1~C5 모두 참, 유효한 사전 위임, 지정 MID/일반카드/operation·조치 범위, 건별 금액·기간별 누적액·건수 한도 이내, 상충·분쟁 없음, origin/시각 근거 신뢰, 아래 위험 제외에 하나도 해당하지 않음 | 위임 서비스가 조건/상태를 재확인한 뒤 승인 기록. 사람은 기한이 정해진 배치 로그를 사후 확인. 사후확인은 사전 조건·권한을 대체하지 않음 |
| 2 사람 건별 승인 | C1~C5 모두 참이나 금액/범위/잔여 위험·origin_unknown 등의 이유로 자동 위임 밖 | 현재 권한 있는 사람이 남은 위험·정확한 허용 조치를 건별 승인. 동의하지 않거나 담당자 미지정이면 보류 |
| 3 승인 없음 | C1~C5 중 미충족/미확인, 필수 증거 누락, 능동 시도, 확인된 capture를 부재로 종결하려 함, 권한/저장 검증 실패 | 자동·사람 모두 승인 없음. 조회·대사·증거 확보를 계속하며 시간으로 통과시키지 않음 |

금액·누적 한도·관찰정책의 운영 수치, 배치 검토주기와 담당자는 사용자가 정한다.
비어 있는 한도를 '무제한'이나 임의 숫자로 채우지 않는다. 한도를 피하려는 operation
분할은 원주문/계정·기간 합계로도 검사할 정책이 필요하며, 그 계약이 없으면 자동 제외다。
상충 증거가 있으면 자동 제외이고, 대사에서 해소하지 못한 충돌이면 C4 미충족이므로
2단으로도 통과하지 않는다. 분쟁은 자동 제외이며 사람에게 분쟁 권한이 없으면 승인 불가다.

**LC-FACT만으로 오승인 비용이 제한되는가: 아니오.** 다음 경로는 자동 승인 금지다.

| 위험 경로 | 원문 보존만으로 제한되지 않는 손실 |
|---|---|
| 좌석 재판매·권리 발행/소비 뒤 과거 결제 성공 | 유일 좌석 제공 불가, 이중 약정·행사 종료 등 비가역 손실 |
| 승인 뒤 자금 지급·준비금 해제 | 늦은 환불/차지백의 자금 부족, 운영자 도산·회수 불능 |
| 담보·채권 해제/재담보·대출 실행 | 제삼자의 선지급·우선순위·이중부담 위험. '닫힘'을 외부 최종성으로 오인 |
| 다른 PG·새 키 재송신 또는 이중 보상 | 중복 청구·환불과 카드사 조정의 중복 지급 |
| 관측 슬롯 해제 후 후기 수신 용량 부족·증거/ID 삭제 | 늦은 성공을 받아내지 못함, UNKNOWN의 재실행·이력 유실 |
| 승인 뒤 로그 유실·stale 승인 재생·권한 변경 경쟁 | 차단 또는 보존되지 않은 승인·중복 후속 실행 |
| 한도 우회·분쟁/비용·전이 손실의 합계 불명 | 원금 상한이 총손실 상한이 아님; 배치 사후확인 전에 누적 가능 |

위 경로와 연결된 자동 조치는 **제외**한다. 장래 조치별로 독립적으로 유효한 제한과
복구 능력이 입증돼 규칙을 별도 승인하기 전에는 금액이 작다는 이유로 허용하지 않는다.
현재는 내구 승인·사후 수신 경로와 risk bound가 미구현이므로 **실제로 활성화된 1단
자동 승인 범위는 0**이다. 3단 구조를 계약으로 검토한 것과 자동화를 가동한 것은 다르다.
2단 승인도 체인 권리·소비·고객/제삼자의 권리를 임의 변경하거나 필수조건을 우회하는
권한이 아니다. 보상 재원·허용 조치가 없으면 운영 메모만 남기고 자원 해제는 보류한다.

위임 규칙 변경은 사용자가 지정한 인간/법인 정책 권한자의 별도 절차다. 규칙 ID·버전·
허용 조치·한도·유효기간·적용 시작점·변경 이유·검토자·승인자를 불변 기록으로 남기며
기존 규칙을 덮어쓰지 않는다. AI/자동 승인 서비스는 자기 규칙·승인자·검증기·키·한도를
수정/활성화할 권한을 갖지 않는다. 변경 제안만 가능하다. 규칙 확대는 새 승인,
회수/긴급정지는 지정 권한자의 기록된 조치이며 재가동에는 별도 승인이다. 심사 중인
요청도 최종 commit 시 현재 규칙/회수를 다시 확인한다. 옛 위임으로 새 승인 금지,
과거 승인·책임을 새 규칙으로 소급 정당화 금지다.

### 5.6 종결 후 늦은 성공 — LC-FACT 연결

늦은 webhook은 신호이며 인증 조회·원operation 결합 후 사실을 보존한다. 이미 승인된
종결 기록을 삭제/덮어쓰거나 기존 command의 최초 결과를 바꾸지 않는다. 정정 사건을
연결해 운영 종결을 재검토하고, '사실 미확인 상태에서 이 근거로 승인했음'과 '이후
성공 확인'을 모두 보인다. **원 operation의 새 승인 요청을 다시 보내지는 않는다.**

실제 capture는 원래 event/경제operation 경계에서 한 번만 반영한다. 현재 재고/체인
권리/취소/소비 상태를 대조하고 옛 주문 부활·다른 구매자 좌석 해제는 금지한다. 이행할
수 없으면 반환 의무·분쟁/대사와 필요하면 자금 노출 조정을 생성할 계약이 필요하다.
기존 환불·차지백·보상도 먼저 대조해 이중 반환을 막는다. 수취인 지급/담보에 영향을
주면 해당 당사자에게 정정 노출을 알리고 신뢰 범위를 재평가한다. 이런 의무의
실제 이행과 손실 흡수가 보장됐다는 뜻은 아니다.

후기 사실 수신/대사 책임과 기록의 가용성을 유지하지 못하면 위험이 없어지는 것이
아니라 종결 후속 해제의 조건이 성립하지 않는 것이다. 새 위임·다른 PG로 과거 이력을
버리지 않는다. provider 보증 없음 또는 '보장하지 않음' 회신 자체는 실패 사실이 아니다.

### 5.7 승인시각과 적용시각, ReturnRequired

기준 main `73f324a00f345e120014718b67a7c03ecbf1198a`의 잠금 커널
`69564b166f0c27f9af5d8422f0a466b18d74c20f`에서 `observe_capture`는 첫 capture를
보존한 뒤 `ctx.now_ms >= expires_at_ms`이면 ReturnRequired로 분기한다.
CaptureObservation에는 provider 승인시각 필드가 없다. expire는 Held만 해제하고
PaymentUnknown은 TTL만으로 해제하지 않는다. **아래 경로는 소스 제어흐름에서 성립한다.**

예시(정적 설명이며 새 실행 transcript 아님): 주문 TTL=600,000ms, 제공자 승인시각
599,000ms, 기존 전송 후 PaymentUnknown, 최초 관측 적용시각 327,660,000ms
(5,461분). 금액/문맥·예약 슬롯이 유효하면 승인시각은 입력되지 않으므로 capture가
보존되고 ReturnRequired가 된다. 테스트를 수정하거나 91시간 시험을 새로 돌리지 않았다.

제공자 `approvedAt`의 원문·offset·출처검증·정규화한 발생시각을 수신시각 및 단조
적용시각과 **별도 사실**로 보존하는 방향을 채택한다[S3]. `ctx.now_ms`를 승인시각으로
되돌리거나 그 값을 조작해 v4의 분기를 피하지 않는다. 향후 권리 이행/반환 정책은
승인 당시 예약·위임 유효성, 현재 취소·재고·이미 발행/소비된 권리와 함께 발생시각을
검토해야 한다. TTL 전 승인도 다른 권리의 침해나 자동 부활을 허용하지 않는다.
현재 v4 결과를 숨기고 PaymentConfirmed로 바꿔 보고하지 않으며, 정책 변경은 별도
커널 버전/승인·시험 범위다. **ReturnRequired는 종결도, 환불 요청 승인도, 실제 환불
완료도 아니다.** 이는 capture를 포함한 미이행 의무 표식이므로 승인 부재 경로 C1로
종결할 수 없다. 반환 작업의 종결은 그 별도 operation의 증거와 정책을 필요로 한다.

### 5.8 슬롯·기록·review에 연결되는 권한의 한계

| 대상 | 이번 정의와의 연결 | 별도로 필요한 조건 |
|---|---|---|
| 슬롯 해제 | 종결 결정에 해당 슬롯의 정확한 조치가 포함되고 내구 기록이 성립한 뒤, 중복 없이 처리할 수 있는 자격 | 후기 사실 custody·처리예산으로 안전하게 인계됐다는 검증, 전송차단·원operation/기록 보존. 없으면 해제 금지. capture의 reserved→stored는 총예산 회수 아님 |
| 기록 회수 | 운영 사건 종결은 active 참조 하나가 바뀌는 사유일 뿐 | 명령 재실행 방지, 법정/분쟁·대사 보존, lease/재생·담보/환불 참조, 원문 접근·복구 검증은 §6 그대로. 승인 한 번으로 증거 삭제 금지 |
| review 해제 | payment workflow 종결과 분리된 승인 조치 | 충돌 원인·영향 operation·모든 관련 사실의 해결과 권한. 상충 원문은 남기고, 미해결 충돌/분쟁이면 해제하지 않음 |

현재 잠금 커널에는 위 종결 승인·해제 전이가 없다. 이 문서는 의사결정 경계만
변경하며 메모리 용량을 늘리거나 가상 GC·새 terminal enum·색인·저널을 만들지 않는다.

## 6. 기록 회수와 의존 참조

메모리 결과 캐시의 축출은 권위 이력 폐기가 아니다. 캐시에 없으면 원결과를
검증할 수 있는 보존 위치를 조회한다. 조회 실패를 미실행으로 승격하지 않는다.
상세 이력을 줄이려면 지원 종료된 command 범위가 신규 실행될 수 없다는 별도
거절/압축 경계가 필요하다. 단순 tombstone 무한 증가로 문제를 옮기지 않는다.
현재 v4에는 이 회수 경로가 없으므로 시험에서도 가상 GC를 넣지 않는다.

회수 후보의 active order/operation, reserved slot, review, retained unbound fence,
반환 의무, replay window, dispute/법정 보존 참조를 확인해야 한다.
보관 성공은 해시뿐 아니라 실제 원문 접근·출처·완전성·복구 가능한 보존 위치의
근거가 필요하다. 아직 저장 backend가 없으므로 그 성공을 모의 boolean 하나로
운영 완료 처리하지 않는다. 정책 수치와 계약 당사자는 미정이다.

증거 추가/회수/binding/review 해제에 따른 색인 일관성은 이후 함께 검토한다.
이번에는 retained-conflict 선형 탐색을 변경하지 않는다.

## 7. 미정 입력과 (a) 영향

[열린 입력표](FIRST_BATCH_OPEN_INPUTS.md)의 기존 13행을 분모로 유지한다. 제공자 영구

확인한 것은 아니다. 이번 변경으로 새로 완결된 기존 실입력 행은 **0개**다.
기존 확인 2행(provider 잠정 선택/공개 API 규격)과 미완결 11행은 구분해 유지한다.

같은 완료 건수로 세지 않는다. 추가로 사용자 한도·권한자/대체자, 대사 필수 원천·
누락 판정, 시간원/운영 유예·origin_unknown 처리 수용, 후기 손실 책임/재원·허용조치,
내구 승인 및 후기수신의 실행 검증이 남는다. 외부 보증이 없어 무한 대기하는 문제를
내부 자료 누락을 덮어쓰는 문제로 대체하지 않는다. 현재는 실제 사건 종결/자동승인 모두 미실행이다.

(a) 종전 **추정 16~26인일**은 제한된 모델1 로컬 통합이며 문서·계약 중복을 단순
합산하지 않는 기준이었다. 동일한 제한 범위에서 승인기록/규칙 참조/잔여위험의

실측이나 착수 견적 확정이 아니다. 이번 계약 문서 작성 노력은 다시 더하지 않는다.
