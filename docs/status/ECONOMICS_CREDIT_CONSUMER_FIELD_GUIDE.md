## Histories and consumer example

Each scenario uses a fresh session, separate order/group/advance IDs, public
capture confirmation and settlement. Both advances (`6000` and `4000`) are
offered the literal original `claim`, approved, bound, then drawn. The first
successful draw freezes the face; offer alone does not. Both advance views
used for aggregation are captured after both draws, at the same observation
point. The injected `_CapturedSettlementReader` exists only in the test module:
it holds detached public settlement envelopes captured before credit operations
and returns detached copies with identical content. It never accesses
`session._settlement`, changes provenance, derives a face, or mutates settlement.

| ID | Explicit history after draws | Distinction |
| --- | --- | --- |
| `P_partial_requester` | Refund only `line-1` (`6000`); distribute `['organizer-1', 'platform']`; observe mock acceptance `6000` | `REQUESTER`; payee faces unchanged; distribution applies `9700/300`; no recovery |
| `F_full_before_distribution` | Refund both lines once (`10000`, `CASH_REFUND_FIXTURE`); attempt distribution; observe mock acceptance `10000` | `FIXTURE_FULL_GROSS_RECLASS`; unpaid obligations cancelled `9700/300`; economics distribution refuses `GROUP_NOT_SETTLED` |
| `FD_full_after_distribution` | Distribute `9700/300`; refund both lines once with same full-refund route; observe mock acceptance `10000` | Distributions retained; recovery due `9700/300`; no unpaid cancellation |

No full history is constructed by summing successive partial refunds. A full
refund prepares/sends the existing mock REFUND intent; it is not a completed

## Exact field paths

For a live **in-memory reference session** only,
`G = session.view(order_id)['orders'][order_id]['groups'][group_id]`,
`S = G['settlement']`, `F = S['claim']`.
In vectors, each checkpoint is
`scenarios[i].steps[j].result.ok` where `step_id` is `frozen`, `after_refund`,
`after_distribute` or `after_accept`; its `group` is G, `credit.claim` is C and
`credit.views[k]` is A[k]. Ordinary operation results are complete `{ok: ...}`;
the F distribution error is `{error: {type, code}}`. `capture_confirm` records
the existing helper's complete return (capture submission); the helper also
confirms it through the public API before settlement. No private state is exported.

## Independently stated arithmetic

Original unpaid face is `9700 + 300 = 10000`. Credit reservations are
`6000 + 4000 = 10000`; exposure outstanding is drawn `10000` minus repaid `0`.
Every shared observation has **two advances, one claim**, open/reserved `10000`
and residual `0`. Summing claim capacity per advance would incorrectly double
it. The shared limit is explicitly synthetic `10000`, so `within_limit` is true
at equality and still authorizes nothing.

| Checkpoint | Settlement outstanding sum | Variance (`sum - 10000`) | Recovery delta | Refund face / accepted / adjustment |
| --- | ---: | ---: | ---: | --- |
| All `frozen` | 10000 | 0 | 0 | 0 / 0 / 0 |
| P `after_refund` | 10000 | 0 | 0 | 6000 / 0 / 0 |
| P `after_distribute` | 0 | -10000 | 0 | 6000 / 0 / 0 |
| P `after_accept` | 0 | -10000 | 0 | 6000 / 6000 / 6000 |
| F `after_refund`, `after_distribute` | 0 | -10000 | 0 | 10000 / 0 / 0 |
| F `after_accept` | 0 | -10000 | 0 | 10000 / 10000 / 10000 |
| FD `after_distribute` | 0 | -10000 | 0 | 0 / 0 / 0 |
| FD `after_refund` | 0 | -10000 | 10000 | 10000 / 0 / 0 |
| FD `after_accept` | 0 | -10000 | 10000 | 10000 / 10000 / 10000 |

Cash delta is `10000 - 10000 = 0` at every checkpoint. Recovery delta is
`F.recovery_due - C.recovery_due_on_face`; neither companion enters variance or
the tolerance gate. Tolerance `0` means only zero variance is within tolerance.
Acceptance changes only `refund_accepted`, `refund_outstanding` and
`pg_adjustment_outstanding` on F; it does not repay credit, release reservations,
revalue the frozen face, clear recovery or move bank money.
