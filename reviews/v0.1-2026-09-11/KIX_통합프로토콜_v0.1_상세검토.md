# KIX 통합 프로토콜 v0.1 상세 검토

검토일: 2026-09-11. 대상: 사용자 첨부 명세와 `KIX_프로토콜_통합검증_v0.1(1).zip`.

이 문서는 수정 권고와 재현 근거다. 원본 구현을 수정한 v0.2 출시본이 아니다. 실제 PG 요청·체인 거래·은행 송금·외부 발송은 수행하지 않았다. 특허 선행기술 전수조사와 한국법 전체 재검토도 이번 작업 범위에 포함하지 않았다.

## 1. 판단

**v0.1은 유지할 가치가 있는 통합 기준 모형이다. 다만 이 상태에서 Sui 어댑터를 먼저 붙이면, 합성 금융 가정과 빠진 티켓 생애주기까지 체인 구현의 기준으로 굳어질 수 있다.** 다음 작업은 기준 모형의 핵심 수정과, 권리 정본을 별도 프로그램으로 분리하는 일을 연결하는 것이다.

KIX의 목표는 예매·공식 리셀·발권·정산·금융 자료·마케팅이 같은 권리를 일관되게 다루는 것이다. 블록체인과 ZK의 연구 목표도 유지한다. 이를 실제로 확인하려면 **운영자가 바뀌어도 검증·복구 가능한 권리와, 각 참여자가 필요한 사실만 확인하는 증명 경계**를 코드와 시험으로 보여줘야 한다.

| 구분 | 이번 판단 |
|---|---|
| 유지 | 권리 버전·잠금, 결제와 현금 분리, 배분과 회수채권 보존, 내구 영수증, 명시적 동의, 합성 범위 표시 |
| 즉시 수정 | 취소 후 미송신 지급의 송신 허용, 환불 계획 대기 중 노출액 표시, PG 식별자 규격 대응 |
| 일반 규칙에서 분리 | 전 거래 전액 환원, 거래별 현금 출금으로만 환불, 실제 수수료 0원, 공연 완료 후 모든 수취인 지급 |
| 추가 | 재고와 발행 권리의 분리, 반환 좌석 재발행, 무상 양도·초대권, 게시와 거래 잠금 분리, 외부 관찰 inbox |
| 블록체인 고도화 | 실제 권리 프로그램, 범위별 권한, 확정 영수증, 취소와 늦은 전이 경합, 운영자 장애 시 복구 |
| ZK 고도화 | 공개·비공개 입력, 증명 명제, 상태 갱신·중복 소비, 자료 복구와 선택적 공개를 구체화 |
| 검증 보강 | 현재 방어를 제거하면 검사가 실패하는지, 분리된 시스템에서도 같은 불변조건을 지키는지 확인 |

## 2. 무엇을 직접 확인했는가

명세 전체, `core.py`, `adapters.py`, `test_core.py`, `verify.py`, 두 vendor 모형, 계약·출처·결과 메타데이터를 읽었다. ZIP을 별도 작업 경로에 풀고 원본과 실행 사본을 분리했다.

| 확인 | 결과 | 의미와 범위 |
|---|---|---|
| 배포 manifest의 파일 해시 | 14/14 일치 | 해당 ZIP의 내부 일관성 확인. 과거 원본 자산과의 동일성까지 이번에 재검증한 것은 아님 |
| 별도 첨부 명세와 ZIP 안 명세 | 바이트 일치 | 두 문서의 내용 차이 없음 |
| 원본 `verify.py` 재실행 | 31/31 통과 | 제공된 합성 시나리오 재현 |
| `verification.json`·`synthetic_lifecycle_trace.json` | 배포본과 각각 바이트 일치 | 두 주요 JSON의 재현 확인. 실행 시간 문자열이 있는 로그 전체의 동일성을 주장하지 않음 |
| 추가 경계 사례 | 10개 현재 동작 재현 | 기존 `Harness`를 가져오지 않고 작성한 호출 코드로 원본 `Core`를 시험. 전체 프로토콜의 독립 재구현은 아님 |
| 단일 변이 | 10개 중 5개 탐지, 5개 생존 | 목적을 정해 고른 작은 표본. 전체 안전성이나 테스트 신뢰도의 50% 점수가 아님 |
| 생존 변이 확인 | 5개 모두 원본은 거절·변이는 허용하는 별도 입력 확인 | 효과 없는 동치 변이가 아니라 검사 공백임을 확인 |

환경: Python 3.12.14, SQLite 3.53.1, cryptography 46.0.0. 원본 재실행 환경과 동일하다.

## 3. 먼저 고칠 동작: 취소 후 미송신 지급

근거: `core.py`의 `_prepare_effect`(312행), `_send_effect`(340행), `reverse`(233행), `view`(414행). 재현 C01.

다음 순서가 현재 허용된다.

1. 10만 원 티켓을 발행하고 합성 입금을 반영한다.
2. 행사를 완료 처리한다.
3. 주최자 배분금 95,000원의 지급 의도만 준비한다. 아직 `sent=False`다.
4. 행사를 취소한다.
5. 앞서 준비한 지급에 `send_effect`를 호출한다.

5번이 성공해 `sent=True`, `OUTCOME_UNKNOWN`으로 바뀌고 95,000원 요청 자료를 반환했다. 실제 송금은 하지 않았지만 **송신 허가 상태가 취소 뒤에 새로 생긴 것**이다. `_prepare_effect`는 행사·환원 상태를 검사하지만 `_send_effect`는 DONE·ABORTED 여부만 검사한다.

수정할 내용:

- 최초 송신 의도를 확정하는 같은 트랜잭션에서 현재 지급 허용 조건, 행사 취소, 환원 요청, 배분 버전을 다시 검사한다.
- 아직 송신 의도가 없는 지급은 취소 후 새로 송신하지 않는다. 예약을 정리하고 환원 계산을 진행한다.
- 이미 송신 의도를 기록한 지급은 외부 호출 여부가 불명확할 수 있다. 이 경우 결과 조회·실제 이동 대사·송신 종료 근거를 다루는 별도 절차로 보낸다.
- 멱등키는 중복 실행 방지에 관한 조건이다. 취소된 지급을 처음 실행해도 되는지까지 판단하지 않는다.
- 작업자 세대 번호를 추가하더라도, 외부 PG가 그 번호를 검사하지 않으면 이미 나간 요청을 취소하는 효과는 없다. 이 한계를 프로토콜 계약에 적는다.

현재 명세가 수동 `abort_effect` 경로를 설명한 것은 맞다. 그러나 정상 작업자의 늦은 송신을 코드 자체가 차단하도록 하는 것이 더 안전한 실행 기준이다.

같은 재현에서 금융 조회는 다음을 반환했다.

| 항목 | 값 |
|---|---:|
| `refundOutstanding` | 0원 |
| `refundPlansPending` | 1건 |
| `organizerPayable` | 95,000원 |

계획 대기 건수를 표시하므로 문서가 이 상태를 숨겼다고 볼 수는 없다. 다만 돈을 판단하는 소비자에게 0원과 1건만 주면 노출액을 계산할 수 없다. **환불 의무 발생, 회계 분류 확정, 자금 조달, 실제 이행을 따로 기록해야 한다.** 현재 전액 환원 정책에서는 대기 거래의 환불 대상 총액이 이미 100,000원이다. `refundLiabilityRecognized`, `refundLiabilityUnclassified`, `payoutAtRisk`, `refundFundingGap` 등의 금액과 증거 기준을 정의한다. 미확정 값을 0으로 대체하지 않는다.

## 4. 금융 모형의 가장 큰 수정: 원결제 취소와 현금 송금을 분리

근거: `_prepare_effect`(312행), `_settle_capture`(203행), `_observe_effect`(364행), 명세 6·7절. 재현 C02·C03.

현재 `REFUND`와 `PAYOUT`은 모두 거래별 `funds` 잔액을 예약하고, 실제 출금 증거가 와야 완료된다. **현금을 직접 내보내는 합성 프로필로서는 일관되지만, 원화 PG 취소의 공통 모형으로 삼기에는 좁다.**

카드 승인 100,000원, 정산 입금 0원, 행사 취소 상태를 만들면 환불 준비가 `INSUFFICIENT_CONFIRMED_FUNDS`로 막힌다. 토스 공식 문서는 매입 전·후의 취소 처리와, 이미 정산받은 결제의 후속 정산 차감을 구분해 설명한다. 따라서 KIX 계좌 입출금이 반드시 생기는 경로만 표현하면 원결제 취소와 맞지 않는 경우가 생긴다. 실제 허용 방식은 KIX의 가맹점 계약과 결제수단별로 연결해야 한다. [토스 결제 취소 안내 — 결제 취소 기한·이미 정산 받은 결제](https://docs.tosspayments.com/guides/v2/cancel-payment)

다음은 새 설계의 **제안 프로필**이며, 실제 계약 권한을 확보했다는 뜻은 아니다.

| 프로필 | 실행 권한의 근거 | 자금·채무에 생길 수 있는 결과 |
|---|---|---|
| 원결제 승인 취소 | 원결제 참조, 취소 가능 잔액, 취소 권한, 현재 결과 | PG 수취채권 및 구매자 관련 의무 감소. KIX 은행 출금이 없을 수 있음 |
| 정산 이후 원결제 취소 | 원결제 취소 결과와 해당 계약의 회수·차감 방식 | PG에 지급할 의무, 계약상 후속 정산 조정 등을 별도 기록 |
| 지정 계좌로 환불 송금 | 해당 환불 경로의 허용 근거, 수취 계좌, 확인 자금·승인 재원 | 실제 외부 출금 및 수취 결과 |
| 수취인 배분금 지급 | 배분 의무, 지급 가능 시점, 확인 자금 | 판매자·주최자·공연자 등의 배분 의무 이행 |
| 온체인 자금 지급 | 지정 자산·금액·수취인·허용된 실행 규칙 | 해당 체인의 자산 이전 결과. 원화 PG 취소 결과를 대신하지 않음 |

프로필별로 `PG_CANCELLED`, `CUSTOMER_CREDIT_CONFIRMED`, `MERCHANT_SETTLEMENT_ADJUSTED`, `BANK_DEBIT_OBSERVED`를 필요한 범위에서 구분한다. PG의 취소 확인을 곧바로 고객 카드 명세 반영이나 KIX 현금 출금으로 바꾸지 않는다. 반대로 KIX 현금 출금이 없다는 이유만으로 확인된 원결제 취소를 영원히 미완료로 남기지도 않는다.

이것은 예전에 논의했던 ‘원결제 경로 보존’을 실제 실행 계약으로 만드는 지점이다. `ExecutionEffect`에 `routeProfile`, `originalPaymentRef`, `providerOperationId`, `contractRef`, `fundingBasis`, `requiredEvidence`를 명시한다. 허용된 경로를 보존하면서 이행 증거의 종류를 구분한다. 임의의 다른 가맹점 자금을 섞거나 원결제 취소를 임의 계좌이체로 바꾸는 기능은 이 수정의 의미가 아니다.

### 수수료를 0원으로 두는 가정도 프로필로 격리

100,000원 승인 뒤 97,000원만 실제 입금된 입력을 넣었다. 현재 코어는 3,000원을 PG 미수채권으로 남긴다. 주최자 95,000원을 지급하면 자금은 2,000원이고 플랫폼 배분 의무는 여전히 5,000원이어서 나머지 지급이 막힌다. 입력에 수수료 구분이 없으므로 코어가 그 차액을 스스로 수수료라고 추정해서는 안 된다. **필요한 수정은 차액을 무시하는 것이 아니라 수수료·세금·보류·조정 자료를 받는 것이다.**

토스 Settlement 객체는 결제 금액·수수료·지급 금액을 별도로 제공한다. [토스 코어 API — Settlement 객체의 fee·payOutAmount](https://docs.tosspayments.com/reference)

새로 정의할 관계는 계약에 따라 다음 항목을 대조하는 것이다: 승인 총액, 취소액, 수수료·세금, 보류·조정액, 확인된 순정산액, 미수·미지급 잔액. 수수료를 주최자·플랫폼·판매자 중 누가 부담하는지도 배분 정책에 넣는다.

## 5. 전 거래 환원은 시험 사례로 유지하고, 환불의 기본값에서는 분리

근거: `_create_event`의 `refundProfile` 제한(140행), `terminate_ticket`(255행), 명세 4·6절. 재현 C05.

현재는 `FULL_CHAIN_UNWIND_FIXTURE`만 허용한다. A가 10만 원에 구매하고 B에게 12만 원에 재판매한 뒤 B가 환불을 신청하면, 최초 거래 A에게 10만 원, 재판매 거래 B에게 12만 원의 환불 의무를 만든다. 지급 후라면 앞서 지급한 배분금을 회수해야 한다.

이는 명세에 표시된 의도적인 정책이며 산술 오류가 아니다. 그러나 **마지막 구매자의 환불이 과거 판매자·주최자·플랫폼 거래를 모두 되돌리는 상품**이 된다. 그런 상품을 채택할지 결정하지 않은 채 공통 엔진의 유일한 환불로 두면, 일반 리셀 플랫폼과 금융 활용에 큰 제약이 생긴다.

| 취소 원인 | 별도로 결정할 내용 |
|---|---|
| 결제됐지만 권리 전이는 실패 | 해당 미이행 거래의 돈을 반환. 이전의 유효한 거래까지 취소하는지 분리 |
| 재판매 계약 자체의 취소 | 되돌릴 권리, 판매자 책임, 구매자 지급액, 이미 지급한 배분금 |
| 현재 관람권자의 일반 환불 | 환불 가능 조건, 지급 상대방, 금액, 권리 소멸, 반환 좌석 처리 |
| 공연 전체 취소 | 영향받는 회차·권리·거래, 각 환불 채무자, 플랫폼·PG 비용 부담 |
| 회차 변경·일부 행사 취소 | 변경 동의, 대체 회차, 부분 권리·부분 환불 |
| 사후 차지백·지급 반환 | 외부 사실에 따른 채권·채무 조정. 이미 사용한 관람권을 미사용으로 복구하지 않음 |

`RefundCase`는 사유·원천 거래·영향받는 권리·정책 버전·금액·채무자·수취인·이행 경로를 가져야 한다. 사용자가 받을 금액과 누가 그 비용을 부담하는지는 다른 질문이다. 소비자 환불을 재판매 성사나 회수 성공에 자동 종속시키지 않는 기존 원칙은 유지한다.

## 6. 반환 좌석 재판매와 리셀 게시를 실제 제품 생애주기로 추가

### 좌석과 발행된 관람권을 나눈다

근거: `_create_event`(148행), `terminate_ticket`(255행), `_prepare_trade`(161행). 재현 C04.

현재 `show/A1`이 좌석 식별자이면서 티켓 권리 식별자다. 정상 환불을 완료해도 상태는 `VOID`이며, 이 좌석을 다시 구매하려 하면 `RIGHT_NOT_TRANSFERABLE`로 거절된다. ‘옛 티켓을 다시 살리지 않는다’는 안전 조건은 지키지만 반환 좌석을 다시 팔 수 없다.

제안 구조:

- `InventoryUnit`: 회차와 좌석 또는 자유석 수량 단위. 판매 가능 여부와 현재 연결된 권리를 관리한다.
- `AdmissionRight`: 이번 발행에서 생긴 관람권. 발행 식별자, 현재 제어자, 버전, 정책, 소비·위임 상태를 관리한다.
- 기존 권리는 영구 폐기한다. 안전한 종료 조건을 확인한 뒤 재고 단위를 다시 열고 **새 발행 식별자**로 판매한다.
- 재고 단위에는 동시에 유효한 발행이 하나만 연결되도록 권리 원장에서도 검사한다. 늦은 발급 요청은 닫힌 거래 ID·발행 세대에서 거절한다.

현장 사용 여부가 불명확한 권리는 좌석으로 돌려 새 구매자에게 재발행하지 않는 원칙을 유지한다.

### 게시글과 구매 진행 중 잠금을 분리한다

현재 `prepare_trade`는 판매자가 지정 구매자에게 제안하는 순간 티켓을 잠근다. 만료·게시 상태는 없으며 구매자의 수락 전에 잠길 수 있다. 현 상태는 공개 리셀 시장의 게시 API보다 ‘특정 상대와 시작한 거래 예약’에 가깝다.

`ResaleListing`은 티켓 버전·판매 조건·가격·정책·유효기간을 가진 제안으로 두고, 구매자가 실제 거래를 시작할 때 `TradeReservation`을 확보하는 안이 적합하다. 게시 상태에서 입장을 허용할지 여부는 정책으로 명시한다. 허용한다면 입장·양도·환불 시 기존 게시를 무효화하고 구매자가 예약할 때 최신 권리를 재검사한다.

예약 기한도 추가하되 HTTP 시간초과와 혼동하지 않는다. 기한 경과 후 잠금을 해제하려면 해당 거래의 늦은 체인 전이 실행 가능성을 닫아야 한다. 이미 송신된 외부 결제 결과는 별도로 대사한다. **기간 제한은 정상 거래가 영구히 잠기는 것을 막고, 종료 증거는 오래된 요청이 부활하는 것을 막는다.**

## 7. 무료 양도·초대권·회차·주문을 보충

재현 C06에서 0원 양도는 `INVALID_AMOUNT`로 거절됐다. 현재 첫 발행은 유료 결제 확인이 필수다. 명세의 범위를 넘는 오류라기보다는 이전에 계획한 제품 기능이 빠진 것이다.

- `GIFT_TRANSFER`: 소유자 승인·수신자 수락·자격·정책·권리 충돌 검사는 유지하고 결제 의무는 만들지 않는다.
- `COMPLIMENTARY_ISSUE`: 승인 물량에서 권한 있는 발행자가 무료 권리를 발급한다. 초대권도 발행 한도와 중복 사용 검사를 받는다.
- 금전 분개의 `positive()`를 일괄적으로 0원 허용으로 바꾸지 않는다. 권리 동작과 금전 의무를 구분한다.
- `Event` 아래 `Performance` 또는 `Session`을 두어 판매 종료·입장 운영·공연 완료·정산 공개를 분리한다. 영화제의 여러 회차와 회차별 변경을 표현할 수 있게 한다.
- `Order`·`OrderLine`·`Payment`를 나누고, 한 결제가 여러 티켓을 살 수 있게 한다. 결제의 소비 금액 합계와 각 주문행 귀속을 검사한다. 현재 한 결제의 중복 재사용 금지 조건을 무조건 풀어서는 안 된다.
- 배지·패스가 회차 예약권을 만드는 기능은 별도 확장으로 둔다. 초기 구현에서 제외하더라도 단일 `ticketId`에 모든 권리를 합치는 구조는 피한다.

플랫폼 수수료 0원의 파일럿과 관객 티켓 가격 0원은 계속 구분한다.

## 8. 거절된 외부 관찰을 잃지 않는 구조가 먼저 필요

근거: `execute`의 롤백(86행), `_capture`(195행), `_observe_effect`(367행), 명세 7·9.4·11절. 재현 C07.

동일 거래에 두 번째 결제 ID의 승인 관찰을 넣으면 `SECOND_PAYMENT_REQUIRES_SEPARATE_REVIEW`로 거절된다. 재현에서 원장과 증거 저장 상태는 호출 전과 완전히 같았다. **두 번째 발권을 막는 것은 맞지만, 실제로 돈이 들어온 사실을 검토 큐에 남기는 기능은 없다.** 명세가 이 한계를 공개한 것은 정확하다. 이제는 어댑터 연결의 선행 구현으로 올려야 한다.

| 저장 단계 | 역할 |
|---|---|
| RawInbox | 수신한 원자료·원천·수신 시각·해시·인증 결과를 접근 통제하에 저장 |
| SourceFact | 원천 거래 ID·취소 ID·입출금 ID·금액·상태·원천 시각을 정규화 |
| Attribution | 의무·실행 시도에 연결하거나 미귀속·상충 상태로 보존 |
| LedgerApplication | 검증된 귀속을 바탕으로 분개·진행 상태 반영 |

`observationId`, `providerOperationId`, `movementId`, `effectId`, `attemptId`는 각각 다른 식별자다. 재조회·웹훅·정산 파일이 같은 외부 사건을 전하는 경우 관찰은 여러 개, 경제적 효과는 하나다. 하나의 원천 이동을 여러 의무에 배분해야 한다면 부모 이동과 배분행을 만들고 배분 합계 상한을 검사한다.

사업 명령과 외부 사실의 처리 원칙도 구분한다. 무재원 지급 **명령**은 거절해야 한다. 반면 실제 출금 **사실**이 내부 예상액을 초과했다면 거절로 지우는 대신 미귀속 금액·대사 차이로 남겨야 한다. 아무나 외부 사실을 주장할 수 있다는 뜻이 아니라, 인증·검토 단계와 경제적 사실의 보존을 구분한다는 뜻이다.

`Obligation → ExecutionAttempt → SourceFact` 관계를 추가하고 다음을 명시한다.

- 확정 실패 전에는 새 실행 키로 같은 의무를 지급하지 않는다.
- 확정 실패·송신 종료를 확인했다면 새로운 시도는 같은 의무를 참조한다. 이전 시도를 덮어쓰지 않는다.
- 실패로 분류한 시도에 늦은 돈이 도착하면 `LATE_MOVEMENT_REVIEW` 같은 명시 상태와 잔액을 남긴다.
- 한 외부 실행의 부분 성공은 별도 부분 실행 ID 여러 개와 다르다. 누계·잔액·최종 여부를 표현한다.
- DONE 후 사후 반환은 과거 DONE을 삭제하지 않고 연결된 반대 방향 사실로 처리한다.
- 멱등 보장 기간·조회 지원·재전송 조건은 PG별 계약에 고정한다. 이번 검토에서는 모든 PG에 공통인 기간을 제시하지 않는다.

## 9. 블록체인 목표는 권리 정본과 운영자 독립성으로 구현

### 현재 재사용 범위

`core.py`는 `vendor/rights_model.py`를 호출하지 않는다. 기존 권리 모형은 `test_existing_private_rights_model_financial_terms_binding`에서 별도로 만든 티켓 노트에 통합 거래의 `termsHash`를 넣어 검사한다. 따라서 다음이 현재의 정확한 표현이다.

> 통합 금융 조건과 기존 권리 모형의 수신 확인이 결합되는 별도 계약 검사를 수행했다. 같은 티켓이 두 시스템 사이에서 실제 이전되는 실행 연결은 아직 없다.

기존 권리 모형의 암호화·서명 라이브러리 사용은 보존할 수 있다. 다만 그 모형은 공개된 합성 seed로 키를 만들고, 검증기에 평문 witness를 전달하며, 원장의 원자적 실행과 진실한 최종 상태를 가정한다. 이를 운영용 보안 모듈로 옮기지는 않는다.

### 공통 권리 프로그램이 결정할 사항

제안 모듈은 `IssuerAuthority`, `InventoryUnit`, `AdmissionRight`, `TradeIntent`, `AdmissionGrant`, `PolicyVersion`, `PaymentAttestationRegistry`, `OperationReceipt`다. 실제 Move 객체 개수·소유 형식은 접근 방식에 맞춰 정하며 이름만으로 안전성을 주장하지 않는다.

| 결정 | 반드시 명시할 내용 |
|---|---|
| 발행 | 어느 주최자가 어느 회차의 몇 장을 누구에게 위임했는가 |
| 양도·리셀 | 현재 권리 제어, 수신자 수락, 정책, 거래 잠금, 결제 근거를 누가 검증하는가 |
| 소비·위임 | 같은 티켓의 입장·양도·환불을 공통 상태에서 충돌 없이 처리하는가 |
| 결제 증거 | 실제 PG 자료를 조회한 어댑터의 서명인지, PG 자체 서명인지 구분하는가 |
| 취소 | 행사·거래 취소와 늦은 전이 중 무엇이 먼저 확정됐는가 |
| 업그레이드·복구 | 누가 어떤 범위의 권리를 바꿀 수 있고, 기존 보유자가 무엇을 검증할 수 있는가 |
| 운영자 장애 | 지갑·권리 자료·검증기·RPC·수수료 지원 중 무엇이 KIX 밖에서도 사용 가능한가 |

현재의 `operator`, `venue`, `finance-adapter`는 전역 합성 역할이다. 운영 구현에서는 사람 또는 기관의 신원, 역할, 행사 범위, 허용 행위, 권한 버전과 회수 조건을 분리한다. 예를 들어 한 공연장 검표자가 다른 공연의 입장을 승인할 수 없어야 한다. 공동의 공유 객체를 전달받는 것만으로 권한이 생기지 않도록 Move의 명시적 검사를 둔다. [Sui 객체 소유·접근 제어 안내](https://docs.sui.io/develop/objects/object-ownership)

직접 지갑 전송으로 정책을 우회할 수 있는지도 검사한다. Sui는 객체의 능력에 따라 `transfer`와 `public_transfer` 접근이 달라진다. 일반 전송 가능한 NFT를 만들고 KIX API에서만 리셀 정책을 검사하면 정책 적용 경로가 불완전해진다. [Sui Address-Owned Objects — Create address-owned objects](https://docs.sui.io/develop/objects/object-ownership/address-owned)

### SQLite의 원자성을 외부 시스템으로 확대하지 않는다

현재 `commit_trade`는 권리·배분 기록을 한 트랜잭션에서 갱신한다. 실제 연결에는 다음 상태가 필요하다.

| 사건 | 보존해야 할 상태·다음 처리 |
|---|---|
| 체인 제출 전 장애 | 서명된 요청과 거래 의도가 저장됐는지 확인 |
| 제출 후 응답 유실 | digest로 결과 조회. 조회 누락을 실패로 확정하지 않음 |
| 체인 전이는 성공, KIX DB 반영은 실패 | 확정 영수증으로 조회 원장·배분 기록을 멱등 재구성 |
| PG는 승인, 권리 전이는 미확정 | 사용자에게 이전 완료로 표시하지 않음. 새 환불·원권리 복구와 충돌 방지 |
| 취소와 권리 전이가 경합 | 원장에 닫힌 거래·취소 버전을 검사해 늦은 실행 차단 |
| 외부 결제 사후 반환 | 이미 사용한 권리는 되살리지 않고 금전 채권·채무로 처리 |

Sui 공식 문서는 서명된 거래의 저장·재제출, digest 조회, 조회 결과가 없을 때의 불확실성, ‘확정됐으나 실행은 실패한 거래’의 구분을 설명한다. 어댑터는 최종성 존재와 성공 여부를 따로 검사해야 한다. [Sui 거래 생애주기 — Transaction idempotence and finality verification](https://docs.sui.io/develop/transactions/transaction-lifecycle)

체인을 쓰는 이유를 증명하는 첫 시험은 **KIX 조정 서비스를 중지한 상태에서, 이미 정상 발행·전이된 권리를 다른 검증자가 확인하고 보유자가 복구할 수 있는가**로 잡는다. 그 시험도 PG·신원 서비스·현장 운영까지 모두 무정지임을 뜻하지 않는다. 필요한 외부 의존성을 조건으로 명시한다.

## 10. ZK는 ‘무엇을 누구에게 숨기는가’에서 출발

현재 `view`에서 이름을 빼거나 참조값을 해시하는 것은 ZK가 아니다. `zkLogin`도 로그인 정보를 보호하는 구조이며 그 사실만으로 티켓 거래·금액·지갑 사이 연결까지 비공개가 되지는 않는다. 공식 문서는 공개되는 로그인 관련 값, 비공개 입력, 증명·salt 서비스가 알 수 있는 정보를 구분한다. [Sui zkLogin Technical Reference — Privacy](https://docs.sui.io/sui-stack/zklogin-integration/zklogin)

우리가 원한 익명성과 검증 가능성은 다음처럼 **검증 명제와 공개 범위**로 바꿔야 한다. 아래는 설계 제안이며 신규성·진보성 확인 결과가 아니다.

| 검증자 | 확인할 사실 | 기본적으로 받지 않을 자료 | 필요한 연결 |
|---|---|---|---|
| 구매자 | 정당한 권리이며 수락한 정책대로 이전됨 | 판매자의 다른 관람·거래 이력 | 입력 권리, 정책 commitment, 거래 조건, 출력 권리 |
| 검표자 | 이 회차의 사용 가능한 권리를 제어하며 아직 소비하지 않음 | 전체 결제·이전 사슬, 불필요한 실명 | 현재 상태, 행사·위임 범위, 제시 challenge, 소비 표식 |
| 배분 검증자 | 약정한 배분 산식과 금액 보존 조건 충족 | 필요 없는 구매자 신원·다른 행사 내역 | 거래 금액·배분 commitment, 산식 버전, 결제 근거 |
| 금융 자료 수신자 | 허용된 기간·행사의 확정 매출·취소·배분·부담을 일관되게 계산 | 개별 관객 연락처·전체 지갑 이력 | 원천 집합, 포함 범위, 기준 시점, 집계 증명 |
| 정당한 자료 요청 처리자 | 요청 범위의 거래와 당사자 정보를 확인 가능 | 요청 밖의 자료 | 별도 보호 저장소, 접근 근거, 범위 제한 공개, 접근 이력 |

첫 증명 명세에는 공개 입력, 비공개 witness, 검증할 식, 사용 표식의 생성 규칙, 허용된 상태 root, 오래된 증거의 거절 조건을 넣는다. 옛 상태의 포함 증명이 참이라는 것과 지금도 미사용이라는 것은 다르므로, 최신 소비 집합·현재 권리 검사를 결합해야 한다.

특히 기존 노트 모형의 ‘양도·입장·환불을 공통 소비 표식으로 연결’하는 조건을 유지한다. 동작 종류마다 별개의 표식을 써 같은 권리가 두 경로에서 소비되는 우회를 허용하면 안 된다. 수신 확인에는 수락한 조건과 출력 암호문을 결합하되, 서명 하나가 디스크 보존을 증명한다고 설명하지 않는다.

### 공개 티켓 객체와 비공개 노트는 별도 프로필

- 공개 프로필은 소유·거래 연결이 노출되는 범위를 정확히 표시하고 공통 전이 규칙을 먼저 검증할 수 있다.
- 비공개 프로필은 commitment·nullifier·암호화된 권리 복구 자료·실제 증명 검증기를 사용한다. 공개 객체에 있던 신원·연결 가능한 참조를 그대로 올린 뒤 증명만 추가해서는 목표를 달성할 수 없다.
- 두 프로필은 같은 검증 결과와 입출력 의미를 공유할 수 있지만, 동일한 저장 필드와 전이 비용을 가진다고 가정하지 않는다.
- 증명자가 거래 결과를 조작하지 못하도록 원천 서명·허용된 어댑터·자료 집합을 고정한다. ZK가 잘못 입력된 PG 사실을 진실로 바꾸지는 않는다.
- 복구용 암호문과 공개 검증 근거를 KIX 단일 저장소에만 두면 운영자 장애 때 사용할 수 없다. 자료 가용성·복구 키·독립 검증 경로를 함께 시험한다.

자료 제출이나 계약상 확인을 지원하는 공개 기능은 프로토콜의 범위 제한 인터페이스로 둔다. 현재 한국 법령의 세부 제출 범위·보존기간은 별도 정책 근거로 관리한다. 이번 웹 확인으로 해당 시행령 전문을 확보하지 못했으므로 이 보고서가 새 법정 보관 목록을 확정하지 않는다. 공연·스포츠·영화제 유형을 하나의 법 적용으로 합치지 않는다.

## 11. 리셀 가치 재분배를 고정 비율에서 정책 모듈로

현재 리셀은 판매자 95%, 주최자 2%, 플랫폼 3%다. 이는 산술 검증용으로 적합하다. 하지만 우리가 논의한 ‘가격 발견의 이익 일부를 창작·운영 주체에 돌리는 구조’의 선택지는 아직 좁다.

| 정책 요소 | 결정할 질문 |
|---|---|
| 수취인 | 주최자·공연자·기획사·공연장·플랫폼의 어떤 주체가 계약상 받을 권리가 있는가 |
| 배분 기준 | 리셀 총액, 원금 초과분, 비용 공제 후 금액 중 무엇인가 |
| 원금 기준 | 최초 정가, 판매자의 실제 취득가, 다른 합의 기준 중 무엇인가 |
| 하한·상한 | 손해 보고 재판매할 때 배분이 음수가 되지 않는가, 상한·최소 수취액은 무엇인가 |
| 원 단위 잔여 | 절사·반올림·잔여액 귀속을 모든 구현이 동일하게 계산하는가 |
| 취소·차지백 | 어떤 수취인이 어느 범위에서 환원·회수 책임을 지는가 |
| 지급 시점 | 판매자 대금과 로열티를 같은 시점에 지급할 것인가 |

예를 들어 10만 원 취득권을 12만 원에 팔 때 ‘총액 12만 원의 일정 비율’과 ‘차익 2만 원의 일정 비율’은 다른 상품이다. 계산식과 원금 기준을 계약·명세·테스트에서 일치시켜야 한다. 최종 비율을 이번 검토에서 확정하지 않는다.

**이전 구매자라는 이유만으로 후속 리셀 이익을 계속 받는 구조는 추가하지 않는다.** 현재 판매자가 자기 권리를 팔아 받는 대금은 그와 다르다. 토큰 보상·채굴 보상도 이 배분 의무에 임의로 섞지 않는다.

현재 ‘행사 완료 후 모든 배분금 지급’ 정책은 일반 관객 판매자에게도 적용된다. 이는 손실 방지에 유리한 합성 조건이지만 리셀 완료 뒤 대금을 받기까지 기다려야 하는 상품이 된다. 판매자 대금 지급 조건과 행사 수익·로열티 지급 조건을 독립적으로 버전 관리하되, 조기 지급 시 취소 부담·회수 재원도 함께 모델링한다.

## 12. 금융·마케팅은 공통 증거를 쓰되 서로의 권한을 공유하지 않는다

### 금융 자료

현재 `primaryCaptured`·`resaleCaptured`·주최자 배분을 구분한 것은 유지한다. 이 수치는 이름 그대로의 누적 승인·배분 통계다. 대출 가능한 매출액이나 현재 남아 있는 정상 관람권 판매액으로 바꾸어 해석해서는 안 된다.

추가할 항목:

- 승인됐지만 미발행·중단된 거래, 확정된 권리 전이, 취소·환불, 순판매를 각각 분리.
- 미분류 환불 대상 금액, 결과 미확정 지급액, 사후 반환, 미회수금, 실제 자금 부족액.
- `asOf`, 원천 자료 cursor·누락 여부, 체인 확정 참조, 정책·계산기 버전, 상충·검토 상태.
- 주최자 배분권과 금융 제휴사가 보유한 계약상 권리를 별도 참조. 티켓 소유권만으로 정산채권·담보권이 생기는 구조를 사용하지 않음.
- 금융기관이 신뢰한 자료 범위가 완전한지 표시. 데이터 몇 건의 올바름과 전체 모집단에서 누락이 없다는 주장은 별개.

대출 원금·회수·담보권 실행은 현재 금융 조회와 다른 모듈이다. 첫 연결은 금융기관이 검증할 수 있는 자료와 그 버전으로 진행하되, 향후 금융 권리의 ID·계약·실행 주체를 붙일 자리는 남긴다.

### 마케팅

근거: `_set_consent`(397행), `view`(426행). 재현 C08.

같은 `operationId`의 중복 동의 요청은 기존 멱등성으로 막힌다. 그러나 별개의 명령 ID로 늦게 도착한 예전 동의와, 철회 후 사용자가 새로 선택한 동의를 구분하는 전제는 없다. 재현에서 동의→철회→새 ID의 동의는 version 3으로 허용됐다. 마지막 동의가 실제로 새 의사라면 올바른 동작이다. **문제는 현재 계약에 그 차이를 확인할 정보가 없다는 것**이다.

동의 갱신에 `expectedConsentVersion` 또는 서버가 확인하는 갱신 근거를 결합하고, 거절된 오래된 동의를 최신 버전으로 자동 재승인하지 않는다. 동의 대상 사업자·목적·연락 채널·이용 범위·시각·철회 근거도 기록한다. 캠페인 추출본이 아니라 실제 발송 허가 직전 상태를 확인하고, 이미 발송 허가된 작업과 철회의 순서도 정의한다.

현재 `attended`는 권리의 `used`로 계산한다. 이것을 실제 공연 관람의 확정 증거로 표현하지 말고 ‘검표 승인/권리 사용 기록’과 ‘실제 관람 확인’을 구분한다. 공개 원장에 연락처·동의 이력을 그대로 기록하지 않는다.

## 13. 실제 PG·발권사 연동 계약의 작은 불일치도 수정

재현 C09·C10. `ident()`는 내부·외부 식별자를 모두 최대 100자로 제한하고, `externalOrderId`는 `tradeId`를 그대로 반환한다. 그래서 `주문 1`을 외부 주문 ID로 내보낼 수 있는 반면 150자의 결제 ID는 거절한다.

토스 문서는 `orderId`에 영문·숫자·`-`·`_`의 6~64자, `paymentKey`에 최대 200자를 정의한다. [토스 코어 API — Payment 객체의 orderId·paymentKey](https://docs.tosspayments.com/reference)

따라서 내부 ID와 provider ID의 검증 함수를 분리하고, provider에 맞는 주문 ID를 생성해 원거래와 불변 매핑한다. 문자열을 잘라서 맞추면 충돌이 생길 수 있으므로 자르지 않는다.

추가 계약 수정:

- `protocol_contract.json`은 현재 필수 필드 목록이지 완전한 실행 검증 schema가 아니다. 형식·상한·enum·조건부 필드·오류 코드를 명시하고 실제 요청 검증에 사용한다.
- `close_delegation.provenance`는 계약 파일에서 선택 필드인데 현재 함수에서는 특정 값이 필수다. 합성 계약부터 일치시킨다.
- 외부 서명에 사용할 결정적 직렬화, 해시 입력 버전·도메인, 알 수 없는 필드 처리, nonce·만료·서명자 범위를 고정한다.
- 반환한 ‘내 거래’ 데이터는 해당 사용자가 구매자·판매자 중 어떤 지위인지 표시한다. 현재 판매자에게 보여주는 재판매 거래의 환불 금액은 새 구매자에게 줄 돈일 수 있다.
- 기존 예매처와는 `(issuerNamespace, externalEventId, externalTicketId)` 매핑 외에 구권리 종료 영수증·신권리 승인·재시도·결과 미확정 상태가 필요하다.
- API 규격을 만든 사실과 인터파크·YES24 등의 실제 연동 권한을 확보한 사실은 계속 구분한다.

| 상호운용 | 서로 다른 발권/검표 구현이 같은 권리·영수증을 해석. 구권리와 신권리 동시 유효 없음 |
| 자료 품질 | 미귀속·상충·누락 자료를 보존하고 금융 수치의 증거 범위·부족액에 표시 |

별도 경계 검사는 ‘현재 결함/제약이 재현된다’는 검사다. 이를 수정 후의 성공 검사로 계속 통과시키면 안 된다. 수정판에서는 기대 동작을 바꾸고 원본에서 실패·수정본에서 통과하는 회귀 검사로 전환한다.

31개의 개수를 늘리는 것보다, 현재 핵심 방어의 삭제를 잡고 분리된 권리·금전 원천의 경합을 확인하는 것이 중요하다. SQLite 연결 두 개의 직렬화 성공은 실제 체인·PG·현장 시스템 사이의 경합 시험을 대체하지 않는다.

## 15. 일반 구현에서 분리하거나 당장 추가하지 않을 것

| 항목 | 처리 |
|---|---|
| `FULL_CHAIN_UNWIND_FIXTURE` | 역사·회수 계산 회귀 사례로 유지. 모든 상품의 유일한 정책에서는 분리 |
| 수수료 0원·전액 현금 입출금 | 명시적 테스트 프로필로 유지. 실제 PG 연결의 기본 원장으로 사용하지 않음 |
| 모든 금전 지급을 행사 완료 뒤에만 실행 | 수취인·계약별 지급 조건으로 분리 |
| 고정 300석·KRW·Toss test scope | 시험 설정으로 이동. 체인 독립 프로토콜의 보편 제한으로 고정하지 않음 |
| 한 JSON 상태 행·전역 쓰기 잠금 | 작은 기준 모형에는 유지 가능. 실제 저장 구조로 복제하지 않음 |
| `check()`의 전체 분개 재계산 | 독립 검증/복구 도구로 활용. 전체 이력을 매 요청 재검사하는 운영 경로와 분리 |
| 마케팅 명단을 원장에 저장 | 권리 원장에는 필요한 증거만. 연락처·동의·대상 추출은 별도 권한 저장소 |
| 자체 L1·다중 체인 동시 권리 정본·토큰 보상 | 현재 권리·거래 문제를 해결하는 전제에 넣지 않음 |
| 체인 TPS를 예매 완료 속도로 표기 | 사용하지 않음. 접수·좌석 확보·결제·권리 확정 지연을 별도 측정 |
| 테스트 통과를 특허 진보성으로 사용 | 사용하지 않음. 실제 차이·효과·대조 문헌과 발명 기여는 별도 기록 |

각 요청이 전체 상태 JSON을 읽고, 전체 분개를 재계산하고, 다시 전체 상태를 저장하는 구조라는 점은 코드에서 확인된다. 지금 규모의 기준 모형으로 유지할 수 있지만 다수 행사 운영용 저장 방식은 별도 행·키·인덱스·제약과 도메인별 트랜잭션으로 바꿔야 한다. 같은 전체 상태를 하나의 체인 공유 객체로 옮기지 않는다. 이 보고서에서는 새로운 처리량 수치를 측정하지 않았다.

## 16. 권고하는 다음 구현 순서와 완료 기준

현재 명세 12절의 ‘Sui 어댑터부터’라는 문구를 다음 순서로 바꾸는 것을 권한다. 이 순서는 블록체인 연구를 중단하거나 일반 SaaS만 만들자는 전환이 아니다. **권리 프로그램에 넣을 규칙을 바로잡으면서 실제 분산 검증으로 전진하는 순서**다.

| 단위 | 산출물 | 완료 기준 |
|---|---|---|
| 1. 통합 기준 수정 | 취소 송신 검사, 환불 경로 프로필, 명시적인 환불 노출액, 회귀 검사 | C01 수정과 생존 변이 5종 탐지. 알려진 기존 정상 흐름 보존 |
| 2. 제품 권리 확장 | 재고/권리 분리, 재발행, 무상 양도, 초대권, 게시/예약 분리 | 기존 권리의 부활 없이 반환 좌석 재판매. 거래 수락·잠금·기간 명세 일치 |
| 3. 원천 연결 계약 | RawInbox, 시도별 Outbox, provider ID 매핑, 수수료·순정산 | 거절 사실 보존. 중복 관찰이 의무·자금을 늘리지 않음. 프로필별 완료 증거 구분 |
| 4. 실제 권리 프로그램 | 범위별 발권/검표 권한, 티켓·거래 상태, 확정 영수증 | 같은 의미의 입력에 기준 모형과 같은 허용/거절. 응답 유실·취소 경합 검증 |
| 5. 독립 검증·복구 | 독립 클라이언트, 원천 검증, 복구 자료와 가용성 실험 | KIX 조정 서비스 중지 중 정해진 범위의 보유 권리 복구·검증 |
| 6. 실제 ZK 프로필 | 증명 명세·회로·검증기·노출 표·변조 검사 | 약속한 비공개 값의 보호와 공개 검증, 증명 생성·검증 비용 측정 |
| 7. 금융·마케팅 연결 | 증거 범위를 가진 금융 리포트, 발송 시점 동의 확인 | 원장·PG와 수치 대조. 철회·미귀속·상충 상태 반영 |

1~3의 계약이 정리되는 동안 4의 발권·소유·소비 모듈과 직렬화 테스트 벡터를 설계할 수 있다. 모든 운영 기능을 완성한 뒤에야 체인을 시작할 필요는 없다. 다만 수정 중인 금전 가정을 이미 검증된 체인 규칙으로 배포하지 않는다.

다음 버전이 보여줘야 할 대표 여정은 다음이다.

> 주최자 승인 물량 발행 → A 유료 구매 → B에게 정책에 따른 리셀 → B의 권리 수신·독립 검증 → 입장 또는 원결제 경로의 환불 → 배분·수수료·회수 부담 대조. 별도 분기로 무상 양도와 반환 좌석 신권리 발행을 확인한다.

혁신의 측정 대상은 ‘서비스들이 한 DB에 모였다’는 사실에서 **운영 주체가 달라도 권리·정책·복구 근거가 유지되고, 불필요한 거래정보를 공개하지 않아도 정해진 검증이 가능하다**는 결과로 옮긴다. 이 기술 목표와 특허 등록 가능성은 별도 판단이다. 이번 검토는 새 특허 가능성을 상향하거나 낮추는 결론을 내리지 않는다.

## 부록 A. 재현 파일 사용

검토 패키지는 원본 `core.py`를 수정하지 않는다. `original_bundle/`은 첨부 ZIP의 내용 사본이며, 단일 변이는 실행할 때 임시 디렉터리에만 적용된다.

```bash
python review_probe.py --bundle original_bundle --output rerun_review
```

`review_results.json`에는 10개 재현 사례, 각 변이의 정확한 교체 문자열·결과·실패 검사, 생존 변이의 원본/변이 비교 입력 결과가 있다. `mutation_logs/`에는 기존 31검사의 변이별 전체 로그가 있다. `baseline_run/`에는 원본 재실행의 주요 JSON·검사 로그를 보존했다.

결과 JSON의 재현 사례 성공은 제품 요구사항 통과가 아니라 **현재 동작을 다시 관찰했다는 의미**다. 실제 PG·체인·은행·사용자 자료는 포함하지 않는다.
