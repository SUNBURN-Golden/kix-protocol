# KIX v0.2 목적 대조·기술 검토

검토일: 2026-09-11. 대상은 사용자 첨부 v0.2 수정 명세, Sui·ZK 후속 구현 계약 및 소스 검증 패키지다. 첨부 원본과 GitHub의 v0.1 구현은 변경하지 않았다. 별도 호출 코드와 검토자료를 작성했다.

**판단: v0.2를 다음 개발의 기준으로 삼는 방향은 맞다. 금융·권리 상태의 기준 모형은 실제로 개선됐다. 다만 KIX의 차별화 목표인 운영자 독립성·거래 프라이버시·사업자 간 상호운용성은 아직 설계 단계다. 확인된 경계 문제를 수정하면서 실제 권리 프로그램과 독립 클라이언트를 구현하는 것이 다음 진전이다.**

이번 결과를 특허 진보성 확보, 실제 PG 연결 완료, 블록체인 성능 입증으로 해석하지 않는다. 이번 회차에는 새로운 특허 선행문헌 전수조사나 한국법 개정 전체의 재검토를 수행하지 않았다.

**1. 원래 목적과 현재 위치**

KIX의 목적은 여러 예매처·리셀 사업자·주최자·검표자가 같은 티켓의 발행·이전·사용·취소 규칙을 검증하고, 필요한 거래·정산 사실을 과도한 개인정보 공개 없이 연결하는 것이다. 특정 운영자의 장애로 이미 발행된 권리를 사용할 수 없게 되는 의존성도 줄여야 한다. 이 기반 위에 이해관계자 배분, 금융 자료, 동의에 따른 마케팅이 연결된다.

| 원래 목표 | v0.2의 실제 상태 | 다음에 필요한 증거 |
|---|---|---|
| 티켓 생애주기 | 재고/발행 권리 분리, 구매·리셀·양도·초대·입장·폐기 구현 | 실제 권리 프로그램에서도 같은 전이와 거절 조건 성립 |
| 블록체인에 기초한 운영자 독립 | 단일 SQLite가 정본. 로컬 명령 재실행 복구 | KIX 서비스 중지 후 별도 클라이언트가 체인에서 권리 확인·사용 |
| 익명성·검증 가능성 | 금융 조회의 필드 최소화, ZK 명제 후보. 실제 증명기 없음 | 누구에게 어떤 정보가 숨겨지는지 정의하고 회로·전송·저장 모두에서 확인 |
| 공식 리셀과 암표저항성 | 가격 상한·권리 잠금·게시/예약·이전 권리 거절 | 양도 정책 우회, 무결제 예약 점유, 자격·수량 제한의 처리 |
| 리셀 가치 재분배 | 최초 판매 2자, 리셀 3자의 고정 비율 배분 | 공연자·공연장·기획사 등 수취인 정책, 총액/차익 기준, 취소 부담과 지급 시점 |
| 상호운용성 | 단일 원천 scope, 문자열 권한, 이전 모형과 일부 계약 검사 | 서로 다른 발권사·운영자 키와 독립 어댑터가 같은 규격을 실행 |
| 금융성 | 환불 의무·미확정 지급·PG 조정 등 합성 금융 조회 | 원천 범위·시점·귀속·제한 상태를 검증하는 자료 계약 |
| 마케팅 | 동의 버전 및 발송 의도 직전 확인 | 사업자별 권한·실제 발송 연결·철회 처리. 개인정보는 별도 저장 |
| 혁신의 객관적 근거와 IP | 실패 사례와 상태 전이를 설명할 재현 자산 | 구체 해결수단, 가까운 기존 수단 대비 차이·효과, 구성요소별 선행기술 대조 |

이번 판의 성과는 ‘운영 규칙을 구현하고 잘못된 상태를 더 많이 차단한 것’이다. 운영자 독립성과 ZK가 미구현이라는 점은 문서에도 정확히 표시돼 있다. 여기서 제품 전체의 완성도를 한 숫자로 표시하면 현재 위치가 오히려 흐려진다.

**3. 그대로 유지할 개선**

- 취소가 먼저 확정된 미송신 지급을 중단하고 예약을 해제한다. 송신 의도가 앞섰다면 외부 실행 가능성을 남긴다.
- 환불 의무를 분류 완료까지 숨기지 않고 먼저 인식한다. 회수채권과 고객 환불 의무를 분리한다.
- 원결제 취소와 실제 현금 송금을 다른 경로로 처리한다. PG 취소 수락·고객 계정 반영·가맹점 정산 조정을 구분한다.
- 폐기된 티켓을 되살리는 대신 재고를 해제하고 새 발행 세대를 만든다. 늦은 결제가 옛 거래를 확정하지 못한다.
- 원자료를 먼저 보존한다. 재처리와 명령 멱등성이 이어지며, 두 번째 결제 승인을 조용히 버리지 않는다.
- 무상 양도·초대권을 금액 0원의 유상 거래로 우회하지 않는다. 동의의 오래된 갱신과 과거 발송 허가의 재사용을 제한한다.

이 변화들은 실제 분산 구현의 비교 기준으로 가치가 있다. 체인에 옮길 때도 유지해야 할 의미다. 특히 토스의 안내는 이미 정산된 결제 취소를 다음 정산에서 조정할 수 있다고 설명한다. 따라서 원결제 취소를 항상 가맹점 현금의 동시 출금으로 보던 가정을 분리한 것은 타당하다. [토스 결제 취소 안내, ‘이미 정산 받은 결제’ 및 ‘전액 취소하기’](https://docs.tosspayments.com/guides/v2/cancel-payment)

**4.1 고객 환불 확인과 실패 fence의 충돌 — R02·R07**

재현 순서는 다음과 같다.

1. 100,000원 구매·정산 후 행사를 취소한다.
2. 원결제 취소 effect를 송신 의도 상태로 만든다.
3. `CUSTOMER_CREDIT_CONFIRMED=100000` 관찰을 입력한다. `APPLIED`가 된다.
4. 같은 effect에 ‘이후 실행 불가’를 뜻하는 `FENCED_FAILURE`를 입력한다. 이것도 `APPLIED`가 되고 `FAILED_FENCED`로 바뀐다.
5. 다른 현금 환불 경로로 100,000원 effect를 준비·송신 의도 확정하고 성공·출금을 반영할 수 있다.

최종 상태에는 PG 측 고객 환불 확인 100,000원과 별도 현금 경로 이행 100,000원이 함께 있다. 원래 의무는 100,000원인데, 현재 `Core.check`는 이 상태를 받아들인다. 순서를 바꿔 실패 fence가 먼저 오면 뒤의 고객 환불 확인은 `REVIEW`로 남는다.

**실제 PG가 이 두 개의 모순된 사실을 제공했다고 주장하는 것이 아니다.** 같은 원천의 상충 관찰을 받아 처리하는 합성 모델에서, 먼저 받은 긍정적 자금 사실을 후속 부정 표식이 무시한다는 반례다. 기존 검사에도 실패 fence 이후의 늦은 출금을 검토로 남기는 사례가 있으므로, 이 순서 역시 같은 방어 범위에서 다뤄야 한다.

원인은 `finance.py`의 `_observe_effect()` 중 `FENCED_FAILURE` 분기가 `confirmedAmount`와 `fundsAmount`만 확인하고 `customerCreditConfirmed`를 확인하지 않는 데 있다. 이 상태가 `TERMINAL`에 들어가면 다른 경로의 의무 예약이 풀린다.

수정 방향은 다음과 같다.

- 최종 실패는 ‘해당 시도의 실행 결과가 없고 앞으로도 실행될 수 없음’이라는 계약과 연결한다.
- 이미 고객 귀속·출금·이행을 나타내는 증거가 있으면 모순된 실패 표식으로 예약을 해제하지 않는다.
- 상충을 별도 상태로 남기고, 같은 의무의 새 경로 활성화를 제한한다.
- 긍정적 사실을 되돌리려면 그에 대응하는 반환·정정 증거와 귀속 규칙이 필요하다.
- 두 관찰의 도착 순서 각각에서 원자료 보존과 중복 의무 실행 차단을 확인한다.

이는 단순히 조건 하나에 `customerCreditConfirmed`를 더하는 수정으로 시작할 수 있지만, 최종 계약은 ‘어떤 증거가 어떤 사실을 부정할 수 있는가’를 정의해야 한다.

**4.2 정상 반영을 마친 정산 자료가 검토금액에 남음 — R01**

승인 관찰보다 정산 자료가 먼저 들어오도록 했다. 정산 100,000원은 처음에 `SETTLEMENT_BINDING_MISMATCH`로 `REVIEW`에 들어간다. 이후 승인을 반영하고 동일 원자료를 재처리하면 정상 정산이 이뤄진다.

그런데 결과는 다음과 같다.

| 항목 | 실제 결과 |
|---|---:|
| 원자료 상태 | APPLIED |
| 정산 반영액 | 100,000원 |
| inboxPendingOrReview | 0건 |
| observedMovementAmountUnderReview | 100,000원 |
| amountsAreUnpostedObservations | true |

돈을 두 번 분개한 오류는 아니다. **이미 분개한 금액을 미반영 관찰금액이라고 다시 표시하는 조회 오류**다. 금융 자료를 읽는 기관이 확인된 정산과 미해결 관찰을 구분할 수 없게 만든다.

`observations.py`의 `record_review_fact()`는 행을 생성하지만, `apply_observation()`의 성공 경로에는 해당 경제적 사실의 해결 상태를 반영하는 동작이 없다. `inbox_summary()`는 남은 행을 그대로 합산한다.

원문이나 과거 검토 이력을 삭제하지 말고, 경제적 사실별로 `OPEN / RESOLVED / CONFLICT`와 해결한 원장 사건을 연결한다. 여러 관찰이 같은 사실을 가리킬 수 있으므로 관찰 한 건의 성공만으로 관련 충돌 전체를 해결했다고 처리하면 안 된다. 금융 조회의 ‘미반영’ 합계는 아직 원장에 귀속되지 않은 활성 사실만 집계해야 한다. 원장 반영과 해결 표시 사이 장애에서도 같은 결과로 재처리할 수 있어야 한다.

**4.3 일부 지급 후 확정 종료·반환 경로 — R03·R04**

95,000원 지급 중 40,000원의 성공과 출금이 확인된 뒤 행사를 취소했다. 지급된 40,000원은 반영되지만, 나머지 55,000원의 실행이 최종 종료됐다고 기록할 수 없다. `FENCED_FAILURE`는 기존 성공·출금이 모두 0인 경우에만 허용된다.

그 결과 55,000원이 계속 미확정 지급으로 남고 환불 분류 대기 100,000원도 유지된다. 이미 지급된 40,000원이 반환되는 사건을 입력해도 `_observe_return()`이 effect 전체의 `DONE`을 요구해 거절한다.

현재 명세의 ‘부분 이행’은 **결국 전액 성공하는 진행 과정**에는 대응한다. ‘일부 성공으로 최종 종료’와 ‘진행 중 부분 지급분 반환’은 별도 상태가 필요하다.

보충할 계약 예시는 다음과 같다.

- `PARTIALLY_FINALIZED`: 최종 실행 누계와 미실행 잔액을 함께 고정한다.
- 잔여 실행의 종료 증거에는 시도, 누계 금액, 마지막 원천 순번·기준 시점, 이후 실행 불가 범위를 결합한다.
- 실행되지 않은 잔여분만 예약을 해제한다. 확인된 지급분은 계속 지급 이력으로 남긴다.
- 반환은 실제 반영한 지급 부분을 참조한다. 전체 요청이 끝나지 않았다는 이유로 실제 입금 사실을 버리지 않는다.
- 완료 누계·반환 누계·현재 미지급 의무를 구분해 동일 반환을 중복 반영하지 않는다.

원천이 잔여분 종료를 보장하지 못한다면 불명확 상태를 유지하는 것이 맞다. 그 경우는 지원하지 못하는 복구 경로로 명시해야 한다.

**4.4 최초 송신 의도 응답 유실 — R05**

`send_effect`에서 로컬 커밋 직후 응답 유실을 주입하고 DB를 다시 열었다. 이 재현에서는 실제 외부 송신을 한 번도 수행하지 않았다. 같은 명령 ID와 새 명령 ID로 다시 요청해도 둘 다 `QUERY_ONLY`가 돌아왔고, `providerOperationId`는 `null`이었다. 요청 본문 자체는 로컬 상태에 남아 있다.

취소 이후 무조건 재송신하지 않는 방어는 유지해야 한다. 다만 **영속 송신 의도, 작업자 인수, 원천 접수, 원천 완료를 구분하지 않으면 ‘아직 보낸 적 없는 의도’도 끝없이 조회만 하는 상태에 들어갈 수 있다.** 원천 실행 ID가 없는 경우 어떤 참조로 조회하는지도 필요하다.

실제 어댑터 계약에는 다음을 넣는다.

| 구분 | 필요한 정의 |
|---|---|
| 요청 보존 | 정확한 요청 바이트/해시, 논리 명령, 시도, 원천 scope |
| 동일 요청 재제출 | 동일 멱등키·동일 내용·동일 경로를 언제 재사용할 수 있는지 |
| 취소와 재제출 | 아직 유효한 의무인지, 재제출이 최초 외부 실행을 일으킬 수 있는지 |
| 접수 여부 확인 | 원천 실행 ID가 없어도 조회할 수 있는 키와 보장 범위 |
| 새 시도 | 옛 시도의 이후 실행 불가와 미이행 잔액 확인 |
| 보장 만료 | 오래된 미확정 요청을 새 키로 자동 실행하지 않는 처리 |

토스 공식 안내는 멱등키를 이용한 동일 요청 재시도, 처음 사용한 날부터 15일의 유효기간, API 키·주소·HTTP 메서드와의 결합을 설명한다. 오류 뒤 키를 바꿔 재시도하는 위험도 명시한다. 이 안내를 은행 송금의 일반 계약으로 확대하거나, 15일이 지나면 과거 결과 확인 없이 새 환불을 실행해도 된다고 해석하면 안 된다. [토스 인증 및 기타 헤더 설정, ‘멱등키 사용하기’](https://docs.tosspayments.com/reference/using-api/authorization)

Sui는 같은 서명 거래의 재제출과 digest 조회를 따로 설명한다. 조회에 안 나온 거래는 미확정 또는 해당 노드의 미인지일 수 있고, 확정된 거래도 실행 결과는 실패일 수 있다. 따라서 후속 계약이 `QUERY_ONLY`를 모든 체인 거래에 복사하지 않도록 한 부분은 유지한다. [Sui 거래 생애주기, ‘Transaction idempotence and finality verification’](https://docs.sui.io/develop/transactions/transaction-lifecycle)

**4.5 원문 충돌과 금융 자료의 증거 범위 — R06**

동일 observationId에 다른 원문을 입력하면 `raw_conflicts`에는 정확히 보존된다. 그러나 금융 조회의 `sourceReview`는 변하지 않았다. `conflictingReviewFacts=0`이 유지됐고 `evidenceDigest`도 같았다.

현재 digest는 `raw_inbox`의 일부 열만 포함한다. 원문 충돌 테이블까지 포함하는 전체 증거 commitment가 아니다. 원문 손실 결함은 아니지만, 이를 금융 증명의 입력으로 쓰기 전에는 범위를 넓히거나 이름과 별도 지표로 분리해야 한다.

권장 범위는 원자료 인덱스, 원문 충돌, 경제적 사실의 활성/해결 상태, 귀속 관계, 원장 반영 순번이다. ‘기관에 전달한 원천 집합’의 commitment와 ‘PG에서 얻어야 할 전체 모집단’의 완전성은 여전히 다른 주장이다. 원천 커서나 자료 제출 범위를 인증할 근거가 없다면 `NOT_ATTESTED`를 유지한다.

현재 `evidenceDigest`와 일부 inbox 건수는 전역 자료를 대상으로 한다. 행사별 금융 조회에 넣는 지표는 행사 범위와 전역 범위를 표시해야 한다. 향후 여러 사업자가 사용하는 경우 다른 행사의 자료 변경까지 동일 요약에 반영할 필요가 있는지도 정보 최소화 관점에서 검토한다.

**4.6 재고 식별자와 리셀 예약 정책 — R09·R08**

재고 키를 `eventId + '/' + seat`로 만든다. 허용되는 입력인 행사 `a`의 좌석 `b/c`와 행사 `a/b`의 좌석 `c`를 순서대로 생성하면 둘 다 `a/b/c`가 된다. 재고가 아직 발행되지 않은 경우 두 번째 생성이 첫 재고를 덮어쓴다. 행사 2개, 재고 1개가 남는다.

표시용 경로와 정본 키를 구분하고, 발행자·행사·회차·좌석의 정규화된 튜플이나 별도 내부 ID로 식별한다. 새 재고 등록은 기존 항목의 덮어쓰기를 거절해야 한다. 실제 다중 발권사 연결 전에 고정할 사항이다.

리셀 게시에서는 구매자가 `expiresAt=86400`으로 예약할 수 있고 결제 없이 그 시간만큼 잠글 수 있었다. **판매자는 `abort_trade`로 취소할 수 있으므로 영구 잠금 취약점이라고 표현하지 않는다.** 다만 구매자가 장시간 점유하고 판매자가 수동으로 풀어야 하는 구조는 원래의 암표저항성·원활한 공식 리셀 목표에 맞지 않는다.

게시 만료와 결제 예약 시간을 분리하고, 예약 상한은 행사·상품 정책에서 정한다. 구매자가 임의로 늘리지 못하게 하며, 주체별 동시 예약 제한과 반복 미결제 점유에 대한 처리를 둔다. 지갑 주소 하나를 사람 한 명으로 간주하는 제한만으로 다계정 문제를 해결했다고 보지는 않는다.

**5. Sui 후속 계약에서 먼저 구체화할 것**

**5.1 ‘KIX 서버 중지’의 범위를 서비스 의존성까지 확장한다.**

현재 후속 계약의 독립 검증 목표는 맞다. 시험에서 꺼야 할 것과 계속 필요한 것을 더 구체적으로 정해야 한다.

| 의존성 | KIX 중지 시 확인할 사항 | 선택할 수 있는 구현 방향 |
|---|---|---|
| 웹/조정 API·조회 DB | 이들에 요청하지 않고 발행된 권리를 찾는가 | 독립 클라이언트와 체인 조회 |
| 로그인·제어 키 | KIX 로그인 성공이 권리 행사에 필수인가 | 사용자 보유 키 또는 승인된 독립 복구 수단 |
| salt·세션·증명 생성 | 새 증명을 만드는 비밀과 실행기가 남아 있는가 | 사용자 보관 자료, 대체 증명기·배포 경로 |
| 가스 대납 | KIX가 서명하지 않아도 사용 거래를 제출하는가 | 주최자·다른 대납자 또는 명시적인 사용자 부담 경로 |
| 암호문 저장소 | 권리 노트와 포함 경로를 재구성할 자료가 남아 있는가 | 사용자 사본과 별도 가용 저장소 |
| RPC·인덱서 | 다른 URL이 실제로도 KIX 밖의 경로인가 | 독립 운영 경로와 검증하는 확정 근거 |
| 검표 권한 | 대체 검표자에게 실제 행사 권한이 있는가 | 사전에 발급·검증 가능한 행사별 권한 |
| 취소·업그레이드 | KIX 단독 관리 키가 전체 사용을 막거나 규칙을 교체하는가 | 권한별 범위, 권리의 정책 버전, 회수·변경 절차 |

Sui의 가스 대납 거래는 사용자와 sponsor의 서명을 포함한다. 따라서 sponsor가 KIX 하나뿐이면 KIX 중지가 새로운 소비 거래를 막을 수 있다. KIX 의존성이 없다는 시험에서는 가스 공급·서명 경로도 확인해야 한다. [Sui Sponsored Transactions, ‘Data structure’ 및 ‘Create sponsored transactions’](https://docs.sui.io/develop/transaction-payment/sponsor-txn)

zkLogin에서는 salt와 증명 서비스가 별도 구성요소다. salt 유실은 해당 주소 접근 상실로 이어질 수 있고, 증명·salt 서비스는 신원 정보를 연결할 수 있다. 따라서 ‘zkLogin을 쓰면 복구와 익명성이 모두 해결된다’는 식의 설계를 피하고 실제 보관·복구·증명 경로를 선택해야 한다. [Sui zkLogin Technical Reference, ‘Entities’, ‘User salt’, ‘Privacy’](https://docs.sui.io/sui-stack/zklogin-integration/zklogin)

독립성의 첫 범위는 명세대로 이미 확정된 권리의 복구·검증·소비다. 새 원화 결제, 새 유료 리셀, 환불, 금융 실행까지 KIX 중지 중 계속할 수 있다는 주장으로 확대하지 않는다. 각각 PG 권한과 원천 자료 등 추가 의존성이 있다.

캐시가 남아 있는 기존 브라우저 하나로만 시험하지 않는다. KIX 중지 후 새 검표 challenge, 세션 만료, 조회 캐시 없는 클라이언트, 대체 가스 경로를 구분해 확인한다. 사용자가 정당하게 보관한 복구 비밀·자료를 투입하는 경우와 그 자료까지 잃어버린 경우도 구분한다. 모든 키와 복구 수단을 잃어도 권리를 복원할 수 있다는 목표는 이 시험에 포함되지 않는다.

**5.2 Python의 operator 권한을 체인에 그대로 옮기지 않는다.**

현재 `_commit_trade()`는 `operator`만 실행할 수 있다. 이 역할 검사까지 그대로 Move에 옮겨 KIX가 모든 권리 전이에 서명하도록 하면, 체인에 기록은 남아도 KIX가 없을 때 새 전이는 멈춘다.

체인에서는 ‘누가 요청을 중계했나’와 ‘어떤 권한·증거가 전이를 정당화하나’를 분리한다. 보유자 승인, 수신 수락, 허용된 결제 증거, 행사·권리 상태가 충족되면 지정된 제출 경로로 실행할 수 있게 설계한다. PaymentAttestor가 KIX의 한 키라면 새 결제 연계의 신뢰·가용성은 여전히 그 키에 의존한다. 복수 attestor를 등록할 경우에도 각자의 PG·가맹점·환경·증거 유형 범위를 구분해야 한다.

주소 보유 객체를 사용한다면 모듈 외부 전송을 막는 타입 설계도 구체화한다. Sui 문서는 `transfer<T: key>`와 `public_transfer<T: key + store>`를 구분한다. 실제 권리 타입에 `store`를 부여할지, 보유자 승인과 정책 검사를 어느 진입점이 강제할지 소스와 공격 입력으로 확인한다. [Sui Address-Owned Objects, ‘Create address-owned objects’](https://docs.sui.io/develop/objects/object-ownership/address-owned)

**5.3 독립 검증 영수증은 과거 성공과 현재 유효성을 함께 다뤄야 한다.**

과거에 발행됐다는 영수증만으로 지금 입장할 수 있다고 판단하지 않는다. 예상한 네트워크·프로그램·정책, 현재 소비·취소 상태, 발행 세대, 위임 상태를 확인해야 한다. 확정 근거를 직접 검증하는지, 신뢰하는 노드의 응답을 사용하는지도 시험 보고에 적는다.

읽기 전용 권리 조회와 실제 1회 소비를 구분한다. KIX 없이 조회만 성공하고 소비에는 KIX 서명이 필요한 경우는 최종 목표의 일부만 달성한 것이다. 단절 검표에서는 기존의 배타적 위임과 최종 로그 조건을 유지한다.

**6. ZK 후속 계약의 핵심 설계 공백**

**6.1 공개 객체에 나중에 ZK를 붙여도 이미 공개한 연결은 사라지지 않는다.**

후속 계약은 공개 객체 프로필과 비공개 프로필을 분리한 점이 좋다. 다음은 비공개 프로필의 실제 데이터 구조를 결정하는 일이다.

- `ticketId`가 이전마다 그대로 공개되면 거래 이력을 연결할 수 있다.
- `InventoryUnit.currentRight`가 공개적으로 계속 바뀌면 전후 권리의 연결이 드러날 수 있다.
- 구매자 주소, 결제 참조, 송신자, 가스 대납, 암호문 크기·시각이 증명 밖에서 연결 단서를 만들 수 있다.
- 좌석이나 희소한 회차 정보 자체도 소규모 행사에서는 관객을 좁히는 단서가 된다.

이는 KIX 설계에 대한 정보 흐름 분석이다. 현행 v0.2에 이미 구현된 ZK가 깨졌다는 발견은 아니다. 공개 프로필을 만들 때부터 이것을 최종 익명 티켓으로 설명하지 말아야 한다.

| 상대 | 기본적으로 검증할 사실 | 기본적으로 전달하지 않을 정보 | 별도 결정 |
|---|---|---|---|
| 공개 체인 관찰자 | 허용 전이·소비 표식의 유효성 | 실명·연락처·PG 원문·공개할 필요 없는 금액 | 행사·좌석·거래 연결·송신 메타데이터 노출 범위 |
| 현장 검표자 | 해당 회차·미사용·제어 권한·필요 자격 | 전체 구매/재판매 이력, 불필요한 금융 정보 | 좌석 안내에 필요한 공개 범위 |
| 새 구매자 | 수락한 조건과 실제 수신 권리의 일치 | 판매자의 다른 관람·거래 이력 | 당해 거래에서 필요한 상대 정보 |
| 주최자·정산 수취인 | 자신에게 적용되는 배분·환불 근거 | 다른 수취인의 불필요한 개별 자료 | 계약상 필요한 운영 자료 |
| 금융기관 | 정해진 범위·시점의 집계와 미확정 부담 | 개별 관객 정보 원문 | 실제 심사·계약에 필요한 추가 공개 |
| KIX·PG 등 원천 처리자 | 맡은 업무에 필요한 실제 자료 | 업무와 무관한 타 기관 자료 | 보유·삭제·접근·정당한 제출 요청 처리 |

익명성을 ‘아무도 아무 자료도 보유하지 않음’으로 정의하지 않는다. 원천 처리자가 아는 정보와 다른 검증자에게 공개하지 않는 정보를 구체적으로 구분한다.

공개 필드 수가 줄었다는 숫자만으로 익명성을 입증할 수도 없다. 남은 식별자 하나나 시각·좌석 조합으로 개인을 연결할 수 있는지 별도 관찰 모델에서 평가한다.

**6.2 지금 가장 중요한 기술적 결합 문제는 ‘비공개 권리의 현재성’이다.**

보유 노트의 존재를 숨기면서 미사용을 증명하는 것만으로는 충분하지 않다. KIX에는 취소·양도·위임·재발행·키 복구가 있다. 이들 이후에 옛 노트가 사용되지 않아야 한다.

설계가 답해야 할 질문은 다음과 같다.

1. 개별 권리를 취소하거나 재발행할 때 어느 비공개 권리인지 시스템이 어떻게 식별하는가?
2. 그 식별 과정에서 공개 관찰자에게 전후 보유자·노트를 연결하는 표식을 얼마나 노출하는가?
3. 보유자가 공개하지 않은 비밀로 nullifier를 만들 때, 키 분실·강제 취소 후 옛 권리를 어떤 공개 검증 상태로 무효화하는가?
4. 운영자가 중지돼도 새 검증자가 동일한 현재 상태와 노트 복구 자료를 얻는가?

후속 계약의 ‘재고 발행 세대도 검사한다’는 문장을 비공개 검증으로 구체화해야 한다. 공개된 inventoryId를 입력으로 받아 조회하는 방법은 단순하지만 연결성을 노출한다. 숨긴 슬롯·세대를 인증된 유효 상태 집합에 대해 증명하는 방법을 검토할 수 있으나, 그 root의 갱신 권한·자료 가용성·동시 전이도 설계해야 한다. 어떤 방식이 더 적합한지는 프로토타입과 비교가 필요하다.

이 지점은 연구할 만한 구체 문제다. accumulator, revocation, nullifier 등 알려진 수단으로 해결 가능한 범위를 먼저 대조해야 하며, 아직 신규 발명이라고 판정한 것은 아니다.

**6.3 검증키와 공개 입력 바이트 규격을 구현 계약에 추가한다.**

현재 명세에는 증명할 명제는 있지만 `CircuitRegistry` 또는 이에 해당하는 신뢰할 검증키 선택 계약이 없다. 회로 버전, 검증키 해시, 허용 동작, 공개 입력 순서, 활성·폐기 조건을 프로그램이 고정해야 한다.

Sui의 Groth16 안내는 BN254/BLS12-381 검증, 회로별 trusted setup, 공개 입력 최대 8개를 설명한다. 또한 사용자에게 임의 검증키를 선택하게 두지 말고 예상한 검증키를 계약이 고정하거나 검증할 것을 명시한다. [Sui Groth16, ‘Usage’ 및 검증키 관련 주의사항](https://docs.sui.io/develop/cryptography/groth16)

KIX에 대한 설계 제안은 다음과 같다.

- `circuitId/version → verifyingKeyHash → publicInputSchemaHash → allowedActions`를 등록한다.
- 네트워크·프로그램·회로·행사·정책·만료·동작 등의 바인딩을 필드 입력 또는 규격화된 context commitment로 연결한다.
- 입력을 압축할 때도 실제 전이 인자와 회로 안의 값이 같은지 검증한다. 단순히 hash 한 개를 전달하는 것만으로 바인딩이 생기지 않는다.
- SHA-256 값, 필드 원소, 정수, BCS/JSON, 문자열을 어떻게 변환할지 고정한다. 범위·길이·구분자·잘못된 인코딩을 테스트 벡터로 만든다.
- 금액 보존에는 음수·범위·절사·잔여 배분의 제약을 포함한다. 필드 연산의 합이 맞는 것과 원화 정수의 합이 맞는 것을 혼동하지 않는다.
- 테스트용 setup·고정 비밀을 사용한 결과와 실제 배포용 파라미터를 구분한다.

위 8개 제한은 이번 확인일의 공식 안내 기준이다. 구현에서는 사용할 Sui 버전과 검증 API를 고정해 다시 대조한다.

**6.4 첫 ZK 회로는 검표에 필요한 최소 명제로 시작한다.**

첫 비공개 소비의 목표를 ‘해당 회차의 유효한 미사용 권리를 제어하는 보유자가, 지정된 검표 요청에 대해 한 번 소비한다’로 정할 수 있다. 다음 관계가 필요하다.

- 노트 commitment의 포함과 제어 비밀의 일치.
- 같은 노트의 양도·입장·환불에서 동일한 소비 표식 사용.
- 행사·회차·정책·허용 root·현재 취소/세대/위임 상태의 일치.
- 검표자·challenge·소비 목적·만료와 증명의 바인딩.
- 검증과 nullifier 소비의 원자적 전이.

동작 종류를 nullifier의 구분자로 넣어 같은 노트를 동작마다 다시 쓰게 만들지 않는 원칙은 유지한다. 다만 동작 자체는 별도의 증명 문맥에 결합해야 한다. 소비 표식 공유와 동작 바인딩은 서로 다른 조건이다.

‘옛 root 거절’이라는 시험 문구도 다듬는다. 허용된 과거 root를 사용하면서 아직 유효한 노트는 프로토콜에 따라 정상일 수 있다. 거절 대상은 허용되지 않은 root, 또는 과거에는 유효했어도 현재 소비·취소·세대 변경으로 무효가 된 권리다.

그다음 같은 노트 생애주기에 공식 리셀과 환불·배분 증명을 붙인다. 검표만의 별도 익명 토큰으로 끝내면 우리가 원했던 리셀·금융 연결에서 같은 권리를 사용한다는 보장이 빠진다.

**6.5 복구 자료 가용성과 증명 생성을 별도로 시험한다.**

암호문 hash나 수신자의 ACK는 자료가 계속 존재한다는 증명이 아니다. 사용자 사본·대체 저장소·복구 키로 실제 노트와 필요한 검증 경로를 복원해야 한다. 신뢰할 프로그램·회로·검증키를 어디에서 얻는지도 고정한다.

증명 생성 서버에 개인 노트·거래 원문을 보내는 방식이면 그 서버는 해당 비밀을 볼 수 있다. ‘검증자에게 숨김’과 ‘증명 생성자에게도 숨김’을 분리한다. 사용자 장치에서 생성할지, 신뢰 범위를 정한 외부 증명기를 사용할지 선택하고, KIX 중지 시에도 새 증명을 만들 수 있어야 한다.

**7. 리셀 가치 재분배·금융·상호운용성이 구현에서 빠지지 않게 할 것**

**리셀.** 현재 `_commit_trade()`는 최초 판매의 주최자·플랫폼과 재판매의 판매자·주최자·플랫폼만 계산한다. 상품 정책의 실행 가능한 확장 형태는 수취인 역할·배분 기준·순서·절사·잔여·지급 조건·취소 부담까지 포함해야 한다.

총액 기준과 차익 기준을 구분하고, 차익을 쓰는 경우 최초 표시 가격인지 현재 판매자의 실제 취득원가인지 명시한다. 손해를 보는 재판매, 무상 취득·초대권, 수수료 포함 여부를 처리해야 한다. 양수 차익이 없는 경우에도 배분 때문에 판매자의 순액이 비정상적으로 감소하지 않는지 확인한다. 이는 상품 계약의 선택이며 이번 검토에서 비율을 확정하지 않았다.

현재 판매자가 판매 대금을 받는 것과 과거 구매자에게 이후 리셀 수익을 계속 배분하는 것은 구분한다. 후자를 추가하지 않기로 한 방향은 유지한다. 공식 경로의 배분 집행과 플랫폼 밖의 송금·계정 매매 관측 가능성도 구분해야 한다.

**금융.** 지금 제공하는 자료는 금융 인프라의 입력 후보다. 실제 대출·투자·담보권이나 지급 권한이 아니다. 원천의 귀속·시점·취소 부담·미확정 상태가 명확해야 금융 모듈이 연결될 수 있다.

권리·배분·실제 자금은 최소 세 층으로 나누는 편이 명확하다. 유효한 티켓 전이가 존재하는 것, 누가 얼마를 받을 계약상 근거가 생기는 것, 실제 돈이 이동한 것은 다르다. 증명할 집계의 범위도 최초 판매 총액, 리셀 총액, 주최자 몫, 환불 부담, 미수·보류·회수채권으로 구분한다.

ZK는 제출된 자료의 계산이 맞는지 증명할 수 있도록 설계할 수 있지만, 누락된 PG 자료를 저절로 찾아주지는 않는다. 금융기관에 내놓을 입력은 원천 범위·수집 기준 시점·누락·상충·해결 상태와 결합해야 한다. R01과 R06은 그 전제에 직접 영향을 준다.

현재 모든 수취인에게 공연 완료 후 지급하는 것은 합성 가정이다. 조기 정산·자금조달을 다루려면 수취인별 지급 조건과 재원·환불 부담이 필요하다. 거래 풀을 합치거나 관객 결제금을 회사 자금처럼 쓰는 방식으로 이 차이를 지우면 안 된다.

**상호운용.** 다른 예매처가 HTTP API를 호출하는 것만으로 권리가 상호운용되지는 않는다. 발권사별 권한과 원 티켓의 정본을 확인해야 한다.

| 추가 계약 | 필수 질문 |
|---|---|
| 발권사 registry | 어느 키가 어떤 행사·회차·물량을 발급할 수 있는가? |
| 외부 티켓 참조 | 발권사·native ID·버전의 조합이 유일한가? |
| 공식 전환 | 원 발권 시스템의 폐기/잠금과 새 권리 발급을 어떤 증거로 연결하는가? |
| 중단·지연 처리 | 원 티켓 종료 후 새 발행 실패, 또는 그 반대의 상태를 어떻게 보존하는가? |
| 독립 검표 | 어느 권리 규격·검증키·행사 위임을 인정하는가? |
| 결과 대조 | 원천 사건과 체인 영수증이 같지 않을 때 누가 어떤 근거로 해결하는가? |

초기 자체 발권은 이 계약을 단순하게 시작할 수 있다. 기존 예매처의 이미지나 QR만 받아 새 권리를 만드는 경로는 두 개의 유효한 입장 근거를 만들 수 있으므로 공식 전환을 대신할 수 없다. 인터파크·YES24 등과의 실제 제휴/API 권한이 확보됐다는 근거는 이번 자료에 없다.

**마케팅.** 동의 처리의 개선은 유지하되 ZK 권리의 비공개 이력을 상시 고객 프로필로 복원하는 지름길을 만들지 않는다. 현재 `business='KIX'`만 허용하므로 주최자 CRM과 복수 사업자 동의는 추가 설계 대상이다. 마케팅 확장이 독립 권리·비공개 검증의 첫 실증보다 앞설 이유는 없다.

**8. 특허 목표로 이어지는 방법**

이번 코드의 수정과 검사 통과는 발명을 설명할 자료다. 그 자체로 기존 수단 대비 결합의 곤란성이나 등록 가능성을 확인한 것은 아니다. 동시에 이번 결과만으로 특허 가능성이 0이라고 판단할 근거도 없다.

연구 질문을 다음처럼 좁히면 우리가 원한 혁신과 구현이 이어진다.

| 질문 | 구체화할 구성 | 비교해야 할 기존 수단 |
|---|---|---|
| 비공개 권리의 취소·재발행을 어떻게 현재 소비 검사와 연결할 것인가? | 숨긴 권리/세대의 인증 상태, 공통 소비 표식, 종료 근거 | 익명 자격증명·revocation accumulator·기존 노트 소비 방식 |
| 운영자 중지 후 어떤 비밀·자료로 새 검증을 계속할 것인가? | 수신 조건·노트·복구 암호문·키 권한의 관계와 자료 경로 | 사용자 백업·전자서명 티켓·독립 원장 조회·기존 암호화 복구 방식 |
| PG 결과가 뒤늦게 바뀌어도 이미 끝난 권리와 남은 금전 의무를 어떻게 검증할 것인가? | 원결제 참조, 실행 시도, 확정/반환 증거, 권리와 금전 상태의 연결 | 멱등성·outbox·saga·기존 원장 간 대사·결제 오케스트레이션 |

이 표는 **조사·설계 후보**다. 알려진 기능을 함께 넣었다는 이유로 차별 구성이 됐다고 하지 않는다. 세 가지를 모두 첫 청구항에 넣을 필요도 없다. 구체적인 입력·메시지·권한·자료 구조가 정해진 뒤 가까운 선행기술과 요소별로 비교한다.

비교 기준은 중앙 서버가 아무 복구 기능도 없는 허술한 시스템이면 안 된다. 서명 티켓·사용자 백업·복제 DB·독립 자료 조회 같은 통상적인 보완을 갖춘 기준선과 비교해야 한다. 그 위에서 어느 사업자의 신뢰·가용성 의존이 사라졌는지, 어떤 추가 정보 공개를 줄였는지, 어떤 오류 조합에서 잘못된 권리 활성화를 막았는지 보여줘야 한다.

효과는 처리량 하나로 제한하지 않는다. 명시한 장애 범위에서의 권리 복구, 독립 검증 성공, 중복 소비 거절, 노출 필드 감소, 증명 생성·검증 지연, 필요한 신뢰 주체가 비교 대상이다. 지연이나 자료 크기가 늘면 함께 기록한다. 아직 수행하지 않은 비교의 숫자를 미리 쓰지 않는다.

박준태 단독출원 전제는 유지하되 이번 보고서의 AI 제안을 인간의 발명 기여로 자동 기재하지 않는다. 실제 선택·수정·문제 해결 과정은 invention log에 날짜와 근거로 남긴다.

**9. 다음 구현을 하나의 완결된 여정으로 묶기**

다음 중심 결과물은 **이미 발행·이전된 관람권을 KIX 서비스 중지 상태에서 복구하고, 필요한 사실만 공개해 권한 있는 다른 운영자에게 한 번 사용하는 실제 실행**이다. 여기에 거래 조건과 배분 근거가 연결돼 있어야 한다.

| 단계 | 구현 내용 | 완료 자료 |
|---|---|---|
| 1 | R02/R01과 증거 요약·식별자 문제 수정, 부분 종결·송신 복구 계약 보충 | 같은 재현 입력에서 새 경로 중복 허용/잘못된 미반영 합계가 사라짐. 상태별 기대 결과 |
| 2 | Sui 권리 프로그램·권한·전송 제한·서명 직렬화 | 소스·컴파일·전이 검사, Python 기준 모형과 공통 입력 벡터 대조 |
| 3 | 실제 체인 발행·리셀·무상 양도 및 확정 영수증 반영 | 거래 digest·성공/실패 effects·응답 유실 후 복구 자료 |
| 4 | KIX 서비스 중지 후 공개 프로필의 독립 검증·소비 | 꺼진 서비스 목록, 대체 키/자료/가스/RPC 경로, 옛 권리 거절 |
| 5 | 비공개 노트의 최소 소비 회로와 신뢰할 검증키 연결 | 실제 proof·Move 검증 결과·변조 입력 거절·공개 필드 목록 |
| 6 | 같은 권리에 거래·취소·배분 증명 연결 | 다른 노트나 다른 거래의 증거로 바꿔 끼우기 거절, 환불 의무와 권리 종료의 대조 |

단계는 개발 의존관계다. 상품별 모든 환불·마케팅 기능을 완성한 뒤에만 체인 연구를 시작하라는 뜻이 아니다. 명시한 합성 정책으로 좁은 여정을 만들면서 실제 상품 계약과 PG 어댑터를 발전시킨다. 공개 프로필은 독립성 검증용이며, 최종 프라이버시 목표의 대체물로 표시하지 않는다.

첫 실행에 포함할 장면은 다음과 같다.

1. 승인된 행사 물량의 권리를 A에게 발행한다.
2. A가 B에게 공식 리셀하거나 별도 분기에서 무상 양도한다. 수락한 조건과 새 권리를 연결한다.
3. B가 독립 복구에 필요한 자료를 확보한다.
4. KIX의 API·조회 DB·호스팅된 로그인/증명/대납 경로를 시험 범위에 따라 중지한다.
5. B가 대체 경로로 현재 권리를 복구하고 새 검표 요청에 응답한다.
6. 권한 있는 다른 검표자가 소비를 확정한다. A의 옛 권리, B의 중복 제시, 취소/재발행된 권리는 거절한다.
7. 금융 측은 지정한 공개 범위 안에서 거래·배분·환불 근거를 확인한다. 개별 관객 원문을 무조건 공유하는 방식에 의존하지 않는다.

이 여정이 실행되면 ‘예매 서비스를 만들고 있음’보다 구체적으로 KIX의 기술적 방향을 설명할 수 있다. 특허 논의도 그때 실제 장치·메시지·증명 관계와 비교 결과를 대상으로 진행할 수 있다.

**10. 재현자료 사용과 변경 기록**

패키지의 `original/`은 첨부 v0.2의 사본이다. 새 `review_v02_probe.py`는 원본 Core를 호출해 본문 R01~R09를 재현한다. 제공된 Harness를 가져오지 않는다. 코드에 있는 assert는 현재의 관찰이 재현되는지 확인하며, 결함이 수정된 버전에서는 일부 assert가 실패하는 것이 정상이다. 이를 새 버전의 제품 수용검사로 복사하지 말고 본문 수정 기준에 맞게 기대값을 바꾼다.

```bash
python -m pip install -r original/requirements.txt
python -m unittest discover -s original -p 'test*.py' -v
python review_v02_probe.py --bundle original --output .local/review
```
