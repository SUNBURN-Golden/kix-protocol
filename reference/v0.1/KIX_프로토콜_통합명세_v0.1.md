# KIX 티켓 권리·거래·정산 프로토콜 통합 명세 v0.1

작성일: 2026-09-11. 상태: 합성 시나리오로 실행·검증한 개발 기준 초안. 이 파일의 정책 선택과 실제 계약 조건을 구분한다.

## 1. 이번 개발의 목적과 결과

예매, 공식 리셀, 발권·검표, 정산, 금융 자료 제공, 동의 기반 마케팅이 같은 공연·티켓·거래를 해석하도록 만든다. 이번 결과물은 이를 위한 데이터 구조, 상태 변경 조건, 실패 처리, 외부 연결 계약 및 Python 참조 구현이다.

**합성 공연에서 A가 10만 원에 구매하고 B에게 12만 원에 재판매한 뒤 입장·배분금 지급, 또는 취소·회수·환불까지 연결했다.** 31개 테스트가 통과했다. 실제 PG 호출·블록체인 거래·은행 자금 이동은 0건이다.

확인한 기존 자산은 다음과 같다.

## 2. 권한과 상태의 기준

최종 운영 구조에서 티켓 권리는 지정한 체인·프로그램의 확정 상태를 따른다. PG는 결제·취소의 원천이며, 자금 원천은 실제 입출금·정산 반영의 근거다. KIX 조정 서비스는 요청·증거·진행상태를 연결한다. 어느 기록도 다른 원천에서 발생하지 않은 사실을 만들어내지 않는다.

| 구성 | 책임 | 책임 밖의 사실 |
|---|---|---|
| 권리 검증 프로그램 | 현재 권리, 허용된 전이, 중복 소비 차단, 정책·위임 검사 | 카드 결제의 실제 성공, 은행 송금, 공연장 문 개방 |
| PG 연결부 | 원결제 및 취소 결과의 인증·정확한 귀속 | 티켓의 현재 소유자와 현장 미사용 여부 |
| 금전 실행·대사 | 원천별 의무·요청·결과·실제 이동과 미확정 잔액 연결 | 증거 없는 지급·회수 완료 |
| 검표 시스템 | 행사 범위 내 제시 검증, 1회 사용, 위임 종료 로그 | 연결이 끊긴 다른 게이트가 실제로 사용하지 않았다는 사실 |
| 조회·정보 제공 | 권한과 목적에 맞는 자료 산출 | 광고 동의 추정, 독자적인 금융 승인 |

참조 구현에서는 위 계약을 평가할 **단일 SQLite 상태기계**를 사용한다. 그 안의 원자적 처리가 PG와 실제 체인의 원자성을 의미하지 않는다. 운영용 구현은 아래 9절의 외부 확정 절차를 별도로 구현해야 한다.

## 3. 공통 식별자와 데이터

식별자는 사업자·환경·체인·프로그램의 범위를 포함한다. 서로 다른 환경의 동일 문자열을 같은 거래로 해석하지 않는다.

| 기록 | 핵심 필드 | 불변성·연결 조건 |
|---|---|---|
| ProtocolDomain | chain/network, package/program, protocolVersion, environment | 테스트와 운영을 분리. 체인별 식별자는 실제 배포 후 부여 |
| Event | eventId, organizerId, status, policyHash, inventory | 발행 권한과 좌석 한도. 이미 판매한 권리의 정책을 조용히 바꾸지 않음 |
| TicketRight | ticketId, eventId, ownerRef, rightsVersion, admissionEpoch, state, lock, delegationSession | 같은 권리의 소비·양도·사용에 공통 버전과 소비 검사를 적용 |
| Trade | tradeId, ticketId, buyerRef, sellerRef, kind, amount, currency, policyHash, termsHash | 거래 조건은 구매자 수락 전에 고정. 금전 상태는 별도 필드 |
| PaymentBinding | provider, environment, merchant, channel, paymentId, externalOrderId, tradeId | 금액이 같다는 이유만으로 연결하지 않음. 한 원결제를 두 거래의 결제 근거로 재사용하지 않음 |
| Allocation | allocationId, tradeId, beneficiaryRef, amount, paid, recovered | 배분 합계는 해당 거래대금과 같아야 함. 이미 지급한 금액의 취소는 회수 의무 생성 |
| ExecutionEffect | effectId, obligationRef, kind, originalPaymentRef, beneficiaryRef, amount, immutableRequest, idempotencyKey | 환불·지급의 단위. 송신 후 같은 본문·같은 키를 유지 |
| SourceObservation | sourceScope, observationId, providerOperationId, observedAt, phase, sourceDigest, provenance | 관찰의 식별자와 PG 거래 ID를 구분. 같은 관찰 ID의 상충 내용은 검토 대상 |
| FundsMovement | sourceScope, movementId, accountOrPoolRef, amount, currency, direction | 결제별로만 중복을 막지 않음. 같은 원천 이동 증거의 다른 의무 재사용 금지 |
| Consent | subjectRef, event/purposeScope, allowed, consentVersion, recordedAt | 구매·양도·입장과 독립. 철회를 다음 발송 직전에 다시 확인 |

현재 코드의 `domain`은 `kix:fixture:lifecycle:0.1`, 원천은 `toss/test/kix-fixture/card`다. 실제 Toss에서 발급받은 자격·가맹점이 아니다. 통화는 KRW, 금액은 원 단위의 양의 정수이며 입력 허용 상한은 합성 모형의 10^12원이다.

`rightsVersion`은 KIX 권리의 논리적 변경 번호다. Sui 객체 메타데이터의 버전이나 PG API 응답 형식의 `version`과 별도로 둔다. Sui 객체에는 자체 ID·소유자·버전·거래 digest가 있으므로 연동 시 그 참조도 따로 저장한다. [Sui 객체 모형](https://docs.sui.io/develop/sui-architecture/object-model)

`admissionEpoch`는 현재 제시·위임이 속한 세대를 나타낸다. 이번 비교 모형은 발행·양도·사용·위임 종료 등에 새 세대를 부여한다. 기존 비공개 노트 모형은 자체 version·epoch 규칙을 가지므로 노드별 필드명을 단순 복사하지 않고 어댑터가 의미를 연결해야 한다.

`operationId`는 한 명령과 그 실행 결과를 고정한다. 같은 ID·같은 actor·같은 본문은 기존 영수증을 반환하며 효과를 추가하지 않는다. ID는 같지만 actor·본문·연산이 달라지면 거절한다. 게이트는 재전달된 성공 영수증을 새 입장 명령으로 사용하지 않고 `admissionId`를 내구 저장해 중복 개방을 막아야 한다. 물리 게이트 구현은 미포함이다.

## 4. 거래 조건의 고정

`termsHash`는 domain, 원천 scope, tradeId, eventId, 거래 종류, ticketId, 당사자, 금액·통화, policyHash, 예상 권리 버전·입장 세대를 포함한다. 결제 완료·정산 완료·환불 잔액처럼 나중에 변하는 운영 필드는 포함하지 않는다. 수신자의 동의가 어떤 조건에 대한 것인지 계속 동일하게 확인하기 위해서다.

정책은 행사 생성 시 복사·해시 처리하며, 현재 API에는 판매된 정책을 변경하는 명령을 제공하지 않는다. 실제 정책 변경은 새 버전과 기존 권리 적용 범위, 당사자 동의 필요 여부를 따로 설계한다.

합성 정책의 정확한 내용은 다음과 같다.

| 항목 | 시험값 |
|---|---|
| 최초 가격 | 100,000원 |
| 허용 리셀 가격 상한 | 150,000원 |
| 최초 판매 배분 | 주최자 95%, 플랫폼 5% |
| 리셀 배분 | 판매자 95%, 주최자 2%, 플랫폼 3% |
| 원 미만 계산 | 비율 수취액은 내림. 최초 판매는 주최자, 리셀은 판매자가 잔여액 수취 |
| 환불 방식 | `FULL_CHAIN_UNWIND_FIXTURE`: 원거래마다 원구매자·원결제로 환원 |
| 비용 | 실제 PG 비용·세금·환불 수수료를 0원으로 가정 |
| 배분금 지급 시기 | 행사 완료 후. 확인된 자금 범위에서 지급 |
| 자금 사용 범위 | 거래별 격리. 같은 행사라도 다른 원결제의 자금으로 보충하지 않음 |

이 값은 계산 검증을 위한 입력이다. 실제 리셀 허용·가격·배분·환불·개인 재판매자 지급은 주최자·이용자·PG의 적용 가능한 계약을 반영해야 한다. 이번 개발은 이 정책을 KIX의 최종 사업 조건으로 확정하지 않는다.

## 5. 권리·거래 상태 전이

### 5.1 티켓

| 전이 | 조건 | 확정되는 변경 |
|---|---|---|
| AVAILABLE → ACTIVE | 좌석 배정 잠금, 구매자 조건 수락, 해당 거래 결제 확인, 행사 OPEN | 소유자 지정, 권리 버전·입장 세대 증가 |
| ACTIVE → ACTIVE | 현 소유자의 양도 의사, 지정 구매자 수락, 허용 가격, 결제 확인, 동일 잠금·현재 버전 | 새 소유자 지정, 기존 제시 무효화 |
| ACTIVE → CONSUMED | 행사 OPEN, 잠금 없음, 현재 보유자의 버전·세대에 맞는 제시 | 1회 사용, 이후 양도·입장 차단 |
| ACTIVE → DELEGATED | 보유자 요청, 잠금 없음, 행사 OPEN | 배타적 검표 session과 새 세대 부여 |
| DELEGATED → ACTIVE 또는 CONSUMED | 정확히 같은 session·세대의 최종 종료·사용 결과 | 미사용이면 복귀, 사용이면 종결 |
| ACTIVE → VOID | 미사용·미위임·미거래 중인 보유자의 환불 요청 | 권리 무효화 및 환불 계획. 돈이 지급됐다는 의미 없음 |
| 행사 취소 → VOID | 행사 취소 권한 확인 | 일반 권리 무효화, 신규 거래·입장 차단, 금전 환원 계획 |
| 위임 중 행사 취소 → CANCEL_PENDING_CLOSE | 행사 취소가 확정됐으나 현장 위임 결과 미확인 | 현장 결과를 미사용으로 추정하지 않음. 돈의 환불과 현장 종료는 따로 추적 |

위임 만료·네트워크 단절·서버 타임아웃만으로 ACTIVE 상태로 되돌리는 명령은 없다. 최종 로그에는 실제 구현 시 session, epoch, controller, 최종 순번·로그 digest, used 결과와 서명이 필요하다. 현재 코어의 종료 입력은 합성 최종 로그를 가정하며, 서명 연결은 기존 권리 모형에서 별도 검사한다.

### 5.2 거래

거래 생성은 해당 티켓을 잠근다. 최초 구매는 구매자가 직접 생성하므로 수락 상태로 시작한다. 재판매는 현 소유자가 지정 구매자에게 제안하며 구매자의 별도 `termsHash` 수락이 필요하다. 실제 결제 연동 전에 이 잠금이 권리 기준 원장에서도 유효하게 확정돼야 한다.

`PREPARED → COMMITTED`에는 결제 확인과 현재 잠금·권리 검사가 모두 필요하다. `PREPARED → VOID`는 거래 중단이다. 결제가 이미 확인됐다면 환불 의무를 만들고, 이후 늦게 결제가 확인돼도 환불 의무를 만든다. VOID 거래에서 티켓을 발행하거나 소유권을 이전하지 않는다.

행사 완료 때 아직 끝나지 않은 PREPARED 거래는 중단한다. 그 뒤 결제 관찰이 도착하면 미이행 대금으로 환불한다. 행사 취소는 이미 COMMITTED된 거래 기록을 지우지 않고 별도의 `reversalRequested`, `reversalPlanned`, `refundDue`, `refunded`를 갱신한다.

### 5.3 경합

| 먼저 확정된 일 | 나중 요청의 처리 |
|---|---|
| 재판매 준비·잠금 | 기존 QR 입장과 두 번째 리셀 준비 거절 |
| 입장 | 후속 리셀·자발적 티켓 환불 거절 |
| 양도 | 이전 보유자·버전·세대의 제시 거절 |
| 티켓 환불에 따른 무효화 | 뒤늦은 입장·양도 거절 |
| 행사 취소 | 이후 발권·이전·일반 입장 거절. 이미 생긴 결제·자금 이동은 별도 대사 |

테스트는 SQLite 직렬화와 별도 연결 두 개의 경쟁으로 이 조건을 확인했다. 실제 퍼블릭 체인의 합의·최종성·재구성·대규모 경합은 검증하지 않았다.

## 6. 금전 원장과 실제 이동

결제 승인, PG가 보유한 지급 의무, 실제 입금, 배분금, 환불 의무, 회수 의무를 각각 유지한다. 토스의 `DONE`, 취소 기록, `balanceAmount` 등은 서로 다른 정보를 제공한다. 승인 또는 취소 관찰을 은행 자금 반영으로 자동 변환하지 않는다. [토스 코어 API](https://docs.tosspayments.com/reference)

원장의 분개는 차변 양수·대변 음수로 표현한다. 모든 분개의 차대 합계는 0이고, 보조 잔액을 분개에서 다시 계산한다. 이것은 프로토콜 내부 대조 원장이며 회사의 법정 회계처리·매출 인식 기준을 확정한 것이 아니다.

| 사건 | 차변 | 대변 |
|---|---|---|
| 결제 성공 확인 | PG 수취채권 | 구매자 대금 임시 의무 |
| 권리 발행·이전 확정 | 구매자 대금 임시 의무 | 수취인별 배분 의무 |
| 실제 입금 관찰 | 해당 거래의 확인 자금 | PG 수취채권 |
| 미지급 배분금 취소 | 기존 배분 의무 | 원구매자 환불 의무 |
| 지급한 배분금 취소 | 해당 수취인에 대한 회수채권 | 원구매자 환불 의무 |
| 실제 외부 출금 관찰 | 결과 대사 중 금액 | 확인 자금 |
| 결과와 출금의 귀속 일치 | 해당 지급·환불 의무 | 결과 대사 중 금액 |
| 실제 수취인 회수 관찰 | 해당 거래의 확인 자금 | 수취인 회수채권 |

자금 출금 증거가 결과 확인보다 먼저 와도 확인 자금은 즉시 줄어든다. 다만 지급·환불 완료를 선언하지 않고 ‘결과 대사 중’ 자산과 미완료 의무를 유지한다. 결과 확인이 먼저 오면 실제 출금 증거가 올 때까지 자금 예약을 유지한다.

### 6.1 예제 산술

| 거래 | 구매자 지급 | 판매자 배분 | 주최자 배분 | 플랫폼 배분 |
|---|---:|---:|---:|---:|
| 최초 구매 A | 100,000 | 0 | 95,000 | 5,000 |
| 리셀 구매 B | 120,000 | A에게 114,000 | 2,400 | 3,600 |
| 합계 | 220,000 | 114,000 | 97,400 | 8,600 |

거래총액 22만 원은 주최자 매출 또는 수익 22만 원을 뜻하지 않는다. 조회 결과는 최초 판매 총액, 리셀 총액, 주최자 배분·지급·미지급·회수 예정액을 따로 제공한다.

배분 전 취소하면 최초 결제의 10만 원은 A에게, 리셀 결제의 12만 원은 B에게 환불한다. A에게 예정됐던 114,000원은 지급하지 않는다. 모든 배분금 지급 후 취소하면 A 114,000원·주최자 97,400원·플랫폼 8,600원의 회수채권과 A 100,000원·B 120,000원의 환불 의무가 남는다. 실제 회수가 확인돼야 가용 자금이 늘어난다.

실제 소비자 환불이 회수 완료까지 기다려야 한다는 법률·약관 결론은 아니다. 회수 이전 환불 의무를 이행해야 한다면 별도 조달자금·지급보증·PG 상계 등 계약상 경로가 필요하다. 이번 모형은 그런 재원을 임의로 생성하지 않는다. 기존 v1.6의 PG 후속 정산 상계·브리지 가지는 별도 모듈로 유지하고, 이번 `pool`을 그 기능의 구현으로 해석하지 않는다.

## 7. 외부 지급·환불의 실패와 복구

| 단계 | 저장되는 것 | 재시작 후 규칙 |
|---|---|---|
| PREPARED | 고정 요청, 멱등키, 의무 예약, 확인 자금 예약 | 실제 송신 의도가 기록되기 전에는 중단·해제 가능 |
| OUTCOME_UNKNOWN | 송신 의도 확정. 실제 네트워크 호출 여부는 불명일 수 있음 | 원천 조회 우선. 새 키로 같은 돈을 다시 요청하지 않음 |
| 결과 성공 관찰 | 원천 범위·원거래·수취인·금액이 일치한 결과 | 실제 자금 이동과 연결 전까지 완료 금액 증가 금지 |
| 자금 이동 관찰 | 원천에서 실제 움직인 금액 | 가용 자금 즉시 반영, 결과는 계속 대사 |
| DONE | 결과와 자금 이동이 같은 실행 의무에 연결됨 | 중복 증거와 오래된 알림으로 잔액을 다시 바꾸지 않음 |
| 상충·실패 관찰 | 검토 표시와 원천 증거 | 기존 성공한 돈을 삭제하지 않음. 종료·늦은 실행 차단 확인 없이 예약 해제 금지 |

예약·실행 의도·명령 영수증은 동일 SQLite 트랜잭션에서 저장된다. 저장 도중 실패 시 모두 롤백되며, 커밋 뒤 응답만 유실되면 DB를 다시 열고 같은 명령으로 기존 영수증을 받는다. 이 보장 범위는 SQLite 트랜잭션이다. [SQLite 트랜잭션](https://www.sqlite.org/lang_transaction.html)

현재 `send_effect`는 **미송신 요청 자료를 반환하는 합성 동작**이다. 실제 PG 재시도에는 어댑터별 멱등 보장 기간, 동일 키 조회·재실행 조건, 송신 작업자 fencing, 성공·실패의 최종성 조건을 추가해야 한다. 함수 호출이 성공했다는 이유로 외부 재시도가 허용되는 것은 아니다.

확정 실패 후 새 실행, 사후 자금 반환, 한 외부 실행 내부의 부분 지급, 귀속 불명 취소·입출금은 별도 구현 과제로 남긴다. 현재 부분 환불 검사는 하나의 의무를 4만 원·6만 원의 서로 다른 실행으로 나누는 경우다. 10만 원 단일 송신에서 PG가 4만 원만 처리한 상황을 구현한 것이 아니다.

이미 송신한 배분금의 결과가 미확정일 때 공연이 취소되면, 해당 거래의 환원 계획을 대기시킨다. 결과가 확정되어 실제 지급됐다면 회수채권을 만들고, 실제 송신 전인 의도라면 `abort_effect`로 중단한 후 미지급 배분을 취소한다. 다른 거래의 독립 처리는 계속할 수 있지만 이번 SQLite 전역 쓰기 잠금의 처리성능은 별도 문제다.

## 9. 외부 연결 규격

### 9.1 명령·영수증

명령 봉투는 `protocolDomain, operationId, actorContext, action, body`를 가진다. 현재 Python 함수는 `operationId, actor, action, body`를 인수로 받고 `body.domain`을 검사한다. `protocol_contract.json`은 이 로컬 호출 형식과 필수 본문 항목을 기록한다. HTTP 서버·OpenAPI 서비스는 아직 없다.

실제 `actorContext`는 인증·서명 검증 결과여야 한다. 요청자가 보낸 문자열 `actor="pg-adapter"`를 권한으로 믿어서는 안 된다. 현재 문자열은 시험에서 신뢰 경계를 명시하는 표식이다.

영수증에는 domain, operationId, 순번, 연산 종류, 결과를 넣는다. 외부 소비자는 자신의 처리 cursor와 수신 ID를 저장한다. 소비자 처리와 cursor 갱신을 같은 트랜잭션에서 수행해 중복 전달을 견딘다. 이 패키지는 영수증 목록을 저장하지만 외부 메시지 브로커·consumer 구현은 포함하지 않는다.

### 9.2 발권·리셀 연결

외부 예매처 티켓은 `(issuerNamespace, externalEventId, externalTicketId)`와 KIX 권리의 1:1 대응을 확인한 뒤 다룬다. 기존 티켓 캡처·양도 게시글만으로 현재 권리 발행 권한을 만들지 않는다. 기존 발권사가 옛 입장 수단을 무효화하고 새 보유자를 인정하는 경로가 필요하다.

외부 재고 단위에는 좌석·등급·수량·유효 범위·예약 기한·최종 발권 상태가 있어야 한다. 예매 대기열 접수증은 좌석 확보나 결제·발권 완료 영수증과 다르다. 기존 v0.7의 배정 시뮬레이션 종료점을 이 프로토콜의 판매 완료로 바꾸어 보고하지 않는다.

### 9.3 권리 프로그램 연결

실제 체인 구현에서 필요한 흐름은 다음이다.

1. 현재 권리·정책에 맞는 거래 준비와 잠금 또는 배타적 소비권을 확정한다.
2. 고정된 조건·거래 ID로 PG 결제를 요청하고 정확한 결과를 확인한다.
3. 결제 증거의 발급 주체·범위·금액·연결·재사용 여부를 검증해 권리 전이를 제출한다.
4. 제출 식별자와 체인 결과를 대조한다. 응답 유실은 실패 확정이 아니다.
5. 확정 영수증을 조회 원장에 반영하고 배분 의무를 기록한다.
6. 미이행·취소 경로는 이미 확정된 권리를 존중한다. 전이 성공 여부가 불명확하면 새 발행·새 환불·잠금 해제를 임의로 실행하지 않는다.

체인 영수증은 chain/network, package/program 및 검증기 버전, 거래 digest·확정 참조, operationId·tradeId, 입력 권리 또는 소비 표식, 출력 권리, policyHash, termsHash, 결과를 결합해야 한다. 단순 JSON에 `finalized=true`를 붙이는 것으로 원천 인증을 대신하지 않는다.

이번 코어의 `commit_trade`는 위 흐름 중 권리·배분 확정의 논리적 결과를 단일 트랜잭션으로 평가한다. 실제 외부 체인의 제출·미확정·실패·대사 상태는 후속 어댑터에서 구현해야 한다. Sui 실사용 선택은 유지 가능한 후보이며, Sui·다른 체인 사이의 이동을 이번 구현이 지원하지 않는다.

### 9.4 PG 연결

`tradeId`를 원주문 연결로, `effectId`를 개별 지급·환불 실행 연결로 둔다. `paymentId`는 확인된 원결제와 결합한다. 원천 namespace는 provider·environment·merchant·channel로 제한한다.

토스 취소 대사 v0.1과의 계약 검사에서는 내부 환불 의도와 기존 요청 생성기를 연결했다. 생성된 요청의 멱등키를 통합 코어가 저장한 키로 통일했다. `[TIXREF:…]` 취소 사유 표기는 KIX의 합성 연결 규칙이며 PG가 보장하는 전용 귀속 필드가 아니다. 원천 응답·요청 로그에 기반한 정확한 귀속이 가능한지는 실제 계약·샘플로 검증한다.

테스트는 합성 토스 응답에서 `MATCHED_AS_RECORDED`, `PG_CANCELLED_AS_RECORDED`를 얻었다. **이는 입력 자료와 일치한다는 뜻이며 인증된 외부 취소나 실제 환불 완료가 아니다.** 그 결과만으로 `refunded`를 증가시키지 않는 것도 검사했다.

실제 adapter에는 원자료를 먼저 내구 저장하는 inbox가 필요하다. 귀속 불명·중복 자금 이동·금액 불일치 입력도 삭제하지 않고 검토 큐로 보존해야 한다. 현재 코어는 검증 가능한 합성 입력만 받아들이며, 거절한 입력을 별도 원자료 저장소에 보관하는 기능은 미구현이다.

| 공개 검증자 | 필요한 상태 commitment·소비 표식·정책 참조·검증 결과 | 평문 성명·연락처·IP·결제수단 원문 |

`view(...,"finance")`는 최초 판매와 리셀 총액, 주최자 배분·지급·미지급·회수 필요액, 미완료 환불 및 아직 계산 대기 중인 환불 계획 수를 구분한다. 이는 금융상품·신용평가·담보권을 생성하지 않는다.

`view(...,"marketing")`는 현재 동의가 있는 대상만 반환한다. 사용 중인 마케팅 사업자에 정보 제공 권한과 발송 근거가 확보됐다는 의미는 아니다. 실제 발송은 별도 서비스에서 동의·위탁·대상·목적·철회를 확인해야 한다. 이 패키지는 메시지를 발송하지 않는다.

SQLite에는 비교 검증을 위한 평문 합성 참조가 들어 있다. 공개 원장용 개인정보 보호 구현이 아니다. 기존 노트 모형과의 테스트는 수신 확인이 금융 조건에 결합되는지를 확인할 뿐, 새로운 코어의 모든 기록이 ZK로 보호된다는 뜻이 아니다. 해시만으로 익명성을 보장한다고 설명하지 않는다.

## 11. 실행 결과와 실무적인 한계

| 검증 묶음 | 결과 |
|---|---|
| 정상 구매→리셀→입장→배분 | 보유자 B, 주최자 97,400원·플랫폼 8,600원·A 114,000원 지급 기록. 잔여 분개 잔액 0 |
| 지급 전 취소·환불 | A 100,000원·B 120,000원 원거래 환원, 권리 무효화 |
| 지급 후 취소 | 220,000원 회수채권과 220,000원 환불 의무를 보존. 무재원 환불 거절 |
| 회수 후 환불 | 회수 관찰 뒤 원결제별 환불을 완료하고 잔액 0 |
| 늦은 결제 | 거래 중단·행사 완료 후 수신해도 발권하지 않고 환불 의무 생성 |
| 중복·상충 증거 | 결제 중복 반영 차단, 자금 증거 재사용 거절, 뒤늦은 실패로 완료 자금 삭제하지 않음 |
| 응답 유실·재시작 | 기존 영수증 재조회, 본문·actor가 다른 동일 ID 거절 |
| 동시 좌석 요청 | 두 독립 연결 중 하나만 예약 |
| 위임과 취소 | 종료 결과 없이 미사용 복귀 금지, 취소 후 미확인 현장 결과 보존 |
| 정보 제공 | 마케팅 동의 철회 반영, 주최자 배분과 리셀 총액 분리 |
| 기존 모형 연결 | 취소 대사 요청·귀속 계약, 금융 조건이 결합된 권리 수신 확인 검사 |

미구현 사항은 다음 단계의 구체적인 개발 범위다.

1. 실제 체인에서의 거래 준비·권리 전이·종료·결과 대사와 검표 연동.
2. PG 원자료 inbox, 인증·서명 검증, 실제 재시도·송신 종료 보장, 실제 순입금·수수료·상계 명세.
3. 한 외부 작업 내부의 부분 성공, 확정 실패 뒤 새 시도, 지급 후 반환, 차지백·미귀속 외부 취소.
4. 오프라인 검표기의 내구 로그·복원 방지·1회 문 개방 및 다중 게이트 권한 배분.
5. 거래별 저장 구조, 병렬 처리, 사용자별 인증, 범위별 접근 통제·보존·감사와 운영 배포.
6. 실제 암호학적 증명·원장 독립성·복구 자료 가용성, ZK의 입력·비용·메타데이터 노출 검증.

개발·시뮬레이션은 이 과제들을 순차적으로 구체화하며 계속할 수 있다. 이번 결과는 과거 연구의 특허 판단을 상향하는 근거나 실서비스 출시 승인이 아니다.

## 12. 바로 이어질 구현 단위

첫 연결 구현은 **현재 코어의 명령·결과 계약을 Sui 권리 프로그램의 준비·전이·취소 영수증에 대응시키는 어댑터**로 잡는다. 동일한 합성 거래 입력을 기준 코어와 체인 구현에 넣어 허용·거절 및 최종 권리가 같은지 대조한다. PG·체인 중 하나의 결과가 불명확할 때 새 거래를 실행하지 않는 기준도 이 단계에 넣는다.

그다음 PG 취소 대사 모형을 원자료 inbox·실행 outbox에 연결하고, 실제 원천 샘플이 확보되는 대로 합성 가정을 교체한다. 금융·마케팅은 이 공통 기록을 조회하는 서비스로 확장한다. 자체 금융 상품과 광고 발송을 권리 상태기계 안에 넣지는 않는다.
