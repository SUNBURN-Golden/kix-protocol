# KIX v0.3-rc1 체인·비공개 현재성 구현 계약

2026-09-11. 이 문서는 포함한 **미컴파일 소스**의 의도와 검증 조건을 정의한다. 구현이 정확하거나 실제 체인에서 성공했다는 보고가 아니다.

## 1. 권리 정본과 권한

Python 모형의 `operator` 문자열을 Move 권한으로 옮기지 않았다. Sui 후보 코드는 `Show`, `Ticket`, `IssuerCap`, `PaymentEvidence`로 나눈다. 보유자는 실제 거래 서명자와 비교하며, 유상 이전은 수신자의 수락과 공연·Ticket·버전·가격·약정에 묶인 결제 증거를 요구한다. 무상 이전에는 결제 증거를 요구하지 않는다.

`Ticket`과 `IssuerCap`에는 `store`를 주지 않았다. 모듈 밖의 일반 객체 전송으로 이 권리 전이 검사를 우회하지 못하게 하려는 선택이다. 이는 Sui의 모듈 내부 `transfer`와 외부 `public_transfer` 능력 제한을 이용한다. [Sui transfer 문서](https://docs.sui.io/references/framework/sui_sui/transfer)

공연별 검표자와 결제 증거 발급자를 생성 시 지정한다. 검표는 보유자의 유효한 검표 요청과 해당 검표자의 서명이 필요하다. 공개 리셀 배분은 총액 기준 주최자·플랫폼 비율을 각각 내림하고 나머지를 판매자에게 배정하는 제한 정책이다. 이 이벤트는 배분 의무의 근거이며 현금 지급 증거가 아니다. 결제 참조 중복 검사는 공연 내부 범위다. 다수 가맹점·행사에 걸친 원천 결제 ID 유일성은 실제 어댑터의 추가 계약이 필요하다.

로컬 실행 스크립트는 패키지의 UpgradeCap을 소모하여 불변으로 만들도록 작성했다. **로컬 실험 전용**이며 네트워크 주소가 localhost가 아니면 중단한다. 운영 배포나 메인넷 변경은 수행하지 않았다.

## 2. 운영자 의존 제거 시험

| 의존성 | 후보 코드가 사용하는 대체 경로 | 남는 조건 |
|---|---|---|
| KIX 로그인/키 관리 | 사용자 Ed25519 키 및 암호화 백업 | 백업과 암호를 미리 확보해야 함 |
| salt·로그인 증명 서버 | 이 제한 프로파일에는 zkLogin을 사용하지 않음 | zkLogin 사용자 이전은 별도 과제 |
| 가스 대납 | 보유자 또는 별도 검표자의 가스 코인 | 네트워크와 가스가 필요함 |
| KIX 노트 저장 | 사용자가 가진 AES-GCM 백업 | 미리 보관한 노트·회로 자료 필요 |
| KIX 증명 서버 | 로컬 WASM·zkey와 snarkjs | 도구 성능과 자료 보존을 검증해야 함 |
| KIX RPC·조회 DB | 직접 지정한 Sui RPC, BCS 객체 읽기 | RPC에 대한 신뢰는 남음 |
| KIX 거래 확정자 | 보유자/수신자/검표자의 체인 서명과 Move 조건 | 발행자·검표자 권한 지정은 남음 |

`IndependentClient.submit`은 서명 바이트와 digest를 먼저 보존한다. 응답 유실은 `OUTCOME_UNKNOWN`으로 남긴다. 조회 실패만으로 새 거래를 만들지 않으며, 재제출은 같은 서명 바이트를 사용한다. SDK의 실행 완료와 실행 성공은 별도로 다루고, 조회 반영을 기다린다. [Sui SDK 실행 API](https://sdk.mystenlabs.com/sui/clients/executing)

직접 선택한 RPC가 KIX 소유가 아니라는 운영 사실, 해당 RPC의 최신성·정직성, 서로 다른 사업자의 장애 독립성은 별도의 배치 검증 대상이다. 이 후보 클라이언트에는 검증자 서명/체크포인트 검증기가 없다. 따라서 ‘KIX 조정 프로세스 독립’과 ‘RPC까지 신뢰하지 않는 검증’을 구분한다.

## 3. 비공개 현재성의 제한된 구현

공개 A→B 이전 뒤 **같은 Ticket**에 `shield`를 호출한다. 보유자 서명, 현재 권리 버전, 노트 생성 증명으로 정확한 재고·권리 세대의 commitment를 등록하고 Ticket을 `SHIELDED`로 바꾼다. 이후 공개 이전·환불·검표는 `ACTIVE` 조건을 만족하지 못한다. 비공개 검표는 동일 공연의 노트 목록·세대 목록·소비 집합을 사용한다.

여기서는 H를 BN254 Poseidon이라고 쓰며, 실제 Circom/Sui 파라미터·직렬화 일치는 아직 실행으로 확인하지 못했다.

- `C = H(secret, slot, generation, domain, 1)`
- `N = H(secret, slot, generation, domain, 2)`
- `R_leaf = H(slot, current_generation, domain, 3)`
- `context = H(gate_low128, gate_high128, challenge, expires_ms, 1)`

`mint.circom`은 공개 `C, slot, generation, domain`에 대응하는 비공개 secret의 지식을 검증한다. 따라서 소유자가 다른 재고의 commitment를 마음대로 등록하는 경로를 막으려 한다.

`spend.circom`의 공개 입력은 다음 **6개, 이 순서**다.

| 위치 | 공개 입력 | 확인 조건 |
|---|---|---|
| 0 | noteRoot | 등록된 commitment의 포함 증명 |
| 1 | revocationRoot | 같은 slot·generation이 지금도 유효한 세대라는 증명 |
| 2 | nullifier | 같은 노트의 모든 검표에 공통인 소비 표식 |
| 3 | context | 검표자·요청·만료시각에 증명을 결합 |
| 4 | domain | 공연 범위 결합 |
| 5 | action = 1 | 검표 전용 명제; 이전·환불 승인으로 사용할 수 없음 |

secret, slot, generation, 두 Merkle 경로는 공개 입력에 넣지 않는다. 회로는 두 경로에서 같은 slot·generation을 사용하고, slot을 4비트로 제한한다. 검표자 주소 두 조각과 시간도 비트 범위를 제한한다. secret이 0인 증명을 허용하지 않는다.

Move는 제출자가 가져온 과거 루트를 그대로 믿지 않고 현재 `Show` 상태에서 noteRoot와 revocationRoot를 다시 계산한다. 폐기 시 발행자는 해당 slot의 generation을 올리고, 공연 취소 시 전체 검표를 막는다. 소비 표식은 검표자·challenge가 바뀌어도 동일하며 이미 기록된 표식은 다시 받지 않는다. 단순한 포함 증명만으로 현재 권리를 주장하지 못하도록 구성했다.

## 4. 검증키와 복구 자료

`Verifier`는 불변 객체로 만들어 mint/spend 검증키와 회로 자료 manifest hash를 가진다. `Show` 생성 시 해당 객체 ID를 한 번 지정하고, 증명 호출에는 임의의 검증키 바이트를 받지 않는다. 독립 클라이언트도 예상한 객체 ID·manifest·키 바이트를 확인하도록 작성했다. 설치자가 올바른 회로와 키를 검토해 고정했다는 신뢰가 필요하며, 임의 키를 불변으로 만들었다는 사실만으로 회로가 올바르게 되는 것은 아니다.

Sui Groth16 API는 BN254/BLS12-381을 지원하고 공개 입력 개수에 제한이 있으며, 앱이 예상 검증키를 고정하거나 확인해야 한다. 이 후보는 BN254와 4개/6개 공개 입력을 사용한다. `encoding.mjs`는 snarkjs 출력을 Arkworks 압축 형식으로 바꾸는 후보 코드이며 실제 Sui 수락으로 호환성을 확인해야 한다. [Sui Groth16 문서](https://docs.sui.io/develop/cryptography/groth16)

`setup-zk.mjs`가 만드는 키는 단일 주체 로컬 시험용이다. 현재 패키지에 생성된 `.wasm`, `.zkey`, 실제 VK나 proof는 없다. 생성 전 placeholder를 실제 증명으로 넣지 않았다. 사용자 백업에는 지갑 키·노트 secret·slot·generation·공연·패키지·verifier·manifest 참조를 암호화해 넣고, PK/WASM은 별도 보관한다.

## 5. 공개 범위

| 관찰자 | 이 제한 프로파일에서 보이는 것 | 감추려는 것/한계 |
|---|---|---|
| 공개 체인 | 공개 권리 ID·주소·이전·shield 시점·노트 commitment·폐기 대상·검표자·소비 표식 | private 검표 호출에 slot/노트 경로는 없음. 시점·IP·집합 크기로 추정 가능 |
| 검표자 | 공연, challenge, nullifier, 현재 루트, 유효한 증명 | 노트 secret·구매 사슬을 요청할 필요 없음. 실제 입장자 관찰은 별개 |
| 주최자 | 공개 발행/이전 자료, 폐기 권한과 대상 | 발행/전환 기록을 이미 알고 있으므로 완전 익명이라고 할 수 없음 |
| 금융 제공자 | 기존 Python 금융 조회 또는 공개 배분 이벤트 | 금융 집계 ZK는 아직 구현하지 않음 |

16개 슬롯은 비용 측정을 시작하기 위한 제한이다. 한 노트만 발행된 실험은 사실상 구별할 다른 대상이 없으므로 익명성을 입증하지 못한다. 비공개 모드에 진입한 좌석은 다시 팔지 않는다. 개별 소비 여부를 공개 Ticket에 되기록하지 않으므로 ‘사용했는지 불명확한 재고를 재판매하지 않는다’는 제한을 유지한다.

비공개 리셀·환불·재발행·비밀 키 교체에는 현재 노트 소비와 새 노트 발행의 결합, 권리 세대 유지/폐기 조건, 수신자만 제어할 수 있는 새 비밀, 환불 경로 증거가 더 필요하다. 이번 검표 회로를 이 동작에 재사용하면 안 된다.

## 6. 기존 방식과의 비교

아래 선택은 설계 판단이며 성능 우위나 특허성 판단이 아니다.

| 비교 방식 | 활용할 수 있는 부분 | KIX에서 별도로 필요한 것 |
|---|---|---|
| 서명 티켓 + 사용자 백업 + 복제 DB | 서명 검증·복구·대체 운영자 조회 | 최신 양도/폐기/소비에 대한 공통 결정과 개인정보 공개 범위 |
| 익명 그룹 포함 증명 + 범위별 nullifier | 신원을 숨긴 포함 증명과 중복 사용 억제 | 티켓의 개별 폐기·세대 변경·현재성 |
| 노트 commitment tree + nullifier set | 과거 발행과 소비를 분리해 관리 | 주최자의 강제 취소/사용 불명확 재고 정책 |
| 공개 폐기 목록 | 폐기 정보 전달과 독립 재구축 | 공개 식별자 연결을 줄이는 비공개 현재성 증명 |
| 동적 accumulator | 집합 포함/비포함 증명의 비교 후보 | 증인 갱신·삭제 권한·암호학 가정·Sui 검증 비용의 별도 조사와 구현 |
| 이번 두 Merkle 루트 + nullifier | 공개 자료만으로 두 경로 재구축, 비밀을 모르는 발행자의 세대 폐기 | 아직 검표만 지원하며 실제 비용/보안/직렬화 미검증 |

Semaphore는 그룹 포함 증명, 범위에 결합된 nullifier, 메시지 결합을 구분한다. 그 자체로 티켓의 개별 취소 정책을 제공한다고 해석하지 않는다. [Semaphore 회로 문서](https://docs.semaphore.pse.dev/technical-reference/circuits)

Zcash는 note commitment tree와 nullifier set을 구분하고 이미 존재하는 소비 표식의 중복을 거절한다. 이번 비교는 이 원리를 참고한 것이며 Zcash의 결제 프로토콜·보안 증명을 KIX가 상속한다는 뜻이 아니다. [Zcash 프로토콜 명세](https://zips.z.cash/protocol/protocol.pdf)

accumulator·익명 자격증명에 대한 체계적 문헌/선행기술 조사는 아직 끝내지 않았다. ‘현재성’, ‘동일 권리의 비공개 이전’, ‘운영자 독립성’의 결합을 새로운 발명으로 인정받았다고 주장하지 않는다.

## 7. 다음 완료 판정

1. 실제 Sui 버전을 고정하고 Move 빌드·권한 반례 검사를 통과한다.
2. 공개 여정에서 A→B 이전과 별도 프로세스 복구·검표의 실제 digest/효과를 보존한다.
3. 회로 컴파일·증명 생성·로컬 검증·Sui 직렬화 검증을 모두 실행한다. 다른 키, 다른 문맥, 폐기 전 증명, 재사용을 실제 체인에서 거절해야 한다.
4. RPC/인덱서까지 다른 경로로 바꿔 복구하고, 증인 갱신·보관과 가스 경로를 확인한다.
5. 같은 권리에서 유상 리셀·환불·배분 근거와 Python/PG 브리지를 실제로 연결한다.

현재 완료한 것은 기준 모형의 반례 수정과 위 실행을 위한 후보 소스 작성이다. **Sui 이전 완료·ZK 검증 완료·운영자 독립성 입증은 아직 완료 판정할 수 없다.**
