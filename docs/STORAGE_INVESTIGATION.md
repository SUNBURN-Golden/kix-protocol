# 저장 기록 유실 조사와 지급 판단 차단

기준: PR #2의 `8e69bd7`. 2026-09-14 후속 작업.

**과거 저장 유실의 근본 원인은 아직 밝혀지지 않았다.** 이번 변경은 원인 수정이나 자동 복구 완료가 아니다. 유실 전후 기록을 수집하는 재현 도구와, 확인한 상태가 달라졌을 때 로컬 유상 시험을 중단하는 방어다. 기존 Python 3.12 / SQLite 3.45.1 유상 CLI 제한을 유지한다.

## 조사 결과

- 기존 Python 검사 96개는 Python 3.12.14 / SQLite 3.53.1과 Python 3.12.3 / SQLite 3.45.1에서 모두 통과했다.
- KIX를 제외한 두 DB 쓰기와 Node 자식 실행, 연결 유지/닫기 비교에서는 유실을 재현하지 못했다. Node 부모가 Python 작업자를 60회 재시작하는 비교도 두 환경에서 통과했다. 이것은 과거 사고를 부정하는 결과가 아니다.
- `probe_paid_storage.py`는 실제 PaidCoordinator의 SQLite 코드와 자식 질의 경계를 사용한다. Node → 새 Python → Node 구조로 리셀 준비·결제·전송·취소·늦은 지급을 실행한다. **체인 응답은 명시적으로 합성하며 돈은 모의 제공자**다. 실제 Sui 여정의 대체물이 아니다.
- 기준 코드의 축소 실험은 두 환경에서 각각 3회 거래 주기, 66개 명령을 통과했다. 수정 후 같은 도구의 결과와 소스 해시는 `validation/2026-09-14-storage/`에 보존한다.
- 과거 손상 DB/WAL 원본은 이번 작업 환경에 없었다. 보존된 사고 JSON과 코드로 조사했다. SQLite 자체 결함, 파일시스템 결함, 자식 프로세스 결함 중 하나로 원인을 단정하지 않는다.

## 명시적 장애 주입의 결과

`reproduce_storage_rollback.py`는 다음 순서를 의도적으로 만든다.

1. 114,000원 지급을 준비하고 전송 전 장부를 보존한다.
2. 전송 허가와 모의 제공자 처리를 저장한 뒤 응답을 잃는다.
3. 제공자 기록과 최신 확인 영수증은 유지하고, projection DB만 1번 상태로 되돌린다.
4. 취소를 시도한다.

방어를 거치지 않은 기존 Core 경로에서는 `integrity_check=ok`이면서 `sent=False`가 되고, 취소가 지급을 `ABORTED`로 분류해 환원 계획을 확정한다. 새 CLI 영수증 검사는 **취소 명령 실행 전** `STORAGE_RECOVERY_REQUIRED:ACKNOWLEDGED_STATE_CHANGED`로 거절한다. 제공자에 추가 지급을 보내지 않는다.

이것은 **유실이 지급 판단에 미치는 결과의 재현**이다. 이전 런타임에서 자연 발생한 유실의 최소 원인 재현에 성공한 것으로 기록하지 않는다.

## 추가한 방어

| 경계 | 동작 |
|---|---|
| CLI 시작 | 파일 잠금으로 한 명령만 실행한다. 기존 DB를 열어 변경하기 전에 읽기 전용 SQL로 마지막 영수증의 상태와 대조한다. |
| 명령 실행 전 | 원 요청의 해시와 이전 영수증 해시를 별도 pending 파일에 저장·동기화한다. |
| 체인 질의 전후 | DB 연결을 닫기 전과 다시 연 뒤 SQL 상태 해시를 비교한다. 변경을 발견하면 새 관측을 적용하기 전에 중단한다. |
| 명령 완료 | SQL 상태를 확인하고 모든 연결을 닫은 뒤, 다시 읽은 상태와 대조한다. 일치하면 새 영수증을 원자적으로 교체하고 pending 파일을 제거한다. |
| 비정상 종료 | pending 기록이 남으면 다음 명령을 중단한다. 확인되지 않은 DB를 새 기준으로 자동 채택하지 않는다. |

SQL 상태 해시는 테이블 정의와 정렬한 행의 내용을 포함한다. 열린 SQLite 파일을 별도의 파일 읽기로 해시하지 않는다. 무결성 검사만으로는 정상 형태의 과거 장부를 식별할 수 없으므로 별도의 마지막 확인값이 필요하다.

일반적인 업무 거절은 해당 명령 뒤의 유효한 상태를 확인하고 영수증을 남긴다. 저장 오류와 예상치 못한 프로세스 종료는 영수증을 갱신하지 않는다. 반환한 `storageReceipt`는 로컬 상태 확인값이며 금융기관의 입출금 증거나 공개 보안 인증서가 아니다.

## 재실행

저장 프로브는 Node 24와 Python 3.12 표준 라이브러리만 사용한다. 실제 체인 SDK나 RPC는 필요하지 않다.

```bash
python scripts/probe_paid_storage.py --python /usr/bin/python3 --directory .local/storage-probe-new --cycles 3 --report .local/verification/storage-probe.json
python scripts/reproduce_storage_rollback.py --report .local/verification/storage-rollback.json
python -m unittest discover -s reference/v0.3-rc1 -p 'test_storage_receipt.py' -v
```

프로브의 `--directory`에는 새 일회용 디렉터리를 지정한다. 각 요청, 작업자 시작/종료 시의 명령 ID·내용 해시·지급 상태, 마지막 확인 DB 세트, 최초 실패 DB 세트를 보존한다. 전체 trace와 DB는 `.local/`에 두며 공개 결과에는 합성 사례 요약과 소스 해시만 포함한다. 실제 장애 조사에서 이 도구를 실금전 장부에 직접 실행하지 않는다.

실제 Sui 통합은 기존 `python scripts/run_localnet.py --paid`가 새 영수증 방어를 거쳐 별도로 실행한다. GitHub CI에는 저장 프로브도 추가하고 기존 공개·유상·ZK 검사를 유지한다. 로컬 네트워크에서 의존성 다운로드가 시간 초과되어 이번 실제 Sui 재실행은 GitHub CI 결과로 별도 확인한다.

## 의도적으로 남긴 제한

- 영수증과 DB가 함께 과거 상태로 돌아가거나 함께 소실되면 이 방어로 탐지하지 못할 수 있다. 별도 실패 영역의 영속 저장·백업·외부 실행 대조가 필요하다.
- 같은 파일시스템의 sidecar와 `fsync` 호출만으로 전원 장애 내구성을 입증하지 않는다. 조사 환경의 overlay 마운트에는 `fsync=volatile` 옵션이 있었다. 이 사실을 과거 기록 유실의 원인으로 단정하지 않는다.
- 영수증과 DB를 임의 변경할 수 있는 공격자에 대한 보호나 제공자 인증을 추가한 것이 아니다.
- 자동 복구·재전송을 구현하지 않았다. pending 상태와 저장 불일치는 원자료를 보존한 채 오프라인 대사를 필요로 한다. pending/영수증을 삭제하거나 현재 DB로 영수증을 다시 만들어 통과시키면 이 방어의 의미가 없어진다.
- 기존 PR #2의 DB에는 영수증이 없으므로 자동 채택하지 않는다. 기존 자료를 보존하고 새 일회용 여정으로 시험한다. 실제 권리나 장부의 이관 절차는 별도 과제다.
- CLI 한 개가 두 시험 DB를 독점 변경한다는 범위다. 여러 운영자·독립 제공자 프로세스의 동시 변경을 지원하는 분산 조정 규격이 아니다.
- 직접 Core/PaidCoordinator를 사용하는 합성 모형에는 CLI 영수증 보호가 자동 적용되지 않는다. 공개 서비스 API로 사용하지 않는다.

다음 완료 항목은 과거 유실의 원인 규명, 안전한 미확정 작업 재개, 실제 제공자 대조, 독립 저장·백업 복구다. 이번 변경만으로 스테이징 운영 준비나 거래 종결을 선언하지 않는다.
