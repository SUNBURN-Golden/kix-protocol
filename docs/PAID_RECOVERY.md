# S03: 중단된 지급의 근거 대사와 명시적 재개

기준: PR #3 `c5121714b58c3e5250740c924733e1964445d102`. 과거 저장 유실의 근본 원인과 독립 저장 내구성은 여전히 미해결이다.

이번 구현은 **유상 시험 CLI의 최초 지급 호출 직전·직후 프로세스 종료**를 다룬다. 보존된 요청과 외부 호출 직전 장부 확인값이 일치하는 경우, 현재 제공자·체인 근거로 재개하거나 이유를 기록해 보류한다. 과거 장부 유실을 자동 수리하거나 모든 미완료 명령을 재실행하지 않는다. 실제 PG·은행 자금은 사용하지 않는다.

## 구현 범위와 판단 근거

- `StorageReceipt`는 정상 CLI의 원 명령을 pending에 보존한다. 실제 지급 호출 직전에 원 요청·멱등 키·전송 허가·SQL 확인값·제공자 기준 자료를 추가로 동기화한다.
- `Recovery.inspect()`는 동일한 로컬 명령 잠금 아래 DB를 읽기 전용으로 대조한다. 원 명령, 요청 바이트, 장부 버전, 제공자 조회 범위·시점, 체인 결과를 복구 계획에 결합한다.
- 실제 체인 조회는 `paid-chain.mjs`가 원 서명 거래 digest의 효과·배분을 검증하고 현재 공연 상태를 조회한다. 호출자가 성공 여부를 입력하지 않는다. RPC는 신뢰하며 체크포인트 증명은 미구현이다.
- 시험용 장애 위치는 주입 프로그램만 안다. 복구 API에는 `before`/`after`, 장애 위치, 시험 정답을 받는 필드가 없다. 호출 직전 확인값의 이름은 모든 실행에서 동일하며 실제 호출 여부를 뜻하지 않는다.

| 관찰 | 결정 |
|---|---|
| 원 요청·장부 확인값 일치, 제공자에 대상 실행 없음, 동일 키 계약·현재 지급 조건·유효시간 충족 | 원 요청·멱등 키로 명시적 재개 |
| 요청에 결합된 제공자 실행 확인 | 기존 실행 연결. 접수·성공 상태·실제 출금을 따로 반영 |
| 조회 부재의 의미 불확실, 만료, 공연 취소로 새 지급 불허 | 보류, 원 예약·의무 유지 |
| 요청·장부·제공자·체인 근거 불일치 또는 자료 부족 | 보류, 이유와 수집 자료 보존 |

계약은 코드가 정한 `kix-mock:stable-key:v1`이다. 모의 제공자는 같은 키·같은 요청을 무기한 중복 제거하지만 이번 재전달 허가는 최초 호출 직전 확인 시점부터 실제 시간 1시간과 모형의 기존 1시간 조건을 모두 만족해야 한다. 외부 사용자가 `replaySafe=true`를 보내 허가할 수 없다. 실제 PG의 보존 기간·조회 완전성·인증은 별도 계약이다.

## 복구 계획의 재검증과 중단 처리

`recovery_apply`는 planId만 받으며 현재 근거에서 계획을 다시 계산한다. 대사 시점 이후 장부·제공자 결과·체인 상태가 바뀌면 `STALE_RECOVERY_PLAN`으로 멈춘다. 원 요청의 재전달 직전, 후보 장부 반영 전, 설치 단계 재시작 시점에 다시 확인한다. 계획 해시에는 판단 근거를 포함하고 조회 시각만 바뀌었다는 이유로 서로 같은 사실을 다르게 취급하지 않는다.

장부의 부분 갱신을 원본에 남기지 않도록 SQLite backup API로 만든 별도 후보에 원자료·관측·취소·금전 분개를 적용한다. 실제 원본은 pending으로 계속 잠겨 있다. 복구 저널에 변경 전·후 SQL 확인값과 근거를 동기화한 다음, SQLite가 기존 WAL을 체크포인트하도록 하고 후보 장부를 원자적으로 교체한다. WAL을 삭제해 진행하지 않으며 체크포인트가 바쁘거나 상태가 달라지면 중단한다.

저널의 `INTENT → INSTALL_READY → DONE`은 복구 프로그램의 진행 기록이다. 재시작 때 원 장부와 후보 장부의 확인값 중 어느 것에 해당하는지 판정한다. 어느 쪽에도 맞지 않으면 계속 보류한다. 제공자 처리 후 복구가 종료돼 계획이 달라졌다면 새 조회에서 기존 실행을 발견하고 새 계획으로 연결한다. 이미 적용한 복구를 반복하면 저장된 결과를 돌려주며 지급·분개·후속 확인 영수증을 다시 쓰지 않는다.

pending 제거는 적용된 후보 장부와 복구 기록을 확인하고 새 영수증을 보존한 뒤에만 수행한다. 파일 수동 삭제·현재 장부의 무조건적 재승인 경로는 제공하지 않는다. `recovery-cases/<planId>/`의 원본 사본·계획·저널·보류 기록은 로컬 조사 자료로 보존한다.

체인 조회와 모의 지급 사이의 원자적 거래를 만든 것은 아니다. 최종 조회 뒤 발생한 공연 취소나 늦은 출금은 후속 대사 대상이다. 이미 발생한 지급은 지우지 않고 환불·회수 의무로 연결한다. 복구 결과는 그때 대조한 근거 범위를 표시하며 모든 미래 외부 사실의 종결을 뜻하지 않는다.

## 실행과 검증

지원하는 유상 CLI 환경은 기존대로 Python 3.12 / SQLite 3.45.1이다. 정상 명령과 같은 stdin JSON에서 다음 action을 사용한다.

```json
{"directory":"/absolute/path/to/paid","action":"recovery_inspect"}
```

```json
{"directory":"/absolute/path/to/paid","action":"recovery_apply","params":{"planId":"조회 결과의 64자리 planId"}}
```

반환한 `decision=HOLD`는 정상적인 보류 판단이다. `RECOVERED`도 지급 완료와 같지 않다. `effect.appliedAmount`, `remainingDuties`, 제공자의 상태·출금 자료를 함께 본다. 예를 들어 접수만 확인하면 지급 적용액은 0원이고 예약이 남는다. 공연 취소 후 114,000원 출금을 확인하면 회수채권 114,000원과 미이행 환불 의무 120,000원이 남을 수 있다.

```bash
python -m unittest discover -s reference/v0.3-rc1 -p 'test_*.py' -v
python scripts/verify_paid_recovery.py --report .local/verification/paid-recovery.json
python scripts/run_localnet.py --paid
```

새 단위 검사 19개를 포함한 Python 검사는 로컬에서 123개 통과했다. 두 원래 중단점 각각에 대해 복구 중 제공자 처리 이후, 후보의 상태 관측 반영 중, 설치 직전, 설치 후·영수증 전, 영수증 후·pending 해제 전, pending 해제 후 종료를 주입한다. 반복 복구·늦은 지급·공연 취소·상충·원 자료 부족·재전달 기간 만료도 검사한다. 합성 단위 검사에는 실제 체인 검증이라는 표기를 붙이지 않는다.

실제 Sui 유상 여정에는 기존 3개 경로에 `recovery-before-call`, `recovery-after-call`을 추가했다. 두 경로 모두 새 Python 프로세스로 정상 CLI를 호출하다 강제 종료한다. 후자는 실제 체인의 공연 취소로 이전 복구 계획을 거절하고, 새 계획으로 기존 지급을 연결한다. 이후 상태·출금 관측을 반영해 장부와 남은 의무를 확인한다. 실행 성공 여부는 해당 변경 커밋의 CI 결과를 기준으로 별도 보고한다.

## 남은 제한

- 과거 자연 유실 원인, DB·확인 기록의 동시 되돌림, 전원 장애, 독립 백업 복구는 해결하지 않았다.
- 기존 PR #3의 pending에는 새로운 전송 직전 확인값이 없을 수 있다. 이 경우 새 확인값을 만들어 덮지 않고 보류한다.
- 최초 지급 호출 직전 상태와 다른 장부, 중단된 최초 발행·리셀 이전·환불 송금, 부분 지급·반환의 통합 복구는 이 경로의 범위가 아니다.
- 같은 로컬 잠금을 따르는 독점 CLI와 모의 제공자에 한정한다. 실제 독립 PG, 다중 서버, 공격자의 파일 변조에 대한 인증·동시성·복구 프로토콜은 아니다.
- 후보·저널·원본 사본도 같은 파일시스템에 있다. 이것을 독립 저장이라고 부르지 않는다.
- 기존 권리·암호 설정·개인정보·외부 발권사 연결의 미완료 항목은 그대로 남는다. S03의 지정 중단점 검증이 G0 전체 완료나 실제 금전 운영 승인을 뜻하지 않는다.
