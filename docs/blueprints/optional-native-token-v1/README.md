# 선택적 자체 토큰 발행·운영 계층 — 청사진 v1 (설계 제안)

문서 버전 0.1 제안 · 작성 2026-09-29 · 상태: **구체 설계·구현 미완료. 설계 제안이며 채택·구현·발행 승인이 아니다.**

사용자 요청으로 개발 범위 편입이 제안된(병합 시 효력) **독립 개발 대상**이다. "언젠가 검토할 아이디어"나 팬 포인트 기능으로 줄여 다루지 않는다.
편입의 효력과 한계는 [범위 편입 결정 기록](../../decisions/TOKEN_LAYER_AND_RIGHTS_SCALE_SCOPE_20260929.md)이 정한다.
이 문서는 다음만 한다.

1. 자체 토큰의 **용도별 필요성을 평가**하고 채택 권고·보류·불채택을 근거와 함께 적는다(§4).
2. **필수 불변식**을 정한다. 관람권·정산채권·대출채권·담보·토큰·실제 지급 자산은 서로 다른 권리·자산이다(§3).
3. 고정된 Sui 소스의 **표준과 호환성**, 공급·분배, 경제적 연결, 권한·보안, 거래 결합, 활성화 조건을 설계한다(§5~§10).
4. TIX 자료를 **등급을 나눠** 기록한다(§11).
5. 후속 작업의 범위·인수 조건·착수 조건을 정의한다(§12).

토큰 모듈, Move, Rust, 회로, SDK, 스키마, 워크플로우는 바꾸지 않았다. 토큰 생성·민팅·판매·유통·풀 개설·바이백, 체인 배포, 외부 트랜잭션 제출, 실자금·PG·은행·KYC 호출은 하지 않았다.

## 1. 위치·범위·비범위

### 1.1 이 계층이 무엇인가

KIX 자체 경제자산(가칭 "KIX 토큰", 이름·기호 미정)의 **역할과 운영 경계**를 설계하는 계층이다. 후보 용도는 프로토콜 이용·수수료, 실행자·참여자의 보증금·책임 담보, 생태계 참여·기여 보상, 거버넌스, 팬 보상·혜택 연계다. **모두 채택한다고 가정하지 않는다**(§4).

### 1.2 "선택적"의 뜻

- **계층의 성격이다.** 토큰을 발행하지 않거나 이 계층을 끄더라도 기본 예매·권리 이전·검표·환불·정산이 성립해야 한다(TK-2). 토큰에 의존하는 기능을 따로 채택한다면 **그 선택 기능만** 제한된다.
- **우선순위를 낮추거나 범위를 줄인다는 표시가 아니다.** 이 계층은 독립적으로 설계·구현·검증된다.

### 1.3 이번 작업에 끼워 넣지 않은 결정

- **자체 체인·L2·합의 네트워크를 만들지 않는다.** 토큰은 Sui 위의 Move 모듈이라는 가정만 둔다.
- **KIX 토큰이 Sui의 네이티브 가스 자산을 대체한다고 가정하지 않는다.** 고정 rev의 공식 문서는 PTB 실행에서 최대 가스 예산을 가스 코인에서 "in terms of SUI" 인출하고 남은 만큼 돌려준다고 적는다(`docs/content/develop/transactions/ptbs/prog-txn-blocks.mdx:149`, blob `757131963bf63296cee3395158864d43d6ede2f3`) **[현재]**. 같은 protocol 136 스냅샷에서 가스를 주소 잔액으로 지불하는 경로의 기능 플래그도 켜져 있다(`enable_address_balance_gas_payments: true`, 스냅샷 `:117`. 소스 주석은 "Enable address balance gas payments"뿐이다, `crates/sui-protocol-config/src/lib.rs:930-932`). 어느 경로든 가스 자산은 SUI라고 **[해석]**하며, 이 청사진은 KIX 토큰으로 가스를 내는 경로를 두지 않는다(TK-9).
- R2, 자체 복제·저장·로그 구현, (a) 통합, 커널 잠금 변경, 실자금 경로는 건드리지 않는다.

## 2. 현재 상태와 기준

### 2.1 토큰 모듈은 없다 **[현재]** **[비활성]**

- Wave 2 검증 기록: "There is no new coin module and no `tix` module." (`validation/2026-09-26-wave2-rights-issuance/README.md:22`)
- `Ticket`은 코인이 아니다. `Issuance` 이벤트의 주석: "Not a fungible coin and not cash." (`rights.move:81-82`). 결제 증거는 "an authorized attester assertion, never proof of bank funds" (`rights.move:4`).
- 새 coin/TIX 모듈은 잠겨 있다. 해제 조건은 "ADR과 Astra 재결정"이다 (`docs/tasks/TASK_005_MEGA_COMMERCE_PROGRAM.md` 결정 5, `docs/decisions/PROGRAM_DECISIONS_20260928.md` §2.1·§5). 이 잠금은 이번에 해제되지 않았다.
- Task 005의 "TIX-parity issuance"는 **티켓 발행 메커니즘의 동등성**을 뜻하며 별도 대체가능 코인이 아니다: "Extending `rights` is not authorization for a separate fungible TIX coin." (`TASK_005_MEGA_COMMERCE_PROGRAM.md:181`).

### 2.2 기존 계약과의 접점 **[현재]**

| 접점 | 내용 |
|---|---|
| 자산 표현 | `AssetSpec(namespace, reference, decimals, max_atoms)`. `decimals` ≤ 38(`reference/v0.3-rc1/assets.py:38`), `MAX_ATOMS = 2**128 - 1`(`:13`). 참조는 (해당하는 경우) 체인·네트워크·토큰 타입을 포함한 완전한 ASCII 참조여야 하고 티커는 자산 식별이 아니다(`:3-5`) |
| 자산 간 산술 | 서로 다른 자산의 `Amount`는 더할 수 없다: `ASSET_MISMATCH`(`:72`). 계약은 "no FX"다(`:1`) |
| 레지스트리 | `RegistryContext`는 "caller-approved fixture/configuration, NOT an authenticated registry, token oracle, credential, observation or execution authorization"이다(`execution_contracts.py:3-4`). 여기서 "token oracle"은 자산 명세를 인증하는 권위가 아니라는 뜻으로 읽힌다 **[해석]**(`assets.py:133`도 같은 표현). 환율·가격 입력은 이 계약에 없다(`assets.py:1`의 "no FX"). 가격원 계약은 **현재 없다** |
| 승인 자산 | KRW는 `AssetSpec("fiat", "KRW", 0, MAX_ATOMS)`(`assets.py:157`). 스테이블코인 항목은 시험 픽스처일 뿐이다(`test_commerce.py:121`) |
| 정산·환불 | 정산 계약과 환불 의무는 KRW 정수 산술이다. "체인 기록이 은행 자금·계약상 채무·공연 이행을 보증하지 않는다"(`docs/contracts/SETTLEMENT_DISTRIBUTION_F01_F03.md:68`). 모두 mock이다 |
| 금융 | "금융 메모는 관람·검표 권한이 아니다"(`docs/contracts/CREDIT_ADVANCE_F04.md:47`). F04는 mock·시뮬레이션만이다 |
| 결제 | 결제수단 1단계는 토스 경유 국내 KRW 일반 카드이고 PG는 잠정 선택이다(`docs/contracts/PG_TOSS_CARD_PROFILE.md:5`). 리셀·금융 가맹 범위와 일반 결제 웹훅 서명은 미확정이다(`:7`) |
| 안정 명령 정체성 | `CommandId`는 "Stable business scope and caller identity. NEVER includes the owner fence."(`runtime/crates/kix-kernel/src/lib.rs:26-28`, 읽기만) |

이 접점이 함의하는 것: KIX 토큰이 생긴다면 **별도의 `AssetSpec`**이며(다른 자산과 합산 불가), KRW와의 환산·가격원은 **현재 계약 밖**이다. 토큰↔KRW 환산이 필요한 기능(수수료를 토큰으로 받기, 바이백, 토큰 담보의 평가와 담보 비율 경보(U2, §7.4), KRW 수익으로 토큰 보상 예산을 정하는 §7.2)은 가격원 계약을 새로 정해야 한다.

## 3. 필수 불변식

### 3.1 서로 다른 여섯 가지 권리·자산

자체 토큰 보유가 관람권·정산채권·원금 상환청구권을 자동으로 만든다고 해석하지 않는다.

| 대상 | 무엇인가 | 원천·권위 | 자동으로 생기지 않는 것 |
|---|---|---|---|
| 관람권 | 특정 공연·슬롯·세대의 입장·이전·검표 권리 | 체인(모델 1). `kix::rights`의 `Ticket` **[현재]** | 토큰 보유·결제 사실·채권에서 자동 생성되지 않는다 |
| 정산채권 | 정수 KRW 총액에 묶인 청구와 수취인별 의무 액면. 법적 채무자, 채권의 발생·소멸, 수익 귀속은 아직 고정되지 않았다(`docs/contracts/SETTLEMENT_DISTRIBUTION_F01_F03.md:56`) | 오프체인 계약과 정산 계약 **[현재: mock]** | 토큰이나 관람권 보유로 생성·소멸하지 않는다 |
| 대출채권·금융 포지션 | 선지급·여신 | 별도 금융 계약 **[비활성: mock only]** | 토큰 보유가 원금 상환청구권이 되지 않는다 |
| 담보·처분 제한 | 채권에 대한 부담 | 별도 계약 **[미구현]** | 토큰 잠금이 담보 완성으로 간주되지 않는다 |
| KIX 토큰(가칭) | 이 청사진의 설계 대상 | 토큰 패키지(가칭) **[미구현·비활성]** | 어떤 권리도 자동으로 부여하지 않는다 |
| 원화·스테이블코인 | 실제 지급 자산. KRW는 승인 자산, 스테이블코인은 별도 채택 전 | PG·은행·자산 레지스트리 **[KRW 승인·스테이블코인 미채택]** | 토큰 전송 성공이 원화 지급 성공이 아니다 |

### 3.2 불변식과 검증 술어 **[제안]**

| ID | 불변식 | 검증 술어 |
|---|---|---|
| TK-1 | 여섯 자산은 서로 다른 타입·기록이다. 암묵적 동치나 변환 함수가 없다. 토큰 보유가 권리를 만들지 않는다 | 토큰 잔액만 가진 주소는 관람권 함수(`offer`·`accept_*`·`authorize_admission`·`consume`)를 통과하지 못한다. 정산·환불 계약은 토큰 잔액을 입력으로 받지 않는다. 계산 계약은 다른 자산 합산을 `ASSET_MISMATCH`로 거절한다 |
| TK-2 | **토큰 없이 성립한다.** 토큰을 발행하지 않거나 계층을 꺼도 예매·이전·검표·환불·정산이 성립한다 | 토큰 패키지가 게시되지 않은 배포에서 `rights` 시험, 로컬넷 공개·비공개 여정, 정산·환불 mock이 그대로 통과한다. 티켓·정산·환불 패키지의 의존 그래프에 토큰 패키지가 없다. 토큰 쪽이 티켓 사건을 읽어야 하는 경우(슬래싱 판정 등)는 티켓 패키지를 직접 import하지 않고 **증거 객체 또는 별도 브리지 패키지**로만 읽는다(TL-1이 정한다). 그런 인터페이스가 정해지지 않은 유형의 판정은 자동화를 약속하지 않는다. TK-2가 자동 슬래싱 약속보다 우선한다 |
| TK-3 | **장애 격리.** 토큰 가격 하락·유동성 부족·토큰 모듈 장애·정지가 기존 관람권의 유효성이나 원화 지급·환불 의무를 소멸시키지 않는다 | 토큰 잔액 0, 유동성 0, 패키지 정지를 가정한 시나리오에서 발급·이전·검표·환불과 KRW 환불 의무 상태기계가 영향받지 않는다 |
| TK-4 | **재원 분리.** 고객 예치금·주최자 정산금·환불 준비금은 토큰 지지(바이백·유동성·보상)에 쓰지 않는다 | 풀별 잔액 보존식. 토큰 관련 지출은 프로토콜 수익 풀과 토큰 보상 풀에서만 나간다(§7.1) |
| TK-5 | **공급 보존.** 발행·소각·배분이 공급량과 배분 예산을 보존한다. 기존 물량 지급과 신규 민팅을 구별한다 | §6의 V1~V6 |
| TK-6 | **권한 분리.** 토큰 관리 권한(발행·소각·금고·업그레이드·정지)은 티켓 발행자·결제확인자·검표자 권한과 다른 주체가 갖는다. AI 출력만으로 민팅·지급·슬래싱을 승인하지 않는다 | 토큰 관리 capability의 보유 주소·서명자·수탁 주체 집합이 `IssuerCap`·결제확인자·검표자의 주소·서명자·수탁 주체 집합과 서로소다(한 수탁자나 키 집합이 여러 주소를 통제하는 경우와 다중 서명 구성원의 겹침까지 본다). 한 주소가 발행과 금고 지출을 함께 갖지 않는다. 모든 실행에 사람이 지정한 승인 기록이 있다. **이것은 목표 불변식이다.** 현재 운영 구조와 바로 맞지 않을 수 있다: 첫 묶음 I11은 사람 승인 주체(기본 승인자와 대체 담당자)를 한 세트로 지정하고(`docs/contracts/FIRST_BATCH_OPEN_INPUTS.md:35`), 같은 수탁자가 키만 나누는 구성은 이 술어를 통과하지 못한다. TL-1은 목표 불변식과 그 전까지의 **기록된 예외**(누가 어느 권한을 겸하는지, 사유, 종료 조건)를 나눠 적고, 예외가 남아 있는 동안 토큰 발행·금고 지출은 시작하지 않는다(localnet 제외) |
| TK-7 | **작업 정체성.** 보상·슬래싱·소각은 원거래의 안정 operation identity에 결합한다. 중복 요청은 효과를 한 번만 낸다 | 같은 원거래에 대한 보상 요청을 재시도·지연 관측·새 트랜잭션 바이트로 N번 해도 지급 효과는 1번이다 |
| TK-8 | **지급 구분.** 토큰 전송 성공과 원화 지급 성공을 혼동하지 않는다 | 두 효과는 별개의 상태기계와 effect ID를 갖는다. 한쪽 성공을 다른 쪽 성공으로 표시하지 않는다 |
| TK-9 | **Sui 자산 비대체.** 토큰은 가스 자산을 대체하지 않고, 자체 체인·L2·합의를 만들지 않는다 | 설계·구현에 토큰으로 가스를 지불하는 경로가 없다 |
| TK-10 | **단계 분리.** 설계 ≠ 비운영 구현 ≠ 통합·보안 검증 ≠ 운영 배포·발행. 단계 전이는 명시적 게이트 기록이 있어야 한다 | 게이트 기록 없이 다음 단계 산출물(배포, 발행)이 존재하지 않는다 |
| TK-11 | **비주장.** 합법성, 인허가 충족, 투자수익, 유동성, 가격 유지를 어떤 산출물에도 적지 않는다 | 산출물 문구 검사 |
| TK-12 | **담보 통화 정합.** 고객 대면 책임의 **단독 담보**로 KIX 토큰을 쓰지 않는다 | 책임 손실이 KRW로 발생하는 항목의 담보 산정에서 토큰 단독 담보가 인정되지 않는다(§4.2 U2) |

## 4. 용도별 검토

### 4.1 평가 방법

각 용도마다 (a) 해결하려는 문제, (b) 자체 토큰이 필요한 이유(주장), (c) 대체 수단과의 비교, (d) 등급, (e) 재평가 조건을 적는다. 이 평가는 데이터 없이 설계 근거로만 한 것이며 **최종 채택은 사용자 결정**이다.

| 등급 | 뜻 |
|---|---|
| 채택 권고 | 설계·검증 대상으로 진행하기를 권고한다. **운영 채택이 아니다.** 권고의 대상이 "메커니즘"인지 "자체 토큰"인지는 카드마다 적는다. U2·U3는 메커니즘이며 자체 토큰의 채택 권고가 아니다 |
| 보류 | 재평가 조건이 충족되기 전에는 설계에 착수하지 않는다 |
| 불채택 | 현재 근거로 채택하지 않는다. 사유가 사라지면 다시 검토할 수 있다 |

### 4.2 용도 카드

**U1. 프로토콜 이용과 수수료**

| 항목 | 내용 |
|---|---|
| 문제 | 프로토콜 수익(발행·리셀 수수료 등)을 받는 방법과 수수료 할인 유인 |
| 토큰이 필요한 이유(주장) | 수수료를 토큰으로 받으면 수요가 생기고 소각과 결합할 수 있다. 할인 수단이 된다 |
| 대체 수단 비교 | **KRW 수수료**: 현행 정산 mock이 이미 수수료를 KRW 정수 bps로 나눈다. **스테이블코인**: 체인 결제를 채택하면 가능. **포인트**: 수수료 크레딧. **권한 객체**: 수수료 면제권 |
| 평가 | 현재 1단계 결제(토스 경유 KRW 일반 카드, PG는 잠정 선택)와 정산·환불 mock은 KRW 전용이다(§2.2). 개발계획 §11은 다중 자산 결합을 범위에 남겨 두었으므로 KRW 고정이 확정된 것은 아니다. 수수료를 토큰으로 강제하면 ① 토큰↔KRW 가격원이 필요한데 현행 계약에 없다 ② 환불 때 수수료 반환이 복잡해진다 ③ 규제·회계 표면이 커질 수 있다(법률·회계 검토 전 미확인) ④ 토큰 가격 하락이 수익 인식에 직결된다 |
| 등급 | 수수료 **지급 수단 강제**는 **불채택**. 수수료 **할인 크레딧**은 **보류**(포인트·권한 객체로 먼저 검증) |
| 재평가 조건 | KRW 외 다중 자산 정산이 채택되고 가격원 계약이 승인된 뒤, 토큰 결제 수요가 실제 데이터로 확인될 때 |

**U2. 실행자·참여자의 보증금 또는 책임 담보**

| 항목 | 내용 |
|---|---|
| 문제 | 위임 실행자(모델 1), 결제확인자, 검표자가 잘못 행동했을 때(허위 결제 증명, 이중 판매, 중복 검표 승인 등) 물을 수 있는 경제적 책임. 현재 결제확인자는 "asserted fiat fact"에 한해서만 신뢰되고(`rights.move:221`), 온체인 담보는 없다 **[현재]** |
| 토큰이 필요한 이유(주장) | 프로토콜에 의존하는 참여자에게 프로토콜 자산을 걸게 해 이해를 정렬하고 슬래싱을 자동화한다 |
| 대체 수단 비교 | **KRW 은행 보증·에스크로**: 손실 통화와 일치. **스테이블코인 담보**: 상대적으로 안정(탈페깅·발행자 동결 위험은 별도), 체인 안에서 슬래싱 가능. **SUI 담보**: 가스 자산이나 변동성. **권한 객체**: 자격 취소만 가능, 경제적 책임 없음. **포인트**: 해당 없음(회수·몰수할 경제적 가치가 없어 책임 담보가 될 수 없다) |
| 평가 | 잘못된 행동의 손실은 KRW(환불 의무·고객 피해)로 생긴다. 담보 통화가 손실 통화와 같아야 실제로 메운다. **자체 토큰은 프로토콜이 부실해질 때 가치가 함께 떨어지는 방향의 위험(wrong-way risk)이 있어 고객 대면 책임의 단독 담보로 부적합하다**(TK-12). 슬래싱은 체인이 객관적으로 판정할 수 있는 위반에만 자동화할 수 있고, 그 증거를 토큰 패키지가 읽는 경로는 TK-2의 증거 객체·브리지 인터페이스로 한정된다(TL-1이 정한다). 허위 결제 증명은 체인이 판정할 수 없어 분쟁 절차와 사람 승인이 필요하다. AI 출력만으로 슬래싱하지 않는다(TK-6). 토큰을 담보로 인정하려면 토큰↔KRW 평가가 필요하므로 가격원 계약이 선행한다(§2.2) |
| 등급 | **메커니즘 채택 권고(조건부)**: 책임 담보(보증금 계층) **메커니즘**을 설계·검증한다. **자체 토큰의 채택 권고가 아니다.** 담보 자산은 비교 후 결정하며, 토큰은 보조·정렬용 추가 담보이거나 스테이블·KRW 담보 위의 초과 담보로만 후보다 |
| 재평가 조건 | 위임 실행(grant·회수 cut)이 구현되어 실행자 책임 손실의 통화와 규모가 정의될 때. 슬래싱에 쓸 객관 증거 유형 목록이 확정될 때. 담보·몰수의 법적 성격에 대한 검토가 끝날 때 |

**U3. 생태계 참여·기여 보상**

| 항목 | 내용 |
|---|---|
| 문제 | 통합 사업자·주최자·판매 채널·팬·추천인이 거래를 가져오도록 하는 유인. 원래 32개 항목의 M04(추천/리워드)는 설계중이다 |
| 토큰이 필요한 이유(주장) | 양도·조합이 가능한 보상, 베스팅을 통한 장기 정렬 |
| 대체 수단 비교 | **KRW 리베이트**: 회계가 단순. **포인트(비양도)**: 규제·회계 표면이 작을 것으로 가정한다(법률·회계 검토 전 미확인). **권한 객체**: 선예매 자격 등. **스테이블코인 보상** |
| 평가 | 보상의 필요조건은 재원, 남용 통제, 지급 정체성이며 이는 **토큰 여부와 무관**하다. 토큰은 양도성과 유동성을 더해 남용(계정 복제로 보상 캐기)과 투기, 규제 표면도 키울 수 있다. 그러나 참여자가 장기적으로 정렬되어야 하고 조합 가능성이 필요해지는 단계에서는 토큰이 구조적 이점을 가질 수 있다(미검증) |
| 등급 | **메커니즘 채택 권고(조건부·순서 고정)** — 자체 토큰의 채택 권고가 아니다: ① 비양도 보상 회계(포인트나 보상 영수 객체)로 재원·남용·정체성 규칙을 먼저 검증한다 ② 토큰 전환은 TL-3 이후의 **선택 기능**이며 그 채택은 별도 결정이다 ③ 양도 가능한 지급(토큰 전환)은 원거래의 **차지백 가능 기간이 끝난 몫에 한한다.** 그 전 몫은 비양도(F3·F4)로 둔다(§9.2) |
| 재평가 조건 | 보상 재원(프로토콜 수익 풀)의 규모와 남용 통제 결과가 데이터로 확인될 때. 법률·회계·세무 검토 결과 |

**U4. 거버넌스**

| 항목 | 내용 |
|---|---|
| 문제 | 파라미터(수수료율·정책 버전·업그레이드·정지) 변경의 정당성과 투명성 |
| 토큰이 필요한 이유(주장) | 이해관계자의 참여와 탈중앙화 |
| 대체 수단 비교 | **다중 서명 capability 보관 + timelock + 문서화된 승인 절차**: 현행 수명 계약은 승인 주체를 사람으로 지정한다 **[현재]**(`docs/contracts/FIRST_BATCH_OPEN_INPUTS.md:35` I11: 인간 지명·권한 범위 확정, 전체 행은 미완결, "AI 자기 위임 확대 금지"). **KRW·스테이블코인**: 해당 없음(지급 수단이지 의사결정 수단이 아니다). **포인트**: 비양도 참여 기록으로 의견 수렴은 가능하나 구속력이 없다. **권한 객체**: 승인 권한을 특정 주체에 부여하는 capability로 표현할 수 있다 |
| 평가 | 현재 위임 실행은 비활성이다(`docs/DEVELOPMENT_PLAN.md` §12). 독립 운영자 집합과 토큰 투표가 대표할 이해관계 집단이 존재하는지는 **[미확인]**이다. 정지·업그레이드·회수처럼 안전에 핵심인 권한을 토큰 투표에 맡기면 사용자 보호와 규제 책임의 주체가 불분명해질 수 있다 |
| 등급 | **보류** (근거가 약해 불채택 쪽에 가깝다는 것이 작성자의 판단이다. §4.1의 세 등급 중 하나를 쓴다) |
| 재평가 조건 | 독립 운영자가 실제로 다수 존재하고, 책임 주체 구조와 법률 검토가 있으며, 안전 핵심 권한은 토큰 투표 대상에서 제외하는 설계가 확정될 때 |

**U5. 팬 보상·혜택 연계**

| 항목 | 내용 |
|---|---|
| 문제 | 팬 자격·선예매·쿠폰·추천 보상(M01~M04)이 거래를 바꿀 때 공통 검증에 결합 |
| 토큰이 필요한 이유(주장) | 보유량 기반 티어, 토큰으로 혜택 구매 |
| 대체 수단 비교 | **권한 객체**: 특정 개인·이벤트·기간에 묶인 자격 증명. **쿠폰**: 정책과 예산 계약(M03). **포인트**. **KRW 할인·환급**: 혜택을 금액으로 지급. **스테이블코인**: 해당 없음(팬 혜택의 단위가 아니다) |
| 평가 | "토큰 보유 = 혜택" 구조는 TK-1(보유가 권리를 만들지 않는다)과 충돌하고, 혜택의 회수·동의·개인정보 관리를 어렵게 한다. 팬 자격은 원래 특정 개인과 이벤트에 묶인 비대체 권한이라 권한 객체가 자연스럽다 |
| 등급 | 혜택 자체는 **권한 객체와 정책으로 구현(토큰 불필요)**. 토큰 연계는 **보류**. "보유 = 혜택" 티어는 **불채택**. "토큰 소각으로 혜택 구매"는 U3 토큰 전환이 검증된 뒤 재평가 |
| 재평가 조건 | U3의 토큰 전환이 통과하고 법률 검토가 끝난 뒤, 소각형 지출(closed-loop `spend`)로 한정해 재검토 |

### 4.3 요약과 권고 역할

| 용도 | 등급 |
|---|---|
| U1 이용·수수료 | 지급 수단 강제 **불채택** / 할인 크레딧 **보류** |
| U2 책임 담보 | **메커니즘 채택 권고(조건부)** — 자산은 비교 후 결정, 토큰 단독 담보 금지. 자체 토큰 채택 권고가 아니다 |
| U3 참여 보상 | **메커니즘 채택 권고(조건부·순서 고정)** — 비양도 회계 먼저. 토큰 전환은 선택 |
| U4 거버넌스 | **보류** |
| U5 팬 혜택 | 권한 객체로 구현. 토큰 연계 **보류**, "보유=혜택" **불채택** |

**권고 역할 [제안]:** 자체 토큰 계층의 설계 대상은 **책임 담보 메커니즘(U2)과 참여 보상 메커니즘(U3) 두 가지**에 한정한다. 이것은 "자체 토큰을 채택하라"는 권고가 아니다. 두 메커니즘 안에서 자체 토큰이 맡을 수 있는 역할(U2의 보조 담보 후보, U3의 선택적 토큰 전환)을 설계 대상으로 삼는다는 뜻이다. 나머지는 보류·불채택이며 재평가 조건이 충족되면 다시 검토한다. 토큰의 존재 자체도 선택 사항이다. TL-0가 이 권고를 확정하거나 바꾼다.

### 5.2 표현 선택지 **[제안]**

| 선택지 | 전송성 | 정책 통제 | 공급 통제 | 적합한 용도 | 주의 |
|---|---|---|---|---|---|
| F1 오픈 루프 `Coin<T>` (Currency Registry) | 자유(`store`) | 없음. 규제형이면 주소 차단·전역 정지뿐 | `TreasuryCap`, 또는 fixed·burn-only | 유통·조합이 가능한 토큰 | 규제형 여부는 초기화 때만 정할 수 있고 되돌릴 수 없다. 공급 모드는 유연(Unknown)이 기본이며 고정·소각 전용으로 바꾸면 되돌릴 수 없다. **`Coin<T>`는 `store`가 있어 배분 즉시 자유롭게 전송된다.** 법률 검토 전에 F1을 배분하면 사실상 유통이므로, 그 단계에서는 F2·F3·F4만 쓴다 |

**담보 보관.** `Balance<T>`는 `store`가 있으므로(`balance.move:36`) 어떤 코인 타입이든 별도 Move 객체(볼트)에 담아 둘 수 있다. 슬래싱 로직은 볼트 모듈에 둔다. 담보 자산 선택(KRW 보증·스테이블·SUI·토큰)과 볼트 설계는 독립이다. **F2 `Token`은 볼트에 담을 수 없다**(`store` 없음). 표준 `spend`는 금액을 정책의 `spent_balance` 하나에 합쳐 예치자별 청구 잔액과 반환 경로가 없고(`token.move:85-91`, `:361-372`, `:599-609`), 요청에서 읽을 수 있는 것은 금액뿐이다(`spent`, `:680-687`). 그래서 환급 가능한 담보를 F2로 만들려면 `to_coin`·`from_coin`을 볼트 모듈의 규칙으로만 승인하는 정책 같은 별도 설계가 필요하고, 가능 여부는 TL-2에서 확인한다 **[미확인]**. 가장 단순한 담보 볼트는 F1의 `Balance<T>` 기반이다.

### 5.3 표준이 제공하지 않는 것

읽은 네 모듈(`coin`, `coin_registry`, `token`, `deny_list`) 범위에서 **소유자의 서명 없이 잔액을 강제로 옮기거나 회수하는 표준 함수는 확인하지 못했다.** 임의 전송·동결·회수가 있다고 가정하지 않는다.

- F1: 동결은 규제형으로 만들었을 때의 **주소 차단**과, 생성 때 허용한 경우의 **전역 정지**뿐이다. 수신 차단은 다음 epoch부터다. 이미 옮겨진 물량의 회수는 없다.
- F2: 관리자는 규칙을 바꾸거나 자기가 낸 요청을 확정할 수 있으나, 사용자 소유 `Token`을 사용자 행동 없이 옮기는 경로는 확인하지 못했다. `ActionRequest`는 능력이 없어 같은 트랜잭션 안에서 소비되어야 하고 토큰 소유자가 만든 요청만 확정할 수 있다(`token.move:98-101`).
- 따라서 설계는 회수·복구를 **약속하지 않는다**.

### 5.4 첫 배포 전에 정해야 하는 비가역 항목 **[제안]**

| 항목 | 왜 미리 정하나 |
|---|---|
| 규제형 여부와 `allow_global_pause` | `make_regulated`는 초기화 때만 가능하고 되돌릴 수 없다. "규제형"은 Sui `DenyCapV2` 기능을 가리키는 용어이며 법적 지위가 아니다 |
| 공급 모드 (fixed·burn-only·flexible)와 초기 민팅 | `make_supply_fixed`·`make_supply_burn_only`는 `TreasuryCap`을 소멸시킨다. `*_init` 변형은 공급이 0이면 중단한다(`coin_registry.move:283-294`). 공급 모드는 유연(Unknown)이 기본이고 한 번 고정·소각 전용으로 바꾸면 되돌릴 수 없다. **F2와 함께 쓸 때:** `TreasuryCap`이 없어지면 `mint`·`burn`·`flush`·`confirm_with_treasury_cap`을 쓸 수 없고(`token.move:402-408`, `:586-609`), 새 정책 생성도 `&TreasuryCap`을 요구한다(`:142-145`). 그래서 `spent_balance`는 `flush`되지 못한 채 총공급에 남는다. 소각형 `spend`를 쓰는 설계와 fixed·burn-only가 충돌하는지 TL-0가 확인한다 |
| 소수 자릿수와 공급 상한 | 총공급은 u64 한도 안이다. 산술 예: 소수 6자리면 최대 18,446,744,073,709 단위, 9자리면 18,446,744,073 단위 |
| 패키지 업그레이드 정책 | 통화 타입은 게시한 패키지에 묶인다. `UpgradeCap`의 보관·제한이 필요하다. 옛 버전 진입점의 존속 여부는 **[미확인]** (TL-1) |
| `MetadataCap` 청구·삭제 | 삭제하면 되찾을 수 없다 |
| 생성 방식 (OTW `init` vs `new_currency`) | 통화가 만들어지는 시점(게시 때 `init` vs 게시 뒤 임의 시점), 등록 절차(`finalize_registration` 필요 여부), 타입 제약(OTW는 `drop`, `new_currency`는 `key`)이 다르다. 소스는 장기적 차이는 없다고 적는다(`coin_registry.move:172`, `:174`, `:209`, `:325-327`, `:353-389`) |

### 5.5 KIX 자산 계약과의 접속 **[제안]**

토큰은 `AssetSpec(namespace=<미정>, reference="sui:<network>:<package>::<module>::<TYPE>", decimals=<정한 값>, max_atoms ≤ 2^64-1)`로 등록한다. Sui 코인의 공급이 u64이므로 이 토큰의 `max_atoms`는 그 안이어야 하며, 다른 자산의 u128 한도를 조용히 줄이지 않는다(`DEVELOPMENT_PLAN.md` §11). 토큰↔KRW 환산은 현재 계약 밖이다(§2.2). Sui `CoinMetadata`의 `decimals`는 표시용 메타데이터다(`coin.move:53-56`). 정수 산술의 기준은 KIX `AssetSpec.decimals`이므로 등록할 때 두 값의 일치를 검증한다.

## 6. 공급과 분배

**숫자는 정하지 않는다.** 총발행량, 배분율, 확정 수익률을 근거 없이 확정하지 않으며 이 문서는 어떤 수치도 약속하지 않는다.

### 6.1 두 가지 연산의 구별

| 연산 | 총공급 | 유통량 | 필요한 기록 |
|---|---|---|---|
| **신규 민팅** | 증가 | 배분 전까지 변화 없음(재무 보유) | 공급 정책의 상한 안인가, 승인 기록, 귀속 프로그램 |
| **기존 물량 지급** (`allocate`) | 불변 | 증가 | 프로그램 예산 안인가, 승인 기록, 수령 조건 |

둘은 이벤트와 승인 기록을 따로 갖는다. 배분 프로그램은 (목적, 예산, 재원[기존 재무 보유분 또는 신규 민팅], 베스팅, 승인자)를 갖는다.

### 6.2 선택지

| 주제 | 선택지 | 장점 | 위험·비용 | 표준 지원 [현재] |
|---|---|---|---|---|
| 초기 발행 | 전량 사전 민팅 후 fixed | 발행 권한 키 위험이 사라진다 | 이후 보상 재원을 만들 수 없다. 사전 배분·베스팅 볼트가 필요하다 | `make_supply_fixed_init` |
| | 부분 민팅 + 상한 있는 추가 발행 | 유연하다 | 발행 권한 키가 남는다. 상한·일정·승인 통제가 필요하다 | `TreasuryCap`이 통제(Unknown) |
| 추가 발행 | 금지 / 조건부 / 일정 | | 조건과 승인 주체를 미리 정해야 한다 | 상한 로직은 자체 구현 |

### 6.3 검증 조건 **[제안]**

F2(폐쇄 루프)에서는 `spend`된 잔액이 `TokenPolicy.spent_balance`에 남아 있는 동안 총공급에 포함되고 `flush`(`TreasuryCap` 필요, `token.move:599-609`)에서 줄어든다. burn-only 모드에서는 보유자가 `coin_registry::burn`으로 KIX 이벤트 밖에서 소각할 수 있다(`coin_registry.move:399-411`). 그래서 재계산은 체인의 공급 상태를 기준으로 하고 어떤 이벤트를 세는지 정의한다 |
| V2 | 프로그램별 지출의 합이 그 프로그램 예산을 넘지 않고, 프로그램 예산의 합이 승인된 배분 상한을 넘지 않는다 |
| V3 | 유통량 = 총공급 − 재무 잠금 − 베스팅 잠금 − 담보 잠금 − (F2면) `flush`되지 않은 `spent_balance`. 각 항의 온체인 근거(보관 객체)가 구별된다 |
| V4 | 민팅은 승인된 프로그램에만 귀속되고, 귀속되지 않은 물량이 0이다 |
| V5 | u64 초과는 표준이 중단시키며, 소수 자릿수와 공급 상한이 정합한다 |
| V6 | 오프체인 공급 보고서와 체인 값이 독립적으로 재계산되어 일치한다. 불일치는 경보와 원인 분류(triage)의 대상이다. 미승인 민팅이나 승인되지 않은 경로가 원인으로 확인되면 지급 정지 조건이다. burn-only 모드의 보유자 소각처럼 KIX 이벤트 밖의 정상 감소는 체인 공급 상태로 재계산해 불일치로 세지 않는다 |

## 7. 경제적 연결

### 7.1 자금 풀 구분 **[제안]**

| 풀 | 성격 | 의무 주체 | 토큰 관련 사용 |
|---|---|---|---|
| 고객 예치금 | 결제 사실 뒤 정산·환불 전의 고객 자금(KRW) | KIX·정산 구조 | **금지**. 고객 지급 의무의 재원이다 |
| 주최자 정산금 | 주최자에게 귀속되는 몫(F01~F03의 의무) | 정산 계약 | **금지** |
| 환불 준비금 | 환불·차지백에 대비한 유보(F03) | 정산 계약 | **금지** |
| 프로토콜 수익 | KIX가 번 수수료 | KIX | **조건부**: 위 세 풀의 의무 이행, 운영비, 손실 충당 뒤의 잔여만 토큰 프로그램에 쓸 수 있다(순서는 제안이며 법률·회계 확정 필요) |
| 토큰 재무·보상 풀 | 사전 배분되었거나 신규 민팅한 토큰 | 토큰 프로그램 | 보상·담보 프로그램에 사용 |

**고객 지급 의무의 재원을 토큰 부양 재원으로 취급하지 않는다**(TK-4).

### 7.2 재원과 지속 가능성 규칙 후보 **[제안]**

- 보상 예산 = min(정책 상한, 직전 N기간 **순 잔여 수익**의 정해진 비율). 순 잔여 수익은 §7.1의 순서대로 세 의무 풀의 이행, 운영비, 손실 충당을 뺀 값이다. 원거래가 환불 가능 창 안에 있는 수익은 창이 끝난 뒤에만 넣는다(총수익이 아니다). 수익이 줄면 예산이 자동으로 줄어든다. N과 비율은 미정이다. **이 식은 예산과 지급이 같은 단위일 때의 식이다**(수익이 KRW이므로 KRW 리베이트 또는 KRW 표시 포인트). 지급물이 토큰이면 토큰↔KRW 가격원 계약이 선행하고(§2.2), 그 계약이 없으면 토큰 지급 프로그램을 만들지 않는다(열린 질문 6).
- **신규 민팅으로 보상 재원 적자를 메우지 않는다.** "적자"는 승인된 보상 예산을 넘는 지급 수요를 뜻한다. §6.1의 사전 승인된 프로그램 민팅(재원이 신규 민팅인 배분 프로그램)은 승인 기록과 공급 상한 안에서 별도로 하며 이 금지의 대상이 아니다.
- 지속 가능성 표시 항목: 예산 소진 예상 기간, 수익 대비 보상 비율, 남용 지표.
- 보상은 원거래가 **환불 가능 창을 지난 뒤**에만 지급 자격이 생기고, 양도 가능한 지급은 **차지백 가능 기간이 끝난 뒤**에만 한다(§9.2).

### 7.3 바이백·스테이킹·슬래싱 — 검토 대상이며 자동 채택이 아니다

- **바이백과 소각은 다르다.** 바이백은 토큰을 취득하는 행위다. 취득한 토큰의 처분(소각, 재무 보관, 보상 재분배)은 별개의 결정이며 회계·세무·법적 함의가 달라질 수 있다(전문가 검토 대상). 소각은 바이백 없이 재무 보유분으로도 할 수 있다.

| | 취득함(바이백) | 취득 없음 |
|---|---|---|
| **공급 영구 감소** | 바이백 후 소각 | 재무 보유분 소각 |
| **공급 유지** | 바이백 후 재무 보관·재분배 | 해당 없음 |

  바이백은 토큰↔KRW 가격원이 필요하고(§2.2) 프로토콜 수익 풀에서만 조달한다.
- **스테이킹**은 U2의 담보 예치를 뜻하는 것으로 한정해 검토한다. 수익률을 약속하는 스테이킹은 검토 범위 밖이다.
- **슬래싱**은 체인이 객관적으로 판정할 수 있는 위반에만 자동화 후보다. 그 밖에는 사람이 지정한 승인자와 이의 절차가 필요하다. AI 출력만으로 슬래싱하지 않는다.

### 7.4 시나리오 **[제안]**

| 시나리오 | 영향 | 규칙 | 시험·모니터링 |
|---|---|---|---|
| 거래량 감소 | 프로토콜 수익 감소 → 보상 재원 감소 | 예산이 수익에 연동해 자동 축소. 신규 민팅 금지 | 수익 대비 보상 비율 경보 |
| 토큰 가격 하락 | 보상의 가치 하락, 담보 가치 하락 | 기존 관람권·KRW 의무는 영향 없음(TK-3). 토큰 담보는 추가 담보 요구 정책 | 담보 비율 경보. 고객 자금으로 방어하지 않음 |
| 보상 남용 (계정 복제, 자전 거래, 추천 농사) | 재원 유출 | 지급 자격은 확정·비환불 거래에만. 보류 기간. 한도. 미지급 보상의 회수 | 이상 탐지 지표. 자전 거래 시나리오 시험 |
| 자금 부족 (보상 풀 소진, 재무 고갈) | 보상 지급 불능 | 지급을 정지한다. 다른 풀로 메우지 않는다. 적립된 청구는 지정된 풀에서만 이행하고 고객 의무보다 우선하지 않는다 | 풀 잔액 경보. 정지 상태 시험 |

## 8. 권한과 보안

### 8.1 권한 분리 매트릭스 **[제안]**

| 권한 | 후보 보유 구조 | 승인 절차 | 반드시 분리할 대상 |
|---|---|---|---|
| 발행(`TreasuryCap` 또는 그 래퍼) | 다중 서명 + timelock. 단일 키 금지 | 승인된 배분 프로그램에 대해서만 실행. 프로그램 예산은 온체인 상한으로 강제 | 금고 지출, 업그레이드, 티켓 발행자 |
| 소각 | 발행과 같은 통제, 또는 burn-only 모드 | 프로그램 승인 | 금고 |
| 금고 보관·지출 | 다중 서명. 프로그램별 한도 | 예산 안에서만. 수령 조건 확인 | 발행 |
| 업그레이드(`UpgradeCap`) | 별도 보관, timelock | 코드 digest 승인, 이전 리허설 | 발행·금고·일반 실행 키 |
| 정지 | 별도 보관. 정지 범위는 **토큰 기능**에 한정 | 사건 기준을 미리 정한다 | 자산 이전·회수 권한 |
| 정책 관리(폐쇄 루프면 `TokenPolicyCap`) | 발행과 별도 | 규칙 변경은 문서화된 승인 | 발행 |

**티켓 쪽 권한과의 분리.** 위 권한의 보유 주소는 `IssuerCap`, 결제확인자, 검표자와 겹치지 않는다(TK-6). 정지는 **토큰 기능만** 멈추며 관람권·정산·환불 경로에는 영향이 없다(TK-3).

**AI.** AI는 배분안 초안이나 이상 징후를 **제안**할 수 있다. 민팅·지급·슬래싱의 승인 주체는 사람이 지정한 승인자다. 개별 실행은 사람이 승인한 프로그램 예산·규칙 안에서만 자동화할 수 있고, AI가 그 범위를 정하거나 넓히지 않는다(`DEVELOPMENT_PLAN.md` §14, `FIRST_BATCH_OPEN_INPUTS.md` I11).

### 8.2 키 사건 경계 **[제안]**

| 사건 | 영향 (표준 기준 [현재]) | 설계 규칙 |
|---|---|---|
| 발행 키 분실 | 신규 발행이 불가능해진다(안전한 방향의 실패). 표준은 분실 키의 복구를 제공하지 않는다 | 다중 서명과 백업 절차. fixed 공급을 택하면 위험 자체가 사라진다 |
| 발행 키 탈취 | 무단 민팅 가능 | 프로그램 예산의 온체인 상한, timelock, 다중 서명. V1 재계산 경보 |
| 탈취 후 대응 | 규제형이면 `DenyCapV2`로 주소를 차단할 수 있으나 수신 차단은 다음 epoch부터. 이미 옮겨진 물량은 회수할 수 없다 | 회수를 약속하지 않는다. 한도를 통해 피해를 제한한다 |
| 교체 | 권한 객체(`store`)를 새 보관 구조로 이전할 수 있다. 코인 타입 정체성은 바꿀 수 없다 | 권한 보유자 교체 절차와 리허설 |
| 비상정지 | 규제형의 전역 정지는 생성 때 허용한 경우에만. 입력은 즉시, 수신은 다음 epoch. **해제도 비대칭**이라 해제 직후에는 입력 사용만 재개되고 수신은 다음 epoch 시작까지 막혀 있다(`coin.move:397-399`). 폐쇄 루프는 정책에서 행동을 막을 수 있다 | 정지 대상은 토큰 기능에 한정. 정지 중에도 이미 일어난 사실의 관측·증거 보존·대사는 계속 가능해야 한다 |

## 9. 거래 결합

**보상과 원거래는 안정적인 operation identity로 결합한다.** 보상의 ID는 (프로그램, 원거래 operation ID, 수령자, 보상 종류)에서 결정적으로 만든다. **규칙 버전은 ID에 넣지 않고 속성으로 기록한다.** 같은 튜플의 보상은 규칙 버전이 바뀌어도 한 번만 지급되며, 규칙 변경으로 보상을 다시 주려면 대체(supersession) 기록과 승인이 필요하다. 원거래 ID는 커널의 `CommandId`처럼 소유 fence를 포함하지 않는다(§2.2).

### 9.1 보상 상태(후보)

| 상태 | 뜻 | 전이 |
|---|---|---|
| OBSERVED | 원거래의 관측 기록 | 원거래 ID 확인 |
| HELD | 환불·취소·분쟁 창 안 | 프로그램의 보류 정책 |
| ELIGIBLE | 지급 자격 확정 | 창 종료, 환불·취소 없음, 남용 검사 통과 |
| ISSUING | 토큰 전송 트랜잭션 제출. 서명 바이트와 digest를 먼저 보존 | 승인 범위 안 |
| ISSUED | 체인 effects를 검증해 발행·전송 결합 확인 | 성공 effects |
| UNKNOWN | 응답 유실·timeout. **미실행으로 취급하지 않는다** | 같은 바이트로 조회·대사. 재전송은 현재 실행 허가·fence가 확인된 경우에 한해 같은 바이트로만 한다 |
| REVERSED | ISSUING 이전에 환불·취소로 자격 소멸 | |
| CLAWBACK_CLAIM | ISSUED 이후 원거래가 환불·취소됨 | 강제 회수 불가(§5.3). 이후 보상과의 상계 또는 손실 처리 정책 |

### 9.2 규칙

| 상황 | 규칙 |
|---|---|
| 중복 지급 | 같은 보상 ID는 효과 한 번. 새 트랜잭션 바이트로 재작성해도 온체인 지급 기록이 같은 ID를 거절한다 |
| 늦은 관측 | 순서와 무관하게 보상 ID로 처리한다. 창이 지난 뒤 도착한 환불도 CLAWBACK_CLAIM으로 남는다 |
| 취소·환불 | 환불은 KRW 경로에서 **토큰과 무관하게** 진행한다(TK-3, TK-8). ISSUED 이전이면 REVERSED, 이후면 CLAWBACK_CLAIM |
| 카드 차지백 | 환불 가능 창이 끝난 뒤에도 카드 차지백이 올 수 있다(`docs/contracts/STATE_LIFECYCLE.md:445`가 늦은 환불·차지백을 위험으로 든다). 양도 가능한 토큰은 강제 회수할 수 없으므로 토큰 전환은 차지백 가능 기간이 끝난 몫에 한하고, 그 전 몫은 비양도(F3·F4)로 둔다. 차지백 가능 기간은 카드·결제 제공자 규정에 따르며 이 저장소 문서에서 확인하지 못했다 **[미확인]** |
| 일부 실패 | 토큰 전송이 실패해도 KRW 정산·환불은 막지 않는다. 반대도 같다. 두 효과는 별개의 effect ID다 |
| 결과 UNKNOWN | 새 보상을 만들지 않는다. 같은 서명 바이트로 조회·대사한다. 재전송은 현재 실행 허가·fence가 확인된 경우에 한해 같은 바이트로만 하며, 허가가 입증되지 않으면 조회·대사만 한다(`DEVELOPMENT_PLAN.md` §9.1) |
| 토큰 전송 vs 원화 지급 | 전송 성공을 원화 지급 성공으로 표시하지 않는다(TK-8) |

## 11. TIX 참고 사례 — 자료 등급 대장

TIX는 참고 사례다. 공식 문서, 공개 SDK, 과거 창업자 발표를 구분하고, 확인한 원문과 날짜를 함께 적는다. **미확인은 미확인으로 남긴다.** 이 조회는 상한을 둔 확인(검색 + 원문 열람 몇 건)이며, **TIX 자료의 추가 확보는 이 설계의 선행조건이 아니다.** 설계 결정 어디에도 이 자료를 근거로 쓰지 않았다.

열람은 2026-09-29에 웹 조회 도구로 했다. 페이지 본문은 **요약기를 거친 결과**이며 원문 바이트를 보존하거나 대조하지 않았다. 아래 따옴표 안의 영문은 요약기가 원문 인용으로 출력한 표현이다. 처음 조회한 뒤 리뷰 지적에 따라 같은 날 인용 형태로 다시 조회해 표의 내용을 확인했다.

## 13. 비주장·잔여 불확실성·열린 질문

**비주장.**

- 이 문서는 토큰 발행이 합법이거나 인허가를 충족한다고, 투자수익·유동성·가격 유지가 있다고 주장하지 않는다.
- 토큰이 구현되었거나 채택되었다고 주장하지 않는다. 총발행량·배분율·수익률을 정하지 않았다.
- 표준 대조는 고정 rev의 소스에 한정된다. 이후 릴리스, 지갑·거래소 호환성, 실제 네트워크 동작은 확인하지 않았다.
- TIX 자료는 참고 사례이며 사실 근거로 쓰지 않았다. 웹 조회는 요약기를 거쳤다.
- 저자 측 점검은 독립 검토가 아니다.

**잔여 불확실성 [미확인].** 토큰의 존재 여부, 역할 확정, 표현(F1~F4), 규제형·공급 모드, 소수 자릿수와 공급 상한, 배분·베스팅, 보유 구조와 승인자, 담보 자산 선택, 토큰↔KRW 가격원, 지갑·거래소 호환성, 옛 패키지 진입점의 존속, F2와 fixed·burn-only의 조합, 주소 잔액 경로와 볼트의 관계, 법률·회계·세무 쟁점의 결론, `docs/research/`와 개발계획 §9.1의 릴리스 커밋 표기 불일치 원인, TIX의 현재 상태.

**TL-0가 답할 열린 질문.**

1. U2·U3 두 역할로 시작하는 것이 맞는가. 다른 역할을 추가하거나 뺄 것인가.
2. 보상의 1단계(비양도 회계)를 포인트로 할지 영수 객체로 할지.
3. 담보 자산의 비교 기준과 후보(KRW 보증, 스테이블, SUI, 토큰).
4. 공급 모드: 전량 사전 민팅 후 fixed와 상한 있는 추가 발행 중 무엇이 U2·U3에 맞는가. F2를 쓸 때 fixed·burn-only와의 조합.
5. 규제형으로 만들 것인가(비가역).
6. 토큰↔KRW 가격원이 필요한 기능(수수료, 바이백, 담보 평가·경보, 보상 예산 산정)을 아예 제외할 것인가.
7. 승인자를 누가 어떤 범위로 맡는가.
8. TL-A ADR이 "범위·한계"로 무엇을 기록하는가(문구 범위와 번호). Astra 판정은 "해당"이며 ADR을 TL-0 앞에 둔다(결정 기록 §4.1).
9. 차지백 가능 기간의 근거(카드·결제 제공자 규정)와, 그 기간 동안 비양도로 두는 보상 단위(F3·F4)의 선택.
10. 환급 가능한 담보를 F2로 할 수 있는가, 아니면 F1 `Balance<T>` 볼트로 한정하는가.
