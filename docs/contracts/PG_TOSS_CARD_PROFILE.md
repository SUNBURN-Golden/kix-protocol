## 3. 늦은 사실은 운영 요구 — 간격과 누적 시점 구분

S2의 마지막 **간격** 4,096분은 68시간 16분이다. 간격 합을 직접 계산하면
1+4+16+64+256+1024+4096=5,461분, **91시간 1분(3일 19시간 1분)**이다.
공식 설명의 최초 전송부터 '3일 19시간'과 구분해 이는 표의 합계 계산임을 표시한다.
실제 처리 지연까지 정확히 이 시각으로 보장된다는 뜻은 아니다. 수일 뒤 지연 통보·
관리 재전송·늦은 API 관측을 보존할 수 있어야 한다. 이를 68시간/91시간 고정 TTL이나
15일 보존 종료일로 정하지 않는다. 실제 재시도·장기 대사·법적 보존기간은 별도 미정이다. LC-TERM은 5,461분을 단독
종결 TTL이 아닌 조건 중 하나로 사용한다. T_anchor와 최초 전송시각 미확인의 처리,
15일 전/후의 재송신 차단은 공통 계약 §5.2–5.3을 따른다.

## 4. 일반 웹훅 서명 미확인 시 방향 — 신호와 사실을 분리

S3의 공개 `tosspayments-webhook-signature` 설명은 payout.changed/seller.changed에만
적용된다. 이를 일반 PAYMENT_STATUS_CHANGED에 복사하지 않는다. S4의 nullable secret
안내만으로 일반 카드 전체 본문의 서명 범위·재전달 방지까지 확인됐다고 보지 않는다.
**일반 결제 웹훅 서명 규격은 확인 불가, 기존 질문지 5번 회신 대기**다.

서명된 webhook을 전제로 하지 않는 설계 방향:

1. 수신 원문·헤더·시각을 미검증 신호로 분류한다. 그 내용으로 captured·종결·권리 발행을 직접 승인하지 않는다. 허용 크기·유입 예산 밖 입력을 정상 제공자 사실로 승격하지 않는다.
2. 현재 등록한 MID/환경/operation에 결합되는 식별자를 확인하고, 서버가 고정한 토스 API와 해당 계정 키로 단건 조회한다. 수신 본문의 URL·키·임의 계정으로 질의하지 않는다. 임의 키 요청이 무제한 조회 부하가 되지 않도록 경계를 둔다.
3. 응답의 계정·paymentKey/orderId·수단/상품·통화·기대 금액·상태·원operation 결합을 대조한다. raw 신호와 인증된 조회 응답·확인시각·출처는 서로 다른 증거다.
4. 검증된 사실만 지원되는 커널 관측으로 정규화한다. 조회 실패/timeout/not-found/unsupported 상태는 미확정 또는 대사 대상으로 남긴다. 현재 snapshot은 모든 과거 이벤트나 미종결 요청 부재의 증명이 아니다.
5. 수신 ACK는 durable custody의 성공을 뜻하도록 설계하며 경제 적용 완료와 분리한다. inbox·인증된 조회가 아직 없으므로 이 문서가 ACK/재시도/실결제를 실제로 수행한다는 뜻은 아니다.

카드의 현재 취소 상태를 'capture가 원래 없었다'로 바꾸거나, webhook만으로 과거 승인
사실을 만들어내지 않는다. 조회에서 결제 취소 이력을 수집할 수 있더라도 취소/환불
종결의 별도 해석과 증거가 필요하다. 서명이 확인돼도 최신 조회·계정 결합·LC-TERM
조건이 자동 면제되지 않는다. TLS+Basic 조회는 통신 상대·계정에 대한 근거이지
외부 검증자가 오프라인 재검증할 수 있는 제공자 서명 증명과 동일하지 않다.

## 5. 테스트 자동화의 제한 — 시험 실행 없음

S5는 국내 테스트 카드번호가 없고 테스트모드에서 실제 카드정보로 시험한다고 설명한다.
따라서 공개 dummy PAN만으로 모든 국내 카드 인증 end-to-end를 무인 재현할 수 있다고
전제하지 않는다. test/live 키와 endpoint·계정을 분리한 별도 승인 시험이 필요하다.
실제 카드의 인증 절차·동의가 필요한 구간은 제한된 수동/상호작용 시험으로 분리한다.
카드번호·CVC·OTP·실키를 Git·채팅·fixture·CI 출력에 보존하지 않는 방향으로 설계한다.

순수 변환·중복·순서 역전·오류 분류는 비식별 fixture/mock에서 자동화할 수 있지만
실제 토스 연동 검증이라고 라벨링하지 않는다. S1/S6의 테스트 오류 헤더·테스트키를
사용한 승인된 sandbox 검증과 브라우저 카드 인증 시험을 구분한다. webhook 신호
처리나 mocked lookup이 통과했다고 실제 서명·종결성을 검증한 것은 아니다.
이번에 계정 발급·카드 입력·결제·웹훅 호출·테스트 코드를 실행하지 않았다.

## 6. 카드 1단계·수단별 종결·작업량 축소

현재 adapter 설계 대상으로 일반 카드 한 경로만 둔다. 간편결제 직접 가맹,
KCP의 noti_id 재사용 매핑, 이지페이의 다거래 장바구니 envelope 분할과 각사 인증·
날짜·금액 매핑은 이번 토스 프로파일의 구현 범위에 넣지 않는다. 이것은 요구 삭제가
아니라 후보가 잠정 좁혀짐에 따른 범위 축소다. 절감 인일의 실측/추정 숫자는 없다.

S3의 PAYMENT_STATUS_CHANGED data는 한 Payment이고, S4의 cancels 배열은 그
결제의 취소 이력이다. 다수 독립 결제의 batch로 취급하지 않는다. 다만 transmission ID의
재전달 불변성이 확인된 것은 아니므로, 전송 identity와 stable economic operation,
정규화한 event-item은 여전히 분리한다. paymentKey는 상태가 변해도 같아 단독 event ID로
쓰지 않는다. lastTransactionKey는 마지막 거래를 가리키므로 고정 capture ID로 대체하지 않는다.
이벤트 매핑식·반복 snapshot의 정체성 관계는 [ADAPTER_EVENT_IDENTITY](ADAPTER_EVENT_IDENTITY.md) 초안 0.1에 둔다. 이 프로파일은 schema를 만들지 않으며 제공자별 값을 바꾸지 않는다.

공통 수명 계약은 provider-specific 종결을 요구하지만 기존에는 결제수단·상품 결합이
명시적이지 않았다. 이번 문서 개정에서는 **provider/MID/환경/API·계약 버전/상품/
결제수단/operation 종류/프로파일 버전**의 범위를 증거에 결합하도록 명시한다.
이는 문서상 경계 정의이며 ProviderOperation나 wire를 변경한 것이 아니다.

토스 내 간편결제·가상계좌 추가 시 각 수단의 실패/입금/취소·반대거래·재전달 의미를
별도로 검토한다. 운영종결 조건도 수단별로 별도 승인하며 현 카드의 부재경로를 자동 승계하지 않는다. S3의 가상계좌 입금오류 재전이는 카드에 이식하지 않는다. S4/S6에
따르면 간편결제에 카드 정보가 함께 있을 수 있으므로, card 객체 하나가 있다는 이유로
일반 카드 범위라고 판정하지 않는다. 요청 경로와 실제 method/type/수단 구성을 대조해야 한다.
범위 밖 수단의 실제 자금 사실이 도착하면 버리지 말고 대사하되 새 권리/전송을 승인하지 않는다.

## 7. 교체 가능한 PG 경계 — 설계만

PG의 URL·credential·상태 문자열·원문 형식은 한 제공자 어댑터 경계 안에 둔다.
코어에는 토스의 15일·웹훅 간격·HTTP 필드/오류명을 박아 넣지 않는다. 어댑터가
통과시킨 증거와 정책 범위를 공통 계약이 다시 대조하도록 한다. 반환형/trait/schema는 미구현이다.

| 책임 | 제공자 종속 부분 | 공통 부분 |
|---|---|---|
| 이벤트 정체성 정규화 | transmission/payment/transaction 필드와 이벤트/조회 의미 매핑 | 원event와 economic operation 분리, 같은 identity 변조 거절, 원문 참조 |
| 서명·인증 | 실제 토스 서명 유무·알고리즘/키 범위, Basic 조회 credential | 출처검증 결과·버전·신뢰 수준·계정 경계; 미검증 신호는 사실 아님 |
| 금액·시각 변환 | JSON 필드·통화 scale·timezone/nullable 원문 해석 | 무손실 정수·u128/자산/registry 결합, 범위 검사, 발생/수신/적용 시각 분리 |
| 조회 경로 | paymentKey/orderId URL, 인증·응답·오류·조회 가능 범위 | stable 원operation 결합·상충 보존·UNKNOWN 유지 |
| 종결 판정 | 수단·상품·API/계약별 status/void/final 증거 의미 | LC-TERM C1~C5·지정 승인·내구 기록·원operation 재송신 차단·후기 사실·조치별 해제 조건 |

국내 KRW ordinary-card profile은 원 단위 정수를 기대한다. JSON number를 f64로
변환하지 않고 정확한 정수/십진 파싱으로 scale·음수·범위·금액 결합을 검사할 설계다.
S4의 approvedAt/requestedAt에는 offset이 있으나 S3의 createdAt 표기에는 offset이
명시돼 있지 않다. 불명확한 timezone을 임의 확정하지 않고 원문·해석 근거를 보존한다.
원발생 시각을 커널의 단조 적용시각으로 대체하지 않는다. 변환 코드·의존성은 추가하지 않는다.

PG를 바꿔도 과거 provider/account/operation 결합은 유지한다. 이미 보낸 UNKNOWN을
새 PG의 새 요청으로 우회하지 않는다. 새 provider는 새로운 승인된 거래 범위에만 적용하고
과거 증거·재시도·대사 책임은 원계정에 남긴다. backend 선택과 이 경계 정의는 별개다.

## 8. 미확정 사항·차단 범위·대안

2026-09-26에 복수 수취인 분리 지급 질문을 한 행 추가했다.
공개 자료 확인일 2026-09-17은 그대로다. 토스에 문의하지 않았고 결제 API를 호출하지 않았다.

| 항목 | 현재 상태·답할 주체 | 미확정일 때 차단되는 것 | 막지 않는 것 |
|---|---|---|---|
| 리셀·금융 대금의 가맹 범위 | 미확정. 사용자가 토스 영업 담당자에게 실제 당사자/MID/자금 흐름별 확인 | 해당 대금의 실제 수취·리셀 판매자 지급/금융상품 결제 제공 승인. 일반 티켓 가맹 가능성으로 확대 금지 | 문서 검토·범위 정의. 일반 예매도 실제 MID·가맹 승인 전 운영하지 않음 |

| 「한 결제의 대금을 복수 수취인에게 분리 지급할 수 있는가. 가능하다면 지급대행 계약이 별도로 필요한가. payout.changed / seller.changed 이벤트가 그 경로인가.」 | **미확인·토스 확인 필요.** 이벤트 이름과 공개 문서는 기능이나 가맹 허용의 증거가 아니다. §4가 적는 `payout.changed` / `seller.changed`는 웹훅 서명 적용 범위다. 이 행은 그와 별개인 가맹 능력 확인이며, 그 이벤트가 복수 수취인 지급을 구현한다는 주장이 아니다 | 분리 지급이 가능하거나 지급대행 계약이 따로 있다고 보고 복수 수취인 지급을 승인하는 일 | 질문을 미확인으로 문서에 남기는 일. §4의 서명 범위 문장 |

기존 질문지의 제출 blob은 `2798352822e7ee657ae789ec370d0390a31febdc`이다.
회신을 받은 것으로 기록하지 않으며 이번에 메일을 보내지 않았다. 원문·대상 MID·
API 버전·회신 권한을 보존하고 프로파일/공통 계약의 변경안으로 검토 후 승인받는다.
인간 승인 발급자/기본 승인자는 박준태, 대체 담당자는 박명운 이사로 지정됐다.
기본 전체·무기한·즉시 철회·승계/복귀 규칙은 공통 계약 §5.4를 따른다. 대체자도
동일한 전체 범위로 확정했으며 유효한 A/B 승계 안에서만 행사한다. 아직 미발급인
`KIX-LC-TERM-HUMAN-AUTH/g0001` 최초 선언에 포함하며 자동 승인 활성 범위 0은 유지한다.
15일 만료 이후 계정 예외·상태/void 증거·조회 보존정책·자동 위임 한도·독립 cut은 계속 미정이다. provider가 보장하지 않는다는 답변이 와도 그것을 받지 못해 운영종결
계약 전체가 닫히지 않는 필요조건으로 남기지 않는다. C1~C5는 그 대신 독립적으로 평가한다.

가맹 범위가 불가로 확인되면 토스는 서면으로 허용된 일반 티켓 경로만 분리해 유지하거나,
불허된 리셀/금융 경로는 그 거래를 허용하는 별도 PG·지급/금융 파트너와의 구조로 재검토한다.
그마저 없으면 해당 자금 기능을 보류하고 권리·계약 검토만 진행한다. 업종·거래 주체를
다르게 표시해 우회하지 않으며, 제공자 교체는 새 거래 범위에 한정하고 기존 UNKNOWN은
원 PG에서 대사한다. 이 문장은 대안 방향이지 다른 제공자의 채택·계약·자동 이행 승인 아니다.

## 9. LC-TERM 변경의 적용 경계 — 2026-09-17

공통 정본은 STATE_LIFECYCLE 초안 **0.6**, 개정 ID
`LC-PRECEDENCE-returnrequired-review-20260919`이다. 0.6은 0.5
(`LC-TERM-alternate-full-scope-20260917`)를 계승하고 §5.7.1에서 ReturnRequired와
review_required의 우선순위·직교성만 명확화한다. 불일치 capture의 Review/격리는
기존 ReturnRequired 상태를 대체하지 않으며 보존된 capture도 지우지 않는다.
운영 종결의 조건·승인 정의는 0.3에서 계승한다. 카드 원천결과 미확인, 처리 흐름 종결,
슬롯 인계·기록 회수·review 해제는 서로 다른 상태/허가다. 가능한 PG 증거가 부족하다는
것과 인증조회 실패/원요청 누락이라는 필수조건 실패를 구분한다. 후자는 사람이 승인해도
통과시키지 않는다. 이미 승인 이력이 있으면 '없었다'로 종결하지 않는다.

기존 표의 '공개 자료가 모든 늦은 결과의 부재를 보장하지 않는다'는 사실은 유지한다.
새 정의로 얻은 것은 외부 사실의 확실성이 아니라 조건·승인·잔여위험의 추적 가능성이다.
3단 자동화는 검토한 설계이고 실제 자동범위는 0이다. LC-FACT만으로 금전/좌석/담보/
늦은 수신 손실이 제한되지 않아 해당 경로는 자동 제외한다. 원문·신호 처리·인증조회·
approval/inbox/slot-release는 여전히 미구현이다. 실제 종결·계약 회신·연동 시험 없음.
