# KIX 프로토콜 수정 명세 v0.2

2026-09-11 · v0.1 상세 검토 및 재현 자료 반영

이 판은 **티켓 권리·거래·정산 기준 모형의 수정판**이다. 취소 이후 미송신 지급 차단, 원결제 취소와 현금 환불 분리, 환불 부담의 즉시 인식, 반환 재고 재발행, 원자료 보존을 코드로 반영했다. v0.1과 첨부 검토 원본은 변경하지 않았다.

권리 정본은 여전히 로컬 SQLite다. 실제 PG·은행·Sui 노드와 연결하지 않았고, 실제 ZK 증명도 구현하지 않았다. 이 문서의 “확인”은 합성 원천을 주입해 기준 모형에서 확인했다는 뜻이다. `fixture_authenticated`, actor 문자열, 최종 검표 로그 표식, 지급 종료 표식은 실제 인증·서명 검증을 대신하지 않는다.

## 3. 데이터와 권리 생애주기

### 재고와 발행된 권리

`inventory["show/A1"]`은 회차의 좌석을 나타낸다. `currentRight`, `version`, `generation`을 가진다. `tickets["right-…"]`는 이번 세대의 관람권 후보 또는 발행된 권리다. 구매 예약에서 새 후보를 만들고, 결제와 거래 확정 조건이 충족되면 `ACTIVE`가 된다. `AVAILABLE`은 이 코드에서 아직 보유자가 없는 발행 후보 상태다.

| 객체 | 중요한 참조·상태 |
|---|---|
| InventoryUnit | 행사, 좌석, 현재 권리 ID, 발행 세대, 재고 버전 |
| AdmissionRight | 재고 ID, 발행 세대, 보유자, 권리 버전, 입장 epoch, 사용 여부, 잠금, 위임 session |
| Trade | 권리 ID, 구매자/판매자, 정책 해시, 조건 해시, 만료, 외부 주문 ID, 결제 ID, 배분 버전 |
| RefundCase | 이유, 원거래, 권리, 정책 해시, 수익자, 부담 주체, 금액, 준비한 실행 경로들의 이력 |
| ExecutionEffect | 의무 계정, 경로, 계약, 시도 ID, 수취인, 원결제, 필요 증거, 준비/송신/부분 이행/완료/종료 상태 |
| RawObservation | 변경하지 않는 원문 바이트·해시, 처리 상태, 인증의 합성 가정, 정규화 결과, 오류 |

관람권의 환불·폐기는 영구 종료다. `release_inventory`는 다음을 모두 확인한다.

- 현재 발행과 닫으려는 권리가 일치하고 재고 버전이 최신이다.
- 옛 권리는 `VOID`이며 사용 기록·열린 위임·잠금이 없다.
- 그 권리의 준비 거래가 모두 종결됐다. 늦은 결제는 환불 의무를 만들 수 있지만 옛 거래를 확정하지 못한다.
- 행사가 열려 있고 판매도 열려 있다.

그 후 새 예약은 발행 세대를 늘리고 새 ID를 만든다. 이전 ID를 다시 `ACTIVE`로 바꾸는 명령은 없다. 전체 상태 검사는 한 재고에 `VOID`가 아닌 권리가 둘 생기는 것을 거절한다. 사용된 권리와 위임 종료가 불명확한 권리는 재발행하지 않는다.

재고 해제는 금전 의무를 없애지 않는다. 이 모형은 권리 종료가 확실하면 환불 지급 완료 전에도 재고를 해제할 수 있다. 옛 구매자의 환불은 옛 거래 풀에 남으며, 새 구매자의 결제금으로 자동 충당하지 않는다. 상품이 ‘환불 완료 후 재판매’를 요구한다면 추가 정책 조건으로 제한한다.

### 게시·예약·확정

게시에는 가격·정책 해시·권리 버전·만료·조건 해시가 들어간다. 게시 자체는 권리를 잠그지 않는다. 구매자가 게시 조건 해시를 수락해 예약하면 배타적 잠금이 생긴다. 이 시험 정책은 게시 중 입장을 허용하며, 입장·양도·환불·위임 등으로 버전이나 사용 가능 상태가 바뀌면 게시를 무효화한다.

예약 만료 시각이 지나면 거래 확정은 즉시 거절된다. 잠금 해제는 별도 `expire_trade`가 거래를 `VOID`로 닫은 뒤 수행한다. 시간 경과만으로 기존 실행을 유효하게 둔 채 잠금을 풀지 않는다. 종료된 예약의 게시도 닫히며 자동으로 다시 게시하지 않는다.

시간은 `advance_clock`으로 주입하는 단조 증가 합성 시계다. 실제 구현은 신뢰할 시계, 허용 오차, 체인 clock/epoch와 PG 요청 만료의 관계를 별도로 정해야 한다.

### 무상 동작과 운영 상태

무상 양도는 보유자의 제안과 수신자의 조건 수락을 결합한다. 수락 시 현재 권리·버전·잠금을 다시 확인한다. 금전 거래의 금액 0 허용으로 구현하지 않는다. 제안에는 원결제 구매자에게 환불이 귀속되는 시험 규칙도 포함된다. 선물 수신자에게 원구매자의 카드 환불 권리가 자동 이전되는 것으로 취급하지 않는다.

초대권은 행사 주최자의 별도 명령으로 승인 한도에서 발행한다. 발행 한도는 누계이며, 폐기했다고 자동 복원하지 않는다. 초대권 취소는 권리를 닫되 없는 결제·환불 분개를 만들지 않는다.

판매 마감, 입장 개방, 공연 완료를 구분한다. 판매를 마감해도 기존 관람권의 입장은 가능하다. 공연 완료 후 입장은 거절한다. 배분 지급은 여전히 모든 수취인에게 공연 완료 이후만 허용하는 시험 정책이다.

## 4. 취소와 지급 송신의 경합

`prepare_effect`는 의무와 자금을 예약한다. `send_effect`는 최초 외부 송신 의도를 영속화하는 경계다. 이 코드 자체는 요청을 송신하지 않는다.

| 취소 당시 실행 상태 | 처리 |
|---|---|
| PREPARED, 아직 미송신 | ABORTED로 닫고 자금 예약 해제 |
| 송신 의도 있음, 결과 불명확 | 의무와 예약 보존. 조회·대사만 허용 |
| 부분 성공/출금 | 확인된 부분만 이행 반영. 남은 실행은 불명확 상태 보존 |
| 완료 | 지급을 지우지 않고 환불 정책에 따른 회수채권 등 생성 |

최초 송신에서는 행사 완료 상태, 해당 거래의 취소 요청, 준비 당시 배분 버전을 다시 확인한다. 조건이 바뀌면 중단한다. 이미 송신 의도가 있는 효과에 새 명령 ID로 `send_effect`를 호출해도 `QUERY_ONLY`만 반환한다. 과거 송신 명령 ID를 재전달한 경우에도 실행 요청 본문을 재교부하지 않는다.

따라서 일반 명령은 기존 영수증을 돌려주는 멱등성을 가지지만, `send_effect`와 마케팅 발송 허가의 재전달은 **과거 영수증이 새 송신 권한이 되지 않도록** 응답을 제한한다.

취소와 최초 송신은 로컬 트랜잭션에서 순서가 정해진다. 송신 의도가 먼저 확정된 뒤 취소됐으면 이미 외부 실행 가능성이 있는 것으로 다룬다. 외부 프로세스가 보유한 요청을 로컬 취소만으로 회수했다고 주장하지 않는다. 이 경계의 원자성은 실제 PG까지 포함하는 분산 원자성이 아니다.

일반 실패 통지나 타임아웃은 자금 예약을 풀지 않는다. `FENCED_FAILURE`는 이 시험에서 최종 실패와 해당 시도의 이후 실행 불가가 확인됐다고 가정하는 별도 증거다. 증거가 있으면 새 effect ID·새 멱등키로 새 시도를 만들 수 있다. 옛 시도의 늦은 출금은 새 성공으로 흡수하지 않고 원자료 검토로 남긴다. 실제 제공자가 이런 종료 보장을 주지 못하면 이 경로를 활성화하면 안 된다.

## 5. 원결제 취소와 현금 환불

토스는 정산받은 결제의 취소와 다음 정산에서의 상계를 설명한다. 따라서 카드 취소를 언제나 가맹점 계좌의 동시 출금으로 표현할 수 없다. 실제 계약과 결제수단별 완료 의미는 어댑터 계약에서 정해야 한다. [토스 결제 취소 안내](https://docs.tosspayments.com/guides/v2/cancel-payment)

| 경로 프로필 | 준비 조건 | 고객에 대한 이행 반영 | 따로 남는 사실 |
|---|---|---|---|
| PG_ORIGINAL_CANCEL_FIXTURE | 원결제 참조, 남은 환불 의무, 원결제 취소 한도, 계약 | 바인딩된 PG_CANCELLED | 고객 계정 반영 확인, 가맹점 PG 정산 조정 의무 |
| CASH_REFUND_FIXTURE | 환불 의무, 해당 풀의 확인된 현금, 수취 계좌 참조, 계약 | 성공 금액과 실제 출금 금액의 일치분 | 미확정 잔여 실행, 사후 반환 |
| BANK_PAYOUT_FIXTURE | 유효한 배분 의무, 행사 완료, 자금, 수취 계좌 참조 | 성공 금액과 실제 출금 금액의 일치분 | 취소 후 회수, 지급 반환 |

`PG_CANCELLED`는 해당 시험 계약에서 가맹점의 원결제 취소 이행을 확인하는 사실이다. `CUSTOMER_CREDIT_CONFIRMED`와 동일하지 않다. 코드의 `refunded`/금융 조회의 `refundFulfilled`는 경로 계약에 따른 이행액이며, 고객 계좌에 실제 입금된 금액이라고 통일해 해석하면 안 된다.

원결제 취소 분개는 환불 채무를 줄이고 `pg_cancel_due`를 만든다. 이후 명시적인 정산 조정 증거가 있어야 PG 부담을 줄인다.

- 정산 전: 원결제 미수와의 `RECEIVABLE_NETTING`을 확인해 상계한다.
- 현금이 이미 입금된 경우: 별도의 `BANK_DEBIT_OBSERVED` 합성 증거가 있으면 확인된 풀에서 출금과 PG 부담 감소를 기록한다.
- 다음 다른 거래의 정산금에서 공제하는 실제 PG 상계는 이 판의 자동 실행 범위에 없다. 그때까지 `pg_cancel_due`를 유지한다. 위 은행 출금 경로가 토스의 실제 계약 방식이라고 가정하지 않는다.

원결제 취소와 현금 환불은 같은 환불 의무 한도를 공유한다. 한 경로가 준비돼 있을 때 다른 경로로 같은 의무를 다시 예약하지 못한다. 일부 의무를 나눠 이행하는 경우에는 각 effect와 경로 이력을 보존한다.

실제 원결제 취소 가능 잔액, 인증된 수취 계좌, 실가맹점 계약은 아직 없다. 이 값들의 문자열이 실제 계약·계좌 확인을 대신한다고 설명하지 않는다.

## 6. 환불 의무와 정산 원장

환불 대상 100,000원이 정해지면 즉시 다음처럼 인식한다.

| 시점 | 차변 | 대변 |
|---|---|---|
| 환불 의무 발생 | 환불 분류 대기 100,000 | 환불 채무 100,000 |
| 미지급 배분 취소 | 미지급 배분금 | 환불 분류 대기 |
| 이미 지급된 배분의 환원 | 수취인 회수채권 | 환불 분류 대기 |
| 출금만 관찰 | 실행 중 자금 | 해당 거래 풀 현금 |
| 현금 경로 성공과 출금 일치 | 환불 채무 또는 배분 채무 | 실행 중 자금 |
| PG 취소 확정 | 환불 채무 | PG 정산 조정 채무 |
| PG 미수 상계 확인 | PG 정산 조정 채무 | 원결제 PG 미수 |

`refund_classification`은 분류 대기 계정이다. 환불 재원으로 사용할 수 있는 자산이라는 뜻이 아니다. 돈의 총액 보존을 유지하면서 의무를 먼저 표시하기 위한 기준 모형의 계정이다.

재현한 대표 결과는 다음과 같다.

| 상황 | 환불 의무 | 미분류 환불 | 미확정 지급 | 환불에 배정 가능한 현금 | 현금 경로 부족액 |
|---|---:|---:|---:|---:|---:|
| 95,000원 지급 준비 후 취소 | 100,000 | 0 | 0 | 100,000 | 0 |
| 95,000원 송신 의도 후 취소 | 100,000 | 100,000 | 95,000 | 5,000 | 95,000 |
| 환불 출금 100,000원, 성공 결과 대기 | 100,000 | 0 | 0 | 0 | 0 |

마지막 행에는 별도로 `refundFundsInTransit=100000`을 표시한다. 이미 출금한 환불을 새로운 자금 부족으로 중복 계산하지 않는다. 성공과 출금이 모두 40,000원까지 확인됐다면 40,000원을 즉시 이행액에 반영하고 잔액을 남긴다.

배분금의 회수 성공을 고객 환불 의무 발생의 전제로 두지 않는다. 현금 환불의 자금이 부족하면 미지급 의무가 그대로 남는다. 원결제 취소는 고객에 대한 취소 이행이 먼저 확인될 수 있고, 가맹점의 PG 부담은 별도로 남는다.

### 명시적 수수료·세금·보류·조정

정산 입력은 다음 식을 만족해야 한다.

`grossAmount = amount + feeAmount + taxAmount + heldAmount + adjustmentAmount`

각 구성의 원천 근거가 있어야 한다. `amount`는 실제 입금분이다. 100,000원 승인과 97,000원 입금만 있으면 나머지 3,000원을 추측해서 수수료로 바꾸지 않는다. 명시적 3,000원 수수료가 있는 정산 자료라면 PG 미수에서 공제하고 플랫폼 비용으로 기록한다. 이 판의 비용 부담자는 명시적 합성 계약의 `platform` 하나다.

수수료가 있다고 약정 배분금을 몰래 줄이지 않는다. 플랫폼의 5,000원 배분금 지급에 현금이 3,000원 부족하다면 그 부족을 보존한다. `observe_funding`으로 확인된 플랫폼 재원을 넣을 수 있으며, 그 자금의 상환 의무도 별도 계정으로 남긴다. 관객 매출로 더하지 않는다. 세금·보류·조정 계정의 실제 회수/해제 절차는 다음 원천 어댑터 작업이다. [토스 코어 API의 정산 및 금액 객체](https://docs.tosspayments.com/reference)

## 7. 환불 정책의 명시적 범위

| 시험 프로필·사유 | 환불 대상 | 권리 처리 | 주의해서 해석할 점 |
|---|---|---|---|
| FULL_CHAIN_UNWIND_FIXTURE | 해당 발행의 과거 구매·리셀 거래 전체 | 현재 권리 폐기 | 기존 회수채권·금액 보존 회귀 시나리오 |
| LATEST_TRADE_UNWIND_FIXTURE의 보유자 환불 | 마지막 확정 거래의 원구매자 | 현재 권리 폐기 | 마지막 거래 배분을 환원하며 이전 최초 판매는 유지하는 분기 시험 |
| 공연 전체 취소 | 행사 전체 거래의 환원 | 모든 관련 권리 폐기/위임 종료 대기 | 이전에 환불돼 이미 VOID인 발행의 거래도 빠뜨리지 않음 |
| 미발행·만료·중단 거래의 늦은 결제 | 해당 미완료 거래의 구매자 | 옛 거래 확정 금지 | 선행 권리나 새 발행을 되살리거나 빼앗지 않음 |
| 무료 초대권 취소 | 금전 환불 없음 | 권리 폐기 | 없는 금전 의무를 만들지 않음 |

두 번째 프로필은 실상품의 권장 일반 환불 정책이 아니다. 예를 들어 판매자 A의 리셀 대금은 환원되지만 A의 최초 구매대금은 환불하지 않으므로, 그 경제적 부담을 누가 받아들일지 별도 계약이 필요하다. 이 판에서는 정책 선택이 다른 의무 집합을 만들 수 있다는 것을 검증한다. 상품용으로는 주최자 부담 환불, 재판매 계약 취소에 따른 권리 반환, 수수료 환불 범위 등을 각각 정의해야 한다.

부분 회차 변경, 재판매 계약 자체 취소, 사후 차지백을 일반 `refund_ticket`으로 대체하지 않는다. 현재 구현된 사후 **현금 지급 반환**은 별도의 반대 자금 사실이다. 지급 반환은 티켓 권리를 복원하지 않는다.

## 8. 외부 사실·시도·재구축

원천 어댑터의 진입점은 `Core.ingest(observation_id, raw_bytes, fixture_authenticated=...)`다.

1. 원문 바이트와 해시를 독립 트랜잭션에 저장한다.
2. 원천 인증을 가정했는지 기록하고 JSON을 정규화한다.
3. 명령 계약과 원결제·효과·금액·통화·수취인 연결을 검증한다.
4. 거래에 반영하거나 검토 상태와 오류를 남긴다.

`Core.execute`의 원천 명령 직접 호출은 낮은 수준의 합성 검사 인터페이스다. 실제 어댑터는 원자료를 건너뛰는 직접 호출을 노출하지 않아야 한다.

같은 거래의 두 번째 결제 ID는 중복 발권하지 않는다. 해당 승인 자료는 `REVIEW`로 보존하고 별도의 미반영 관찰 금액으로 금융 자료에 표시한다. 같은 외부 결제의 여러 관찰은 관찰 ID와 독립된 경제적 참조로 묶는다. 이 표시는 승인·입출금의 실제 귀속을 검토해야 한다는 뜻이며, 확정된 신규 매출·원장 분개를 뜻하지 않는다. 이미 기록된 결제 ID의 다른 거래 귀속 충돌은 새로운 결제금으로 더하지 않는다.

| 식별자 | 역할 |
|---|---|
| observationId | 원자료 한 건의 불변 식별자 |
| sourceId | 정규화된 상태 관찰의 출처 |
| paymentId | 원결제의 식별자 |
| providerOperationId | 하나의 외부 취소·지급 실행 식별자 |
| movementId | 실제 입출금·정산 조정의 경제적 사실 식별자 |
| effectId / attemptId | 코어 의무 실행과 해당 시도 |

같은 observationId에 다른 원문이 오면 원문 충돌 자료도 별도로 보존한다. 원자료 저장 직후 장애가 나거나 원장 반영 직전 실패해도 재처리할 수 있다. 성공한 원장 반영 뒤 inbox의 처리 완료 기록이 늦어져도 영속 명령 ID로 재반영을 막는다.

### 로컬 재구축의 정확한 의미

`export_replay`는 명령 입력·기대 상태 해시·원자료·검토 기록·원문 충돌을 하나의 읽기 트랜잭션에서 내보낸다. `Core.rebuild_fixture`는 빈 DB에서 같은 상태와 미확정 효과를 재구축한다. 거절된 자료를 복구 과정에서 인증된 사실로 격상하거나 새로 실행하지 않는다.

이 내보내기는 **서명되지 않은 로컬 시험 자료**다. 해시 검사는 손상·불일치 탐지이며 운영자 조작 방지 증명이 아니다. 실제 체인 확정 영수증을 검증한 것도, 다른 구현의 검표자가 KIX 서버 없이 티켓을 인정한 것도 아니다. 그 차별화 시험은 후속 구현 계약에서 별도로 정의한다.

## 9. 금융 조회와 마케팅

금융 조회는 상태 원장과 원자료 상태를 같은 읽기 트랜잭션에서 본다. 승인 누계, 권리 확정 누계, 최초 판매·리셀의 환불 의무와 환불 인식 후 순액을 각각 표시한다. 순액은 정의된 합성 환불 의무를 뺀 수치이며, 대출 가능 매출이나 회계상 수익으로 확정하지 않는다.

`asOf`의 로컬 시각/명령 sequence, 정책 해시, 계산기 버전, 원자료 상태 digest를 제공한다. 실제 체인 참조는 `null`, 원천 모집단 완전성은 `NOT_ATTESTED`다. 자료가 하나도 누락되지 않았다고 추정하지 않는다. 연락처나 개별 구매자·판매자 명단을 금융 조회에 넣지 않는다.

동의는 `(주체, 행사, 사업자, 채널, 목적)`별로 버전을 가진다. `expectedConsentVersion`이 현재 버전과 맞아야 갱신한다. 철회 뒤 새 ID로 도착한 옛 동의는 거절한다. 최신 버전을 확인한 진짜 새 의사는 다시 동의할 수 있다.

`authorize_marketing`은 추출 명단을 그대로 신뢰하지 않고 발송 의도 확정 직전에 같은 채널·사업자·목적의 현재 동의를 확인한다. 이미 발송 의도가 먼저 확정됐다면 뒤의 철회가 외부 송신을 소급 취소하는 것으로 가정하지 않는다. 실제 광고 발송은 수행하지 않는다. 기존의 `attended` 대신 `admissionRecorded`로 표시해 검표 기록을 실제 관람 완료라고 부르지 않는다.

마케팅 동의는 현재 로컬 모형의 보호가 필요한 상태다. 공개 체인에 올릴 필드가 아니다.

## 10. 검증과 해석 한계

- 사용자 첨부의 원본 재현 코드로 v0.1 경계 사례 10개를 재현했다. 그 결과는 수정판의 성공 조건이 아니라 비교 근거다.
- 기존 31개 정상·거절 흐름을 새 ID·명령 계약에 맞춰 이식했다. 원결제 취소 포매터 검사는 새 PG 경로에 연결했다.
- 새 검사는 취소 송신 경합, 원결제 취소, 부분 이행, 명시적 수수료, 반환 재고, 게시/예약, 무상 동작, 동의, 원자료 장애와 로컬 재구축을 확인한다.
- 선택한 14개 변이는 원본 상태의 해당 검사가 성공하는 것을 먼저 확인한 뒤, 일회용 사본에서 방어를 제거한다. 구문 오류나 import 실패는 탐지 성공으로 세지 않는다.
- M06은 행사 완료와 현장 gate 설정이 어긋난 경계 입력을 주입해 행사 상태 검사를 고립시킨다. M11도 준비 이후 배분 버전 변경을 주입한다. 일반 API 경로만의 도달성 검사와 구분한다.
- 검사 개수와 14개 변이 결과는 전수 검증·보안 보증·성능 수치가 아니다. 정확한 실행 결과는 `results/verification.json`, `mutation_results.json`, `tests.txt`에 있다.

## 11. 다음 작업의 연결점

다음 구현은 실제 권리 프로그램이다. 이번의 행사·재고·권리·조건 해시·취소 종료 상태를 Sui의 권한과 전이 규칙에 연결한다. 동시에 실제 PG 원천 인증·취소 가능 잔액·정산 상계 계약을 연결해야 한다.

여러 티켓 주문과 수취인별 배분 정책은 별도 모델로 확장한다. 과거 구매자라는 이유만으로 이후 리셀 이익을 계속 배분하는 구조는 추가하지 않았다. 주최자·공연자·공연장 배분이나 차익 기준 산식도 아직 고정 비율 코드에서 확장하지 않았다.

Sui·독립 복구·ZK의 다음 입력/출력, 검증 명제, 종료 조건은 동봉한 `KIX_Sui_ZK_후속구현계약_v0.2.md`를 따른다.
