# S05: 분리된 보존 기록과 새 작업 환경의 장부 복원

개발 기준은 PR #4 `f2a370dd55c29d7b3403e3872489bd965e38411e`다. 이 변경은 **원 운영 폴더 전체 유실**을 시험한다. 보존 저장소와 모의 제공자는 원 폴더 밖에서 살아 있다는 조건이다. 과거 자연 유실의 원인은 계속 미해결이다.

## 이번에 구현한 범위

- 선택한 유상 시험 CLI에 별도 파일시스템의 보존 저장소를 연결한다. 이후 정상 명령은 저장된 연결 설정을 사용하므로 다음 요청에서 설정을 생략해도 보존을 끄지 않는다.
- 명령 의도, 최초 지급 호출 직전의 원 요청·멱등 키·허가·장부 확인값, 명령 완료 및 S03 복구 완료를 보존한다. 보존 확인을 받기 전에 지급 호출 또는 성공 응답을 진행하지 않는다.
- SQLite backup API로 일관된 사본을 만들고, 복사 전후 SQL 내용과 사본을 대조한다. 열린 원본 DB의 파일만 읽어 백업하거나 WAL을 지우지 않는다.
- 보존 기록은 내용 해시·순서·직전 기록 참조를 가진다. 별도 저장소의 최신 기록과 작업 폴더의 확인값을 비교하므로 작업 폴더의 DB·영수증·포인터가 함께 과거로 돌아간 경우도 차단한다.
- 복원은 원 운영 폴더에 접근하지 않는다. 별도 저장소의 최신 기록과 연결 관계를 검증하고 새 폴더에 설치한다. 오래된 유효 사본을 최신 사본 대신 선택하거나 손상된 최신 사본을 피해 과거 사본으로 내려가지 않는다.
- 복원된 DB 안의 제공자 사본은 **과거 관측 자료**다. 별도로 살아 있는 제공자의 현재 DB를 조회해 원 요청과 대조한다. 그 DB에 백업을 덮어쓰거나 지급을 전송하지 않는다.
- 실제 Sui 조회는 S03의 원 거래 효과·배분 검증과 현재 공연 상태 확인을 재사용한다. 복원 경로도 신뢰하는 RPC 범위이며 체크포인트 증명은 아니다.

## 완료와 보류의 의미

| 결과 | 의미 |
|---|---|
| `RESTORED_READ_ONLY` | 보존한 원 요청·장부·확인 기록을 새 폴더에 복원했다. 현재 외부 사실의 대사를 완료했다는 뜻은 아니다. |
| `RECONCILED_VIEW` | 보존한 요청에 결합되는 현재 제공자 실행과 체인 근거로 회계 조회 결과를 다시 계산했다. 지급 권한은 없다. |
| `HOLD` | 자료 부족·상충·권한 부재로 재개하지 않는다. 원 장부의 예약과 의무를 보존한다. |

호출 전에 종료된 지급은 현재 제공자에게 실행이 없을 수 있다. S03의 동일 키 계약이 재전달을 허용하더라도 이 복원 프로파일은 `RESTORED_WRITER_NOT_AUTHORIZED`로 보류한다. 새 운영자를 지급 실행 주체로 승인하는 이관·동시 실행 차단은 이번 범위에 포함하지 않았다.

호출 후 종료된 지급은 살아 있는 제공자의 실행에 연결한다. 접수만 있으면 적용액은 0원이고 예약이 남는다. 공연 취소 후 실제 모의 출금 114,000원이 관측되면 회수채권 114,000원과 미이행 고객 환불 120,000원을 조회 결과에 보존한다. 기록이 정확하다는 사실과 환불·회수의 실제 이행은 구분한다.

복원 폴더의 `restored-from-archive.json`은 정상 유상 CLI와 S03의 `recovery_apply`를 차단한다. 내부 Python 모형 API는 여전히 신뢰하는 시험 코드용이며, 이 파일 검사는 악의적 관리자를 막는 보안 경계가 아니다.

## 시험용 실행

Linux의 다른 파일시스템에 디렉터리를 준비한다. 다음의 `/dev/shm`은 로컬 검사에 쓰는 tmpfs다. 원 운영 폴더 삭제에는 견디지만 **호스트 재부팅·정전에는 보존되지 않는다. 운영용 백업 저장소 추천이 아니다.**

```bash
mkdir -m 700 /dev/shm/kix-archive-example
```

지원하는 유상 CLI 환경은 기존과 같은 Python 3.12 / SQLite 3.45.1이다. 첫 보존 요청에 다음 설정을 추가한다. 기존 정상 영수증과 일치하는 상태에서만 등록한다. 등록 전 과거 요청까지 별도로 보존했다고 주장하지 않는다.

```json
{
  "directory": "/absolute/working/paid",
  "endpoint": "http://127.0.0.1:9000",
  "action": "send_effect",
  "params": {"eid": "existing-prepared-payout"},
  "archive": {"root": "/dev/shm/kix-archive-example", "stream": "show-one"}
}
```

위 JSON은 기존 `reference/v0.3-rc1/paid_driver.py`의 stdin으로 전달한다. 자료 확인용으로 새 지급을 만들지는 않는다. 이미 준비된 시험 지급에만 적용한다.

복원과 대사는 `reference/v0.3-rc1/archive_driver.py`의 stdin으로 전달한다.

```json
{"action":"restore","root":"/dev/shm/kix-archive-example","stream":"show-one","target":"/absolute/new/paid-view"}
```

```json
{"action":"reconcile","target":"/absolute/new/paid-view","providerDatabase":"/separate/provider/live-provider.sqlite"}
```

현재 제공자 경로는 신뢰하는 관리자가 지정하는 독립 모의 제공자 DB다. 복원 폴더나 보존 저장소 안의 사본을 지정하면 거절한다. 경로 검사만으로 실제 PG의 인증과 조회 완전성을 보장하는 것은 아니다.

## 검증 근거

- 두 Python 환경에서 기존 검사를 포함한 141개 검사를 각각 직접 실행했다. 새 검사 18개에는 실제 원 폴더 삭제, 전체 로컬 상태 되돌림, 보존 장애, 오래된 사본·손상된 최신 사본, 잘못된 제공자, 복원 설치 전후 프로세스 종료, 반복 복원·대사, 늦은 제공자 결과·체인 변경이 포함된다.
- `scripts/verify_paid_archive.py`는 두 유실 사례의 원 요청·현재 제공자 관측·합성 체인 근거·예약·잔여 의무와 소스 해시를 보존한다. 이 실행의 체인은 합성이다.
- 실제 Sui 유상 여정에는 `archive-before-call`, `archive-after-call`을 추가했다. 각각 별도 운영 폴더를 삭제하고 새 Python 프로세스에서 복원·대사한다. 후자는 원 폴더 삭제 후 실제 체인 공연 취소와 모의 제공자 출금을 확인한다.
- 실제 Sui·기존 ZK의 실행 성공 여부는 해당 변경 커밋의 GitHub CI에서 별도로 확인한다. 이 문서 작성 시 로컬 Sui·ZK 재실행 결과로 계산하지 않았다.

```bash
python -m unittest discover -s reference/v0.3-rc1 -p 'test_*.py' -v
/usr/bin/python3 scripts/verify_paid_archive.py --report .local/verification/paid-archive.json
python scripts/run_localnet.py --paid
```

## 남은 신뢰와 제한

1. 원 작업 폴더를 쓸 수 없고 별도 파일시스템은 살아 있는 장애만 검증한다. 별도 서버·클라우드의 실제 내구성, 호스트 전체 유실, 정전, 보존 저장소 자체의 전체 되돌림은 미검증이다. 해시 연결은 보존 저장소 자체의 오래된 head를 알아내는 외부 기준이 아니다.
2. 신뢰하는 단일 운영자·로컬 잠금·모의 제공자 범위다. 다중 서버의 쓰기 권한 이관, 원 운영자와 복원 운영자의 동시 실행 차단, 실제 PG 인증은 별도 개발이다.
3. 현재 대사 계산은 S03과 같은 **호출 직전 근거가 남은 최초 지급**에 한정한다. 다른 유형의 복원 장부는 조회 자료로 보존되지만 전체 거래를 자동 재개하지 않는다.
4. 원 요청·지급 허가·영수증은 포함하지만 개인 지갑 키, 비공개 노트, 증명 생성 파일의 독립 복구는 R01의 별도 대상이다.
5. 보존 자료는 소유자 전용 파일 권한의 합성 금융 자료다. 실제 개인정보·지급 계정 자료의 암호화·접근 권한·보관 정책을 검증한 것은 아니다. GitHub에는 코드와 합성 실행 근거만 보관한다.
6. 기록 보존 실패 시 후속 실행을 차단한다. 모든 보존 실패 지점에서 원 운영자를 자동 재개하는 기능은 아니다. G0 전체 완료와 실제 금전 운영 준비를 선언하지 않는다.
