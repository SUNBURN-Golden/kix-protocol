# 유상 리셀·권리 확정·정산의 첫 연결

2026-09-14. ZK 보완 커밋 `a13244f`를 기준으로 추가했다. `main`이나 기존 공연에 자동 적용되는 변경은 아니다.

이번 범위는 **이미 발행된 공개 티켓의 유상 리셀 1회**다. Sui 로컬넷의 실제 권리 이전과 Python 배분·정산 모형을 연결했다. PG·은행은 별도 SQLite에 상태를 보존하는 **모의 제공자**다. 실제 결제나 은행 지급을 검증했다는 뜻이 아니다.

## 실행

```bash
bash scripts/bootstrap.sh
source scripts/env.sh
python scripts/verify_runtime.py
python scripts/run_localnet.py --paid
```

`--paid`는 공개 여정에 추가해 새 공연 세 개로 아래 경로를 실행한다. ZK 증명 생성 파일은 필요하지 않으며 `--private`와 함께 사용할 수 없다. 결과는 `.local/verification/paid-journey.json`에 기록한다.

유상 시험의 조정자는 Ubuntu 24.04의 `/usr/bin/python3`를 기본으로 사용하며 **Python 3.12 / SQLite 3.45.1**을 요구한다. 다른 경로는 `KIX_PYTHON`으로 지정하되 같은 검증 조건을 충족해야 한다. 조건이 다르면 체인을 만들거나 장부를 열기 전에 실패한다. 이 버전 고정은 제한된 시험 재현 조건이며 운영용 SQLite 버전 추천이 아니다.

## 권위와 연결 방법

| 영역 | 이번 구현의 근거 |
|---|---|
| 권리 이전 | 실제 Sui `accept_sale` 영수증과 BCS `Allocation`·`Change` 이벤트 |
| 결제·입금·지급 관측 | 독립된 `mock-provider.sqlite`의 모의 제공자 기록 |
| 배분·환불 의무·회수할 금액 | 위 관측을 반영한 `projection.sqlite`의 Core 복식 장부 |
| 공연 완료에 따른 지급 해제 | 시험 관리자가 주입하는 공연 완료 가정. 공연 사실 인증은 미구현 |
| 인증 경계 | 로컬의 신뢰된 실행 프로세스. 인터넷 요청을 받는 API가 아님 |

`paid_driver.py`의 시험 명령은 매번 새 Python 프로세스로 실행되고, 체인 관측도 별도 Node 프로세스가 로컬 RPC에서 조회한다. 외부 요청의 `actor`·`source` 문자열을 인증으로 사용하는 API를 추가하지 않았다. 모의 제공자와 장부는 별도 데이터베이스여서 제공자만 처리한 뒤 응답을 잃는 상황을 보존할 수 있다.

자식 RPC 프로세스를 시작하기 전에 두 DB의 커밋 완료를 확인하고 연결을 닫는다. 프로세스가 성공·실패·시간 초과로 끝난 뒤 연결을 새로 열어 관측을 저장한다. 각 시험 명령에 `quick_check`가 포함되며, 실패한 새 여정은 이전 성공 결과 파일을 남겨 이번 성공처럼 보이게 하지 않는다.

`Projection._commit_trade`는 저장된 체인 성공 근거가 없으면 소유권·배분 확정을 거절한다. 성공 근거를 저장하고 장부를 반영하기 전에 종료돼도 같은 작업 ID로 재실행한다. 기존 Core의 단독 합성 실행 의미는 바꾸지 않았다.

초기 권리 상태는 Core의 무상 초기화 경로로 가져온다. 실제 티켓이 초대권이었다거나 최초 구매가 결제됐다는 뜻이 아니다. 이번 장부에 최초 발행·구매의 금융 이력을 만들지 않는다.

## 고정하는 거래 조건

거래 ID에 체인·패키지·공연·티켓·슬롯·세대·권리 버전·판매자·구매자·금액·KRW 통화·만료 시각·Move `Terms` 해시·주최자·배분 비율·가격 상한·정책 해시를 결합한다. 준비 시 체인의 현재 제안 및 Move와 동일한 BCS 직렬화 해시를 확인한다. 같은 거래 ID로 조건을 바꾸면 거절한다.

Move `Terms`에는 통화 필드가 없으므로 어댑터는 **KRW만** 허용한다. 정책 해시는 어댑터의 고정 정책이며 온체인 정책 레지스트리는 아니다. 주최자·플랫폼 몫을 각각 정수 나눗셈하고 잔액을 판매자에게 배분한다. 이번 PG 수수료·세금·보류액은 모두 0인 모의 계약이다.

결제 참조는 제공자 범위와 제공자 결제 ID로 만든다. 동일 결제 ID의 다른 거래 귀속은 장부가 거절한다. Sui `PaymentEvidence`도 제안에 결합되고 소비 시 삭제된다. 여러 조정자·가맹점·공연에 걸친 결제 참조 관리와 권한 있는 PG 사실 확인은 별도 개발 대상이다.

## 불명확한 결과의 처리

서명한 Sui 요청과 정확한 digest를 체인 전송 전에 저장한다. 새 프로세스는 그 digest를 조회한다. 성공 시 이벤트의 티켓·금액·배분·판매자와 새 보유자·버전을 대조한다. 체인 결과가 없거나 RPC 조회가 실패하면 `OUTCOME_UNKNOWN`을 유지하며 새 이전을 만들거나 환불을 시작하지 않는다.

실패 영수증만으로 자동 환불을 허용하지 않는다. 이번 보상 경로는 **공연이 영구히 닫혔고, 원 판매자가 같은 버전의 티켓을 보유하며, 저장한 이전 요청이 실제 실패한 경우**로 제한한다. 다른 실패 원인은 검토가 필요하다. 원래 Move 패키지에는 닫힌 공연을 다시 여는 기능이 없다.

공연이 닫혔는지 확인한 뒤 새 지급을 준비·전송한다. 체인 조회와 은행 실행은 하나의 원자적 거래가 아니다. 조회 이후 취소되거나 이미 지급을 보냈다면 미확정 지급의 자금 예약을 유지한 채 늦은 결과를 반영하고 회수 의무를 남긴다.

지급/환불은 전송 의도·작업자 허가를 먼저 저장한다. 이후 같은 요청은 제공자를 조회한다. 제공자에 기록이 없을 때 자동 재전송하는 조건까지 구현하지 않았으므로 조회만 한다. 전송 허가 직후 실제 호출 전에 중단된 작업은 보류될 수 있다. 결제 요청 재전송은 모의 제공자의 무기한 동일 키 보존 계약에서만 시험했다.

## 남은 최소 개발 항목

1. **최초 유상 구매·발행과 실제 제공자 테스트 환경**: 발행 중복 방지, 인증·웹훅 검증, 제공자의 멱등 보존 기간·조회·실패 확정 계약을 연결한다.
2. **미확정 작업의 재개**: 조회 결과가 없는 지급의 안전한 재전송, 이전 실패 유형별 권리 확인·보상, 중단 지점별 복구를 확장한다.
3. **환불 의무 해소**: 남긴 회수할 금액을 회수 근거로 닫고, 부분 지급·부분 환불·사후 반환을 통합 경로에서 확인한다. 기존 Python 단독 검사를 통합 완료로 세지 않는다.
4. **범위 확장**: 공연당 여러 티켓·반복 리셀·입장 경합과 여러 조정자의 일관성을 검증한다. 현재 어댑터는 한 공연당 거래 하나, 공개 권리 버전·세대 1만 받는다.

별도로 ZK 새 컴퓨터 복구, 기존 공연 키 교체·권리 이관, 비공개 리셀·환불은 남아 있다. 이 변경은 Move·ZK 회로·키 설정을 수정하지 않는다. 운영용 배포나 Vercel Import를 승인하는 결과가 아니다.

## 개발 중 발견한 저장 경계 문제

초기 구현은 DB 연결을 보유한 채 Node 자식 프로세스를 실행했다. Python 3.12.14 / SQLite 3.53.1 환경의 반복 실행에서 DB 손상과 저장한 요청의 유실이 관측됐다. 별도 Python 3.12.3 / SQLite 3.45.1 실행은 통과했지만, 이것만으로 SQLite 버전 자체의 결함이라고 단정하지 않았다. 명시적인 WAL 체크포인트도 문제를 해결하지 못했고, 임시 rollback journal 실험에서는 읽기 전용 DB 오류가 발생했다.

자식 프로세스를 거치는 동안 DB 핸들을 유지하지 않도록 보완하고, 시간 초과에도 새 연결을 여는 회귀 검사를 추가했다. 이 변경 뒤 기본 런타임에서 한 차례 통과했지만 추가 실행에서 전송 기록 누락이 다시 관측됐다. 따라서 연결 수명 변경만으로 해결됐다고 주장하지 않는다.

최종 시험 CLI는 통과한 Python 3.12 / SQLite 3.45.1 구성으로 제한하며, 나머지 구성에서 금융 여정을 시작하지 못하게 한다. 원래 WAL + `synchronous=FULL`은 유지한다. 근본 원인과 다른 런타임 지원, 운영 저장·백업 검증은 남은 차단 항목이다. 손상된 장부를 임의 복구하거나 검사를 생략해 성공 처리하지 않는다.

첫 GitHub 실행은 공개 로컬넷 종료 직후 다음 여정의 포트 검사에서 멈췄다. 사전 바인드 검사에 `SO_REUSEADDR`를 지정해 종료된 연결의 `TIME_WAIT`을 허용하되 실행 중인 리스너는 계속 거절한다. 실제 소켓으로 두 경우를 구분해 검사했다.
