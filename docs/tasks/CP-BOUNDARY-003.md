## Work order

### 1. Establish the actual enforcement surface

Read the installed GitHub runner version/source and service configuration; query repository owner type, rulesets/protection and available runner access controls. Permission errors are UNKNOWN, not proof that no protection exists. This ChatGPT session observed an empty ruleset list but received HTTP 403 for branch-protection access; operator must resolve with its authorized read path.

The candidate mechanism is a protected pre-job hook, possibly combined with supported runner access restrictions. It is NOT pre-approved as sufficient. GitHub documents hook execution, not a blanket guarantee that a hook is an authorization boundary. Inspect exact runner ordering and validate it. Repository labels, workflow `if`, writable environment variables, and branch protection alone are not acceptable proof.

If the available mechanism cannot meet the outcome, preserve disabled state and return one minimal architecture exception with a demonstrated bypass and concrete alternative. Do not silently migrate repositories, buy another plan, or build a new orchestration platform.

### 2. Implement the smallest defensible boundary

Expected trusted identity includes repository and owner IDs, approved ref, workflow path, event, actor, and approved workflow/source revision or digest. Claims supplied by task text or arbitrary process environment must not self-authorize access. Pin and verify relevant source/actions; do not fetch and execute mutable code as part of an admission decision.

Hook, policy, interpreter/launcher and runner service/configuration must not be writable by builders or job code. Prevent checkout/PYTHONPATH/module shadowing, PATH/shell/environment injection and script-path substitution. Missing configuration, source mismatch, unverifiable origin and validation failure must deny. Authentication material must not enter source, job output, packets or provider environments.

No general-purpose sudo, Docker socket, root shell, arbitrary command endpoint or merge credential may be given to a probe job. Root/operator authority remains outside agent jobs.

Keep the existing production runner disconnected and runtime_enabled=false. Prepare a versioned installation/rollback procedure; do not deploy an unreviewed security boundary into production.

### 3. Prove rejection before side effects

Use a disposable or tightly isolated staging probe runner with no real provider/control secrets, host-admission privilege, shared credential directory, or production runner label. Do not substitute ordinary unit tests for actual runner behavior. A paid/new external machine requires a separate User decision.

Positive case: an explicitly approved harmless probe workflow/source completes a sentinel action exactly as intended.

Negative cases: wrong repository/ref, wrong workflow/event/actor, unapproved source, missing/modified hook or policy, environment/default-shell injection, attempted hook override, and a workflow containing pre-actions, service/job containers and `if: always()` steps after rejection. For each, prove the forbidden sentinel/action did not execute; failure exit status alone is insufficient. Distinguish an unavailable test from a rejected attack.

Probe policy and production policy are separate. Do not enable the production policy or assert production coverage because the probe used its own approved test path. Record any platform limitation preventing a test.
